# Development Guide

Product plan capability options come from the backend's compiled catalog and the frontend feature manifest. Basic administration remains available and follows RBAC; notices and tenant-initiated message publishing can be enabled or disabled by plan. The initial capabilities use the `standard` variant and a strictly empty object configuration. Disabling notices closes their administration and read endpoints; disabling tenant-initiated messages rejects new publications. Existing data and accepted messages are retained, and system notifications continue to run. Tenant, product plan, data target, and platform infrastructure administration belong to the system tenant and cannot be opened to ordinary tenants through permission wildcards, menu grants, or configuration packages. The system tenant has the deployed administration capabilities, subject to actual infrastructure availability checks.

## Environment and Configuration

Local development verification uses Windows. MySQL 8.0.16 or later, a Redis 7.x protocol environment, and RustFS/MinIO/S3-compatible storage can run on any platform that meets the version, protocol, and connectivity requirements; remote services are also supported. WSL is not required. After installing rustup, run `rustup show` in the project directory to install and select the pinned Rust 1.98.1, rustfmt, and Clippy. The project uses Rust 2024 edition with a minimum Rust version of 1.98; local development, CI, and production build images use the same pinned toolchain. `APP_ENV` is the only project configuration environment entry, for example `$env:APP_ENV = "dev"`, accepting only `dev`, `test`, or `prod`. `config/app.toml` supplies common defaults, and the selected `config/app.<environment>.toml` must exist. Addresses, passwords, JWT, Redis, storage and monitoring credentials use plaintext configuration fields directly. Keep real configuration in ignored local directories and do not commit credentials. Applications select a directory through `--config-dir <directory>`, defaulting to `config`, with relative paths resolved from the current working directory. Arrays are replaced as a whole in environment files; changing one replica, source or tenant target requires rewriting the whole array. See the [Data Guide](data.en.md#file-configuration-and-credentials) for complete rules and examples. Set `app.locales_dir` explicitly in TOML; it defaults to `locales`. Ordinary applications resolve it from the process current working directory, not the configuration directory, and do not read `APP_LOCALES_DIR`. The directory contains `zh-CN.toml` and `en-US.toml`; missing resources or loading failures strictly reject startup in production, while development can fall back to embedded resources. Asset structure checks and CI tool tests for deployment templates and private configuration directories have passed. Real containers, images and the complete deployment flow remain unaccepted; partial checks do not establish a complete gate pass.

## Starting the Backend

Keep real local credentials only in an ignored directory. From the backend root, copy the common and dev examples into a new `.local-tests/dev-config`; stop if it exists, preserving the user's real configuration:

```powershell
if (Test-Path -LiteralPath .local-tests/dev-config) { throw "Configuration directory already exists; preserve it and choose a new directory" }
New-Item -ItemType Directory -Path .local-tests/dev-config -ErrorAction Stop | Out-Null
Copy-Item -LiteralPath config/app.toml,config/app.dev.toml -Destination .local-tests/dev-config -ErrorAction Stop
```
Open `.local-tests/dev-config/app.dev.toml` in an editor and fill in real database, JWT, Redis, storage and `[bootstrap] admin_password` settings. Do not edit the version-controlled originals or put passwords in command arguments. First set `$env:APP_ENV = "dev"` and ensure an empty MySQL database exists. If selecting a different configuration directory, update subsequent paths bound to `.local-tests/dev-config`. From the backend root, run `cargo migrate -- --config-dir .local-tests/dev-config control up`, `cargo migrate -- --config-dir .local-tests/dev-config control verify`, `cargo migrate -- --config-dir .local-tests/dev-config tenant-data up --target shared-control`, `cargo migrate -- --config-dir .local-tests/dev-config tenant-data verify --target shared-control`, and `cargo serve -- --config-dir .local-tests/dev-config` in that order. `control verify` only verifies and cannot initialize a new empty database. The control database and the default `shared-control` tenant data plane have separate ledgers; both require initialization and verification. API/Worker startup only verifies structure and does not execute DDL automatically. See the [Data Guide](data.en.md#initializing-a-new-environment) for the full procedure, SQL import, and multiple targets.

The non-production default is `jobs.mode="embedded"`, so `cargo serve -- --config-dir .local-tests/dev-config` already consumes background tasks. Separate API and Worker instances require separate configuration files. Start this example from the backend root with two entirely new directories; stop if either exists, preserving the user's real configuration. Copy the common and dev files from the configured `.local-tests/dev-config`, not from the version-controlled unconfigured examples:

```powershell
if ((Test-Path -LiteralPath .local-tests/api-config) -or (Test-Path -LiteralPath .local-tests/worker-config)) { throw "Configuration directory already exists; preserve it and choose two new directories" }
New-Item -ItemType Directory -Path .local-tests/api-config,.local-tests/worker-config -ErrorAction Stop | Out-Null
Copy-Item -LiteralPath .local-tests/dev-config/app.toml,.local-tests/dev-config/app.dev.toml -Destination .local-tests/api-config -ErrorAction Stop
Copy-Item -LiteralPath .local-tests/dev-config/app.toml,.local-tests/dev-config/app.dev.toml -Destination .local-tests/worker-config -ErrorAction Stop
```

Open `.local-tests/api-config/app.dev.toml` and `.local-tests/worker-config/app.dev.toml` in an editor. At the top level of each file, set API `snowflake_worker_id=1` and Worker `snowflake_worker_id=2`, and set `mode="external"` under `[jobs]` in both files. Keep `scope_id`, database, Redis and JWT configuration consistent within the deployment. Edit passwords only in configuration files, never in command arguments. After saving, open two PowerShell terminals, set the following `APP_ENV` in each, then run the API command in one and the Worker command in the other. The `--` passes arguments to the corresponding application:

```powershell
$env:APP_ENV = "dev"
cargo serve -- --config-dir .local-tests/api-config
cargo worker -- --config-dir .local-tests/worker-config
```

Run the frontend separately with `corepack pnpm dev`. Non-production rebuilds use the direct `cargo reset` entry point; stop all producers first. See the [Operations Guide](operations.en.md#non-production-rebuilds) for the complete safety procedure. If the Worker is not consuming tasks, confirm file setting `jobs.mode="external"` and check its health port, lease and database connection. For Redis or object-storage failures, check `scope_id`, connection mode, TLS, ownership marker and service ports in the Operations Guide.

## Database Migrations

The control database uses the default target; tenant data operations can select all registered targets or a single target. Common commands are `cargo migrate -- --config-dir .local-tests/dev-config control status`, `cargo migrate -- --config-dir .local-tests/dev-config control verify`, `cargo migrate -- --config-dir .local-tests/dev-config control up`, `cargo migrate -- --config-dir .local-tests/dev-config tenant-data status --all`, `cargo migrate -- --config-dir .local-tests/dev-config tenant-data up --target <target-key>`, and `cargo migrate -- --config-dir .local-tests/dev-config tenant-data verify --target <target-key>`. Tenant targets use configuration keys rather than database names. `--all` only processes registered targets; multiple targets first undergo a physical identity preflight, and any duplicate alias is rejected before DDL. After editing migration source, use `cargo xtask data migrate check` to check history and registration read-only, and use `cargo xtask data migrate check --require-frozen` before committing. Explicitly run `cargo xtask data migrate baseline --write` to reorganize a development-version baseline; stable versions are append-only and use `cargo xtask data migrate freeze`. Production configuration remains `database.migration_mode="verify"`. Only explicit migration commands execute DDL; migration history maintenance commands do not connect to the database. Before initialization, explicitly set `admin_password` under `[bootstrap]`. The password must contain uppercase and lowercase letters, digits and symbols, with a length of 8–72 visible ASCII characters. JWT uses `auth.jwt_secret`, and the monitoring token uses `monitor.metrics_bearer_token`. The root TOML field `snowflake_worker_id` must differ for each instance in the same deployment. The ordinary initial user `user`, newly created ordinary users and bulk-imported ordinary users use `123456`; every new account must change its password on first login. Repeated initialization does not reset existing normal accounts. If startup reports inconsistent migrations, inspect status and verify results before applying up.

## Creating a Business Crate

By default, the skeleton and lockfile are previewed in an isolated copy; only `--write` installs them together. Offline resolution may only add the new local business packages for this invocation; it cannot upgrade, change the source of, or remove existing locked dependencies. The original project needs a valid Cargo.lock and the installed locked dependencies; if either is missing, the command reports an explicit error without installing a partial crate. The creation transaction updates the business crate's `kind = "business"` metadata and SDK feature, workspace membership, the composition root's optional dependencies and API/Worker/migration/data-maintenance features, and the `business_modules()` registration. It does not generate CRUD or operate on a database. Both the command and Builder accept a module name such as `order` or a package name such as `order-business`; the explicit name determines the new package, rather than the configured default package. Module names must start with a lowercase letter. Existing crates, duplicate registrations, and concurrent changes after plan generation are not overwritten. On an intermediate failure, restoration of the original files is attempted; if rollback is incomplete, the recovery directory is retained and identified. Windows CRLF input is validated against its original bytes and output as LF. The business crate's `src/resources/`, `src/extensions/`, and `migrations/` hold handwritten code and this module's migrations. Regenerable code goes into `src/generated/{entities,dto,repositories,services,handlers,openapi,models,resource_catalog}`, with ownership recorded in `.ryframe/generated.toml`. The scaffold already generates module assembly in `src/lib.rs`. Hyphens in module names become underscores in API paths, operation IDs, and page paths; permission segments and menu route keys consistently use hyphens, for example `sales-orders.order-item`. Business menu title keys are converted from resource names to lower camel case, such as `order_item` to `orderItem`; composition stops on conflicts with existing translation keys. Register resources in `resources/mod.rs` through `descriptors()`, for example `vec![<Order as ryframe_sdk::ResourceModel>::descriptor()]`.

The model-level `#[resource(primary_key = ["tenant_id", "id"])]` explicitly defines index order independently of field order. The list must contain exactly all fields marked as primary keys; when omitted, field order is used. Reverse import reads the order from the PRIMARY index, maps the business primary key to Rust `id`, and preserves physical column names with attributes such as `column="order_id"`; generation is rejected if this conflicts with an existing `id` column. Entities declare fields in primary key order, while DDL retains the original physical column order. Tenant primary keys must start with `tenant_id`; other composite primary keys are explicitly blocked without automatically modifying the source database. The audit timestamp column group may be omitted, in which case neither physical nor soft deletion adds timestamp writes. Declared timestamp and actor fields remain strictly validated and managed by the Service; request-level operation auditing continues to follow the existing transaction policy. Models use `#[derive(ryframe_sdk::ResourceModel)]`. After defining a model in `resources/mod.rs`, add its descriptor to `descriptors()` in the same file. `database="tenant"` is for tenant business data: tables start with `biz_` and include `tenant_id` in the composite primary key. `database="control"` is for global business data without `tenant_id`; its Service and persistence layer permit system-tenant access only, and page assets carry the same restriction. Enabling multi-tenancy does not share global business data; cross-tenant shared reads require an explicit use-case extension. IDs are application-generated Snowflake values by default. Database auto-increment primary keys use `#[resource(primary_key, auto_increment)] pub id: i64` (`u64` for unsigned columns), without declaring a default value or form writes. The generator adds a non-unique index starting with id for tenant composite primary keys, omits the ID on insert, and obtains the actual auto-increment value in the same transaction.

Declare the data-scope field with `#[resource(..., owner_field = "owner_id")]`. It must be an `i64` or `Option<i64>` field in the same struct that stores a user ID. Both tenant business data and control-database global business data can declare it; the latter remains system-tenant-only. The generator writes this value to `resources.json` and OpenAPI `access.owner_field`. Creation always writes the current user (`Some(user_id)` for nullable fields); standard updates do not accept changes to it. Lists, details, locked updates, and deletions are filtered by the current role's data scope: all-data scope applies no filter, self scope matches the current user, and department, department-and-descendants, or custom department scopes expand into the accessible owner set. With no scope, results are empty or absent. Tenant business reads lock the current projection; control-database scoped reads use the primary database. `owner_field` does not replace `tenant_id`, RBAC, or server-side authorization, and does not provide arbitrary expression filters or per-row sharing ACLs. Ownership transfers or additional sharing require explicit extensions. When omitted, no creator-based filter is applied. A missing field, incorrect type, empty or whitespace-containing name, or repeated attribute is rejected during macro expansion or generation preflight.

Model-driven creation generates CRUD, migrations, and managed assets from `ResourceModel`. Existing databases use `schema-import` for read-only reverse generation of models, CRUD, and migrations. If tables and business rows already exist in the runtime target, explicit adoption is still required after the model and migration history match; adoption only registers structure and does not execute table-creation DDL or rewrite business rows. `generator.source` or `--connection` only determines the structure source, accepting `primary`, `sources.<name>`, or `tenant_data.targets.<target-key>`. `storage` or `--database` independently determines the runtime scope `control|tenant`; the two are not mapped automatically. `source="local"` reads primary for control scope and `tenant_data.default_target` for tenant scope; the latter must be a MySQL target. The import example uses an explicit primary source. Define and register models before resource generation.

See [README: Develop business modules](../README.en.md#develop-business-modules) for business-crate and resource commands; omit `--write` to preview.

Commands can run from the workspace root or a subdirectory such as a business crate's `src`; the generator defaults to backend `workspace/config`. Relative paths in `--config-dir <directory>` and Builder `.configuration_directory(path)` always resolve from the backend Workspace root. Priority is explicit CLI/Builder, local `.local-tests/tools.toml`, common `config/tools.toml`, then `workspace/config`; `[generator] config_dir` is optional, and tool files are not overridden through environment variables. Preview compiles the model in an isolated cache, generates CRUD and migrations, and reports differences. `sync_frontend=true` or `--sync-frontend` also exports the current candidate OpenAPI, synchronizes typed callers, generates list forms and routes, and runs frontend type and lint checks. Install frontend dependencies first. Business page templates are maintained in the frontend repository's `scripts/resource-render/`; the backend passes validated IR through a fixed Corepack entry point, then validates the returned assets' version, complete set, ownership, and paths before managed installation. Candidate copies reuse the installed frontend environment whose package.json matches exactly. Incomplete dependencies produce an error without implicit installation or lockfile changes. `--no-sync-frontend` temporarily disables synchronization and does not invoke the frontend renderer. Once all steps succeed, `--write` installs managed files in both repositories together; concurrent changes are not overwritten, and an incomplete failure rollback reports the backup path. The default page uses the generated page.vue; the model's `frontend_page="@/views/…/index.vue"` can select a handwritten page. `resource` does not write handwritten directories or overwrite historical migrations. The descriptor reader uses Workspace-locked versions, sources, checksums, and patches offline without changing the project lockfile. Generator build caches use `generator.target_dir` in the tool files (the local file takes precedence), resolved from the backend root or supplied as an explicit absolute path without links, defaulting to `target`; generator cache selection does not read `CARGO_TARGET_DIR`. Bootstrap, catalog, and the candidate pipeline share this cache root. Nested business fixtures record the coordinator-selected directory in their local tool file and explicitly reuse it for Cargo builds to avoid deep paths. Fixtures retain the scaffold’s reviewed incremental lock-file registration instead of resolving all dependencies again; compilation remains `--locked`. Supported configuration includes `package`, `models`, `tables`, `source`, `storage`, `strip_table_prefix`, and `sync_frontend`. `resource --models Order,OrderItem` overrides the model list, and `import --tables biz_order,biz_order_item` selects a complete table batch. `run` selects import or model generation according to whether tables is empty; import requires `--features schema-import`. `--plan` only lists the same execution plan without compiling, connecting to a database, or writing to disk. The scaffold has already updated `crates/ryframe/Cargo.toml` with the `order-business` dependency and updated `crates/ryframe/src/business.rs` so that `business_modules()` includes `order_business::module()`. API, Worker, and migration programs read the same list. Module names, resource names, table names, routes, OpenAPI operations/schemas, and dependency cycles are validated before startup. Generated `access.toml` and `access.rs` are maintained from the model, and the scaffold connects them through `.access_catalog(generated::access::CATALOG)`. Existing handwritten assembly must add this call before regeneration; registering resources without the access catalog is insufficient. The module's parent directory is generated automatically by default; `menu_parent` can reuse an existing framework directory. Directory, page, or permission conflicts stop the entire batch. After reviewing generated output, run `cargo migrate -- --config-dir .local-tests/dev-config control up` and `cargo migrate -- --config-dir .local-tests/dev-config control verify`; service startup does not automatically add menus or permissions. New tenant administrators receive tenant business CRUD by default; ordinary users and extension operations require manual grants. System-tenant-only business data is not copied to ordinary tenants. Existing tenants do not automatically receive additional role grants.

Reverse import reads only selected tables. It preflights names, models, files, and the explicit vec list in `descriptors()` for the whole batch, compiles models in a candidate workspace, and proceeds to generate CRUD and migrations. Any conflict stops the whole batch without overwriting handwritten models. `--strip-table-prefix biz_` only changes resource, module, and type names while preserving physical table names; tenant catalogs require this table prefix. Original column types, defaults, indexes, foreign keys, and schema are retained in `.ryframe/imports/`. `source=primary`, `sources.legacy`, or `tenant_data.targets.<key>` selects the read-only source; `storage=control|tenant` selects the runtime scope independently. With frontend synchronization enabled, this batch's contract and pages are also validated. A mismatch between generated structure and source, such as an unsupported foreign key, stops the entire batch without installing a partial model set. Generation does not create or adopt source tables; their purpose still requires review and explicit migration or adoption. Unknown types, views, and unreadable columns are rejected; `tinyint(1)` is not guessed to be Boolean. Boolean, text/textarea, integer, date, datetime, Decimal, and JSON fields produce type-appropriate standard form controls; JSON query filtering requires a strongly typed extension. Run the Rust [example](../crates/ryframe-generator/examples/generate.rs) with `cargo run --locked -p ryframe-generator --example generate` or an IDE; import requires `--features schema-import`. The Builder's `plan()` is read-only, `execute()` performs execution, and only `.write(true)` updates files. For an existing database, first use `cargo generate --features schema-import -- import --package order-business --connection primary --database tenant --tables biz_order,biz_order_item --config-dir .local-tests/dev-config --plan` to list only the task graph without reading configuration, databases, or migration metadata. Removing `--plan` reads the source read-only and generates and validates models, CRUD, migrations, contracts, and optional frontend assets in an isolated candidate workspace, without updating either repository. Review `.ryframe/imports/`, differences, and compilation results before adding `--write`. If imported tables already exist in the runtime target, after `--write` you still cannot use ordinary `up` to guess adoption.

The model-level `#[resource(collation="utf8mb4_0900_ai_ci")]` declares table collation; string fields can override it with `#[resource(collation="utf8mb4_bin")]`. Undeclared tables use `utf8mb4_general_ci`, and undeclared columns inherit the table collation. Import reads actual table and column collations and preserves them in Rust models; DDL, structure fingerprints, copy catalogs, and adoption checks share these declarations. Only safe utf8mb4 collation names are accepted, and actual availability is verified against the target MySQL instance. Other character sets require migration review or an extension. Changing the collation of an existing model stops automatic migration for the entire batch: first review comparison semantics, unique indexes, and existing data; conversion is not automatic.

### Adopting Existing Tables

Adoption requires an exact match between the model, migrations, and physical database structure. First import or handwrite the model in the business crate and register its descriptor. Preview with `cargo generate -- resource --package order-business`, review the result, then add `--write`. Imported field types, collations, indexes, foreign keys, and migration history must be retained. Stop API, Worker, and scheduled writes on the target, and complete framework initialization in the control database first. Tenant tables must select one target key; `adopt` does not accept `--all`. To generate an adoption plan for the control database, run `cargo migrate -- --config-dir .local-tests/dev-config control adopt --module order --output .local-tests/order-adopt.json --write`. For a tenant database, replace `control` with `tenant-data`, add `--target business-shared`, and select a different new output file. First use `--inspect` on that plan to check physical instance, database, tables, migration prefix, and fingerprints read-only; then use the same plan with `--apply ... --write` and the corresponding `verify`. A `--module` preview with `--plan` does not read configuration or databases. `--output` requires `--write`, and `--inspect` rejects writes. Partial registration, mismatched before-images, different sources, or structure drift all fail closed. For an unknown outcome, inspect the original plan first; do not replay with a different plan. If the target is empty and existing tables are only used as structure templates, adoption is unnecessary; create tables with normal `up`.

### Evolving Model Structure

After editing the Rust model, continue to preview with the same `cargo generate -- resource --package order-business`, review the result, and add `--write`. The generator retains the original bytes and digests of all historical migrations and only appends new migrations with stable numbering. `src/generated/migrations/history.json` and ownership retain the before/after structure chain together; this step does not connect to or modify databases. Fields can preserve physical types with `#[resource(sql_type="VARCHAR(32)")]`. Import writes this attribute automatically, and DDL, copy catalogs, and adoption checks share it. Currently supported types, matched to Rust types, are CHAR/VARCHAR, the TEXT family, signed integers and `u8/u16/u32/u64` unsigned integers, Boolean, DATE, DATETIME (0–6 fractional digits), and JSON. Character lengths, text byte capacities, and integer ranges are derived; contradictory validation, unknown declarations, or SQL clauses produce errors before writing. Integer CRUD preserves Rust width and signedness; defaults and enum values must fit that type. Physical SQL capacity must fully accommodate the model, and incremental conversions are checked against physical ranges. Ordinary `u64` fields retain their full unsigned capacity and are transmitted as strings; defaults above i64 use decimal strings. Primary keys support `i64/u64`, with consistent types across auto-increment and Snowflake strategies, URLs, and persistence. Decimal requires an explicit `DECIMAL(p,s)` declaration (1≤p≤28, 0≤s≤p) and uses the SDK's `rust_decimal::Decimal`; request bodies, queries, responses, and text forms all transmit strings. Values exceeding column capacity or scale are rejected; neither API nor SDK use cases round automatically. FlatCrud generates model-appropriate text or textarea, integer, switch, date, datetime, enum single-select, and exact Decimal text controls. JSON uses an editable textarea and is strictly parsed into a structured value before submission; empty nullable or optional text submits null or omission, respectively. JSON does not support standard query-parameter filtering; use a strongly typed extension for structured queries.

Declare composite indexes with the struct attribute `#[resource(index(name="idx_code",fields=["code","id"]))]`, adding `unique` for unique indexes. Import preserves index names, field order, and uniqueness, while rejecting prefix, descending, functional, invisible, and non-BTREE indexes. Only the necessary id-leading index for an auto-increment composite primary key is added; no redundant indexes are added for fields already covered by the primary key. A field's `#[resource(sql_comment="Database comment")]` is independent of its UI label. Import, DDL, model digests, and appended migrations preserve it, while structure fingerprints still check structure only. Quotes, backslashes, and newlines are retained as-is; field comments cannot contain NUL or exceed 1024 characters. Literal defaults use the field attribute `default="value"`; database clocks use `sql_default="CURRENT_TIMESTAMP(6)"` and `sql_on_update="CURRENT_TIMESTAMP(6)"`. Clocks only support 0–6 digits of precision consistent with the DATETIME column, and do not accept arbitrary SQL. `default` and `sql_default` cannot be combined. Import preserves both types of defaults and update-time expressions; explicit application writes and nullable replacement semantics still apply. Date and Decimal literal defaults must fit the current CRUD-supported range; other expressions require explicit migration extensions.

Read-only foreign key metadata preserves composite column order, same-database reference identities, `ON UPDATE`, `ON DELETE`, and the database-reported `MATCH` rule, and is included in `.ryframe/imports/` source records. Unknown actions or match rules are rejected immediately. Reading reference actions does not mean the generator can write that constraint. Candidate structure verification currently still rejects unexpressed foreign keys; no relational CRUD or foreign-key DSL is generated. If complete import fails, neither candidate source records nor models are installed into the formal working tree.

- New nullable columns, non-null columns with explicit defaults, wider integer or string types, relaxed non-null constraints, and new indexes can generate forward DDL. Unique indexes still require checking existing duplicate values first.
- Dropping or renaming columns, narrowing types, tightening non-null constraints, changing primary keys/table names/storage scope, reordering existing columns, or deleting/modifying indexes only produces review reasons and stops the whole batch, without overwriting initial migrations or publishing partial registrations. For a new non-null column without a default, use a nullable column and backfill in stages first.
- After reviewing migrations, stop producers, then explicitly run `up` and `verify` for control or the selected tenant-data target. If the database is edited directly, verify reports drift; the generator does not overwrite models from the database or guess what has executed.
- Nullable writable fields use full replacement: omission or null on creation means empty, and omission or null on update clears the field. Omitting a non-null optional update retains the original value. Use an explicit extension for three-state patches. Business `i64/u64` values are transmitted as strings by default; bodies, queries, return values, and text forms retain exact decimal values and do not use number controls. Empty text submits null for nullable fields or omission for optional fields; required fields remain validated by forms and the server. Finite enums retain string values without conversion to floating-point numbers. Contract ranges for string-transmitted 64-bit integers also use canonical decimal strings; the frontend validates with BigInt and must not parse boundaries as Number first.

The generator does not execute database migrations. After writing and reviewing managed files, run `status` for the model's storage scope, then `cargo migrate -- --config-dir .local-tests/dev-config control up` or `cargo migrate -- --config-dir .local-tests/dev-config tenant-data up --target <target-key>`, and finally the corresponding `verify`. When multiple targets share a version, `--all` can be used explicitly, but does not replace `control up`. If final structure verification fails, retain the state and check the ledger and actual tables first; do not replay an unknown outcome. Post and Notice remain standard resources of the RyFrame framework itself. Framework maintainers continue to check them with the internal `cargo xtask generate resource`; user business code does not write `catalog/resources/*.toml`.

Tenant business resources also generate `generated/tenant_catalog.rs` and `generated/tenant_catalog.json`, containing full columns, types, copy cursors, and normalized schema. Modules declare generated descriptions through `tenant_data_tables()`. Before database connections are created, the composition root assembles them, verifies dependencies, and freezes the catalog; repeated registration in the same process must use identical descriptions. Duplicate tables, missing descriptions, or invalid schema prevent startup rather than ignoring business tables. Copy and recovery verification use the complete catalog and retain the business migration ledger. Generated migrations register model fingerprints and each table's before/after physical structure; handwritten `SeaOrmBusinessMigration` implementations must also provide `BusinessMigrationSchema`. An individual `verify_ledger` only verifies the historical ledger. The group-level `verify_business_migrations(database, scope, migrations)` receives all registered migrations for that scope, rejects unknown ledgers and ownership conflicts, then validates actual structure against each table's latest state, preventing old structure checks from misclassifying valid appended migrations. After editing a model, first update managed assets through the formal generation entry point, then explicitly execute business migrations; do not hand-edit catalogs or ownership digests. For existing tables, [preview, save, inspect, and apply an adoption plan](#adopting-existing-tables). Tenant adoption must select one target; do not guess adoption through up.

Integration from model to page can follow this sequence:

1. Create a business crate, register `ResourceModel`, preview generation, then write with `--write`; a subsequent preview should show no differences.
2. Add tests for business models and use cases and run `cargo test --locked -p order-business`. First pass migration status checks for the control database and explicit tenant target, then explicitly apply this module's migrations; see the [Data Guide](data.en.md) for commands.
3. Run `cargo serve -- --config-dir .local-tests/dev-config` in default development mode and confirm module routes and embedded tasks are assembled correctly. To verify separate processes, follow the [two-directory startup steps](#starting-the-backend) with different instance IDs in the two configurations. After API changes, run `cargo xtask generate api --write` from the backend to synchronize the candidate contract. OpenAPI and database structure snapshots are produced through formal generation or migration maintenance entry points, not by directly running internal binaries. If frontend requests differ from the backend, rerun contract synchronization and consumer checks.
4. Register the business permission codes declared by the generated contract in permission management, then grant them to business roles in role management. Generating business APIs does not automatically grant permissions to existing tenants. For a page entry, bind the corresponding permission and frontend page identifier in menu management.
