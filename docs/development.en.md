# Development Guide

Product plan capability options come from the backend's compiled catalog and the frontend feature manifest. Basic administration remains available and follows RBAC; notices and tenant-initiated message publishing can be enabled or disabled by plan. The initial capabilities use the `standard` variant and a strictly empty object configuration. Disabling notices closes their administration and read endpoints; disabling tenant-initiated messages rejects new publications. Existing data and accepted messages are retained, and system notifications continue to run. Tenant, product plan, data target, and platform infrastructure administration belong to the system tenant and cannot be opened to ordinary tenants through permission wildcards, menu grants, or configuration packages. The system tenant has the deployed administration capabilities, subject to actual infrastructure availability checks.

## Environment and Configuration

Local development verification uses Windows; native builds require MSVC C/C++ tools for the target architecture and a Windows SDK. See the [official rustup prerequisites](https://rust-lang.github.io/rustup/installation/windows-msvc.html) for installation. Prepare other native build tools, such as CMake and NASM, according to the requirements of the selected target and locked dependencies. MySQL 8.0.16 or later, a Redis 7.x protocol environment, and RustFS/MinIO/S3-compatible storage can run on any platform that meets the version, protocol, and connectivity requirements; remote services are also supported. WSL is not required. After installing rustup, run `rustup show` in the project directory to install and select the pinned Rust 1.98.1, rustfmt, and Clippy. The project uses Rust 2024 edition with a minimum Rust version of 1.98; local development, CI, and production build images use the same pinned toolchain. `APP_ENV` is the only project configuration environment entry, for example `$env:APP_ENV = "dev"`, accepting only `dev`, `test`, or `prod`. `config/app.toml` is optional, and the selected `config/app.<environment>.toml` must exist. Without the common file, the environment file must supply every required setting; an existing malformed or unreadable common file still fails. Addresses, passwords, JWT, Redis, storage and monitoring credentials use plaintext configuration fields directly. Keep real configuration in private directories outside the working tree and do not commit credentials. Applications select a directory through `--config-dir <directory>`, defaulting to `config`, with relative paths resolved from the current working directory. Arrays are replaced as a whole in environment files; changing one replica, source or tenant target requires rewriting the whole array. See the [Data Guide](data.en.md#file-configuration-and-credentials) for complete rules and examples. Set `app.locales_dir` explicitly in TOML; it defaults to `locales`. Ordinary applications resolve it from the process current working directory, not the configuration directory, and do not read `APP_LOCALES_DIR`. The directory contains `zh-CN.toml` and `en-US.toml`; missing resources or loading failures strictly reject startup in production, while development can fall back to embedded resources. Asset structure checks and CI tool tests for deployment templates and private configuration directories have passed. Real containers, images and the complete deployment flow remain unaccepted; partial checks do not establish a complete gate pass. Managed read-only storage observations and initialization commands share the operating-system runtime environment whitelist; explicitly bound private values override system fields with the same name. Additional `APP_*` configuration or credentials are not inherited. Windows platform tools require standard runtime fields such as `SYSTEMROOT` and `USERPROFILE`; the application's `APP_ENV`-only rule does not mean clearing the operating-system environment. When a fixed observation command fails, check the tool, OS runtime environment and process-observation permissions, and retain the failed directory. Failure does not prove that the service stopped and must not trigger automatic replay or cleanup.

## Starting the Backend

Choose a private configuration directory outside Git working trees. Run the following commands from the backend root to copy the common and development examples into a new sibling directory, `../ryframe-dev-config`. The backend uses this private configuration directory at startup. Tools create their runtime directories inside the repository as needed. Select an existing configuration with `--config-dir` if it already fits your setup. The copy commands stop when the destination exists to preserve existing files.

- `if (Test-Path -LiteralPath ../ryframe-dev-config) { throw "Configuration directory already exists; preserve it and choose a new directory" }`
- `New-Item -ItemType Directory -Path ../ryframe-dev-config -ErrorAction Stop | Out-Null`
- `Copy-Item -LiteralPath config/app.toml,config/app.dev.toml -Destination ../ryframe-dev-config -ErrorAction Stop`

Open `../ryframe-dev-config/app.dev.toml` in an editor and fill in real database, JWT, Redis, storage and `[bootstrap] admin_password` settings. Do not edit the version-controlled originals or put passwords in command arguments. First set `$env:APP_ENV = "dev"` and ensure an empty MySQL database exists. If selecting a different configuration directory, update subsequent paths bound to `../ryframe-dev-config`. From the backend root, follow the commands using the same directory in [README: First run after downloading](../README.en.md#first-run-after-downloading) to initialize and verify both ledgers before starting the backend. `control verify` only verifies and cannot initialize a new empty database. The control database and the default `shared-control` tenant data plane have separate ledgers; both require initialization and verification. API/Worker startup only verifies structure and does not execute DDL automatically. See the [Data Guide](data.en.md#initializing-a-new-environment) for the full procedure, SQL import, and multiple targets.

The non-production default is `jobs.mode="embedded"`, so `cargo serve -- --config-dir ../ryframe-dev-config` already consumes background tasks. Separate API and Worker instances require separate configuration files. Start this example from the backend root with two entirely new directories; stop if either exists, preserving the user's real configuration. Copy the common and dev files from the configured `../ryframe-dev-config`, not from the version-controlled unconfigured examples:

- `if ((Test-Path -LiteralPath ../ryframe-api-config) -or (Test-Path -LiteralPath ../ryframe-worker-config)) { throw "Configuration directory already exists; preserve it and choose two new directories" }`
- `New-Item -ItemType Directory -Path ../ryframe-api-config,../ryframe-worker-config -ErrorAction Stop | Out-Null`
- `Copy-Item -LiteralPath ../ryframe-dev-config/app.toml,../ryframe-dev-config/app.dev.toml -Destination ../ryframe-api-config -ErrorAction Stop`
- `Copy-Item -LiteralPath ../ryframe-dev-config/app.toml,../ryframe-dev-config/app.dev.toml -Destination ../ryframe-worker-config -ErrorAction Stop`

Open `../ryframe-api-config/app.dev.toml` and `../ryframe-worker-config/app.dev.toml` in an editor. At the top level of each file, set API `snowflake_worker_id=1` and Worker `snowflake_worker_id=2`, and set `mode="external"` under `[jobs]` in both files. Keep `scope_id`, database, Redis and JWT configuration consistent within the deployment. Edit passwords only in configuration files, never in command arguments. After saving, open two PowerShell terminals, set the following `APP_ENV` in each, then run the API command in one and the Worker command in the other. The `--` passes arguments to the corresponding application:

- `$env:APP_ENV = "dev"`
- `cargo serve -- --config-dir ../ryframe-api-config`
- `cargo worker -- --config-dir ../ryframe-worker-config`

Run the frontend separately with `corepack pnpm dev`. Non-production rebuilds use the direct `cargo reset` entry point; stop all producers first. See the [Operations Guide](operations.en.md#non-production-rebuilds) for the complete safety procedure. If the Worker is not consuming tasks, confirm file setting `jobs.mode="external"` and check its health port, lease and database connection. For Redis or object-storage failures, check `scope_id`, connection mode, TLS, ownership marker and service ports in the Operations Guide.

## Database Migrations

The control database uses the default target; tenant data operations can select all registered targets or a single target. Common commands are `cargo migrate -- --config-dir ../ryframe-dev-config control status`, `cargo migrate -- --config-dir ../ryframe-dev-config control verify`, `cargo migrate -- --config-dir ../ryframe-dev-config control up`, `cargo migrate -- --config-dir ../ryframe-dev-config tenant-data status --all`, `cargo migrate -- --config-dir ../ryframe-dev-config tenant-data up --target <target-key>`, and `cargo migrate -- --config-dir ../ryframe-dev-config tenant-data verify --target <target-key>`. Tenant targets use configuration keys rather than database names. `--all` only processes registered targets; multiple targets first undergo a physical identity preflight, and compatible shared aliases may be merged, while dedicated aliases, multiple existing routes, and fences outside the group fail before DDL. See [initial ownership and adoption](data.en.md#initial-ownership-registration-and-explicit-adoption-of-existing-databases) for the representative-key rules. After editing migration source, use `cargo xtask data migrate check` to check history and registration read-only, and use `cargo xtask data migrate check --require-frozen` before committing. Explicitly run `cargo xtask data migrate baseline --write` to reorganize a development-version baseline; stable versions are append-only and use `cargo xtask data migrate freeze`. Production configuration remains `database.migration_mode="verify"`. Only explicit migration commands execute DDL; migration history maintenance commands do not connect to the database. Before initialization, explicitly set `admin_password` under `[bootstrap]`. The password must contain uppercase and lowercase letters, digits and symbols, with a length of 8–72 visible ASCII characters. JWT uses `auth.jwt_secret`, and the monitoring token uses `monitor.metrics_bearer_token`. The root TOML field `snowflake_worker_id` must differ for each instance in the same deployment. The ordinary initial user `user`, newly created ordinary users and bulk-imported ordinary users use `123456`; every new account must change its password on first login. Repeated initialization does not reset existing normal accounts. If startup reports inconsistent migrations, inspect status and verify results before applying up.

## Creating a Business Crate

By default, the skeleton and lockfile are previewed in an isolated copy; only `--write` installs them together. Offline resolution may only add the new local business packages for this invocation; it cannot upgrade, change the source of, or remove existing locked dependencies. The original project needs a valid Cargo.lock and the installed locked dependencies; if either is missing, the command reports an explicit error without installing a partial crate. The creation transaction updates the business crate's `kind = "business"` metadata and SDK feature, workspace membership, the composition root's optional dependencies and API/Worker/migration/data-maintenance features, and the `business_modules()` registration. It does not generate CRUD or operate on a database. Both the command and Builder accept a module name such as `order` or a package name such as `order-business`; the explicit name determines the new package, rather than the configured default package. Module names must start with a lowercase letter. Existing crates, duplicate registrations, and concurrent changes after plan generation are not overwritten. On an intermediate failure, restoration of the original files is attempted; if rollback is incomplete, the recovery directory is retained and identified. Windows CRLF input is validated against its original bytes and output as LF. The business crate's `src/resources/`, `src/extensions/`, and `migrations/` hold handwritten code and this module's migrations. Regenerable code goes into `src/generated/{entities,dto,repositories,services,handlers,openapi,models,resource_catalog}`, with ownership recorded in `.ryframe/generated.toml`. The scaffold already generates module assembly in `src/lib.rs`. Hyphens in module names become underscores in API paths, operation IDs, and page paths; permission segments and menu route keys consistently use hyphens, for example `sales-orders.order-item`. Business menu title keys are converted from resource names to lower camel case, such as `order_item` to `orderItem`; composition stops on conflicts with existing translation keys. Register resources in `resources/mod.rs` through `descriptors()`, for example `vec![<Order as ryframe_sdk::ResourceModel>::descriptor()]`.

The model-level `#[resource(primary_key = ["tenant_id", "id"])]` explicitly defines index order independently of field order. The list must contain exactly all fields marked as primary keys; when omitted, field order is used. Reverse import reads the order from the PRIMARY index, maps the business primary key to Rust `id`, and preserves physical column names with attributes such as `column="order_id"`; generation is rejected if this conflicts with an existing `id` column. Entities declare fields in primary key order, while DDL retains the original physical column order. Tenant primary keys must start with `tenant_id`; other composite primary keys are explicitly blocked without automatically modifying the source database. The audit timestamp column group may be omitted, in which case neither physical nor soft deletion adds timestamp writes. Declared timestamp and actor fields remain strictly validated and managed by the Service; request-level operation auditing continues to follow the existing transaction policy. Models use `#[derive(ryframe_sdk::ResourceModel)]`. After defining a model in `resources/mod.rs`, add its descriptor to `descriptors()` in the same file. `database="tenant"` is for tenant business data: tables start with `biz_` and include `tenant_id` in the composite primary key. `database="control"` is for global business data without `tenant_id`; its Service and persistence layer permit system-tenant access only, and page assets carry the same restriction. Enabling multi-tenancy does not share global business data; cross-tenant shared reads require an explicit use-case extension. IDs are application-generated Snowflake values by default. Database auto-increment primary keys use `#[resource(primary_key, auto_increment)] pub id: i64` (`u64` for unsigned columns), without declaring a default value or form writes. The generator adds a non-unique index starting with id for tenant composite primary keys, omits the ID on insert, and obtains the actual auto-increment value in the same transaction.

Declare the data-scope field with `#[resource(..., owner_field = "owner_id")]`. It must be an `i64` or `Option<i64>` field in the same struct that stores a user ID. Both tenant business data and control-database global business data can declare it; the latter remains system-tenant-only. The generator writes this value to `resources.json` and OpenAPI `access.owner_field`. Creation always writes the current user (`Some(user_id)` for nullable fields); standard updates do not accept changes to it. Lists, details, locked updates, and deletions are filtered by the current role's data scope: all-data scope applies no filter, self scope matches the current user, and department, department-and-descendants, or custom department scopes expand into the accessible owner set. With no scope, results are empty or absent. Tenant business reads lock the current projection; control-database scoped reads use the primary database. `owner_field` does not replace `tenant_id`, RBAC, or server-side authorization, and does not provide arbitrary expression filters or per-row sharing ACLs. Ownership transfers or additional sharing require explicit extensions. When omitted, no creator-based filter is applied. A missing field, incorrect type, empty or whitespace-containing name, or repeated attribute is rejected during macro expansion or generation preflight.

Model-driven creation generates CRUD, migrations, and managed assets from `ResourceModel`. Existing databases use `schema-import` for read-only reverse generation of models, CRUD, and migrations. If tables and business rows already exist in the runtime target, explicit adoption is still required after the model and migration history match; adoption only registers structure and does not execute table-creation DDL or rewrite business rows. `generator.source` or `--connection` only determines the structure source, accepting `primary`, `sources.<name>`, or `tenant_data.targets.<target-key>`. `storage` or `--database` independently determines the runtime scope `control|tenant`; the two are not mapped automatically. `source="local"` reads primary for control scope and `tenant_data.default_target` for tenant scope; the latter must be a MySQL target. The import example uses an explicit primary source. Define and register models before resource generation.

See [README: Develop business modules](../README.en.md#develop-business-modules) for business-crate and resource commands; omit `--write` to preview.

Commands can run from the workspace root or a subdirectory such as a business crate's `src`; the generator defaults to backend `workspace/config`. Relative paths in `--config-dir <directory>` and Builder `.configuration_directory(path)` always resolve from the backend Workspace root. Priority is explicit CLI/Builder, local `.local-tests/tools.toml`, common `config/tools.toml`, then `workspace/config`; `[generator] config_dir` is optional, and tool files are not overridden through environment variables. Preview compiles the model in an isolated cache, generates CRUD and migrations, and reports differences. `sync_frontend=true` or `--sync-frontend` also exports the current candidate OpenAPI, synchronizes typed callers, generates list forms and routes, and runs frontend type and lint checks. Install frontend dependencies first. Business page templates are maintained in the frontend repository's `scripts/resource-render/`; the backend passes validated IR through a fixed Corepack entry point, then validates the returned assets' version, complete set, ownership, and paths before managed installation. Candidate copies reuse the installed frontend environment whose package.json matches exactly. Incomplete dependencies produce an error without implicit installation or lockfile changes. `--no-sync-frontend` temporarily disables synchronization and does not invoke the frontend renderer. Once all steps succeed, `--write` installs managed files in both repositories together; concurrent changes are not overwritten, and an incomplete failure rollback reports the backup path. The default page uses the generated page.vue; the model's `frontend_page="@/views/…/index.vue"` can select a handwritten page. `resource` does not write handwritten directories or overwrite historical migrations. The descriptor reader uses Workspace-locked versions, sources, checksums, and patches offline without changing the project lockfile. Generator build caches use `generator.target_dir` in the tool files (the local file takes precedence), resolved from the backend root or supplied as an explicit absolute path without links, defaulting to `target`; generator cache selection does not read `CARGO_TARGET_DIR`. Bootstrap, catalog, and the candidate pipeline share this cache root. Nested business fixtures record the coordinator-selected directory in their local tool file and explicitly reuse it for Cargo builds to avoid deep paths. Before creating the business module, the real two-table reverse-import acceptance records `target_dir` from the existing `resource-workspace-control.json` in the candidate’s local `generator.target_dir` and preserves it during frontend synchronization. A missing control file limits verification to the backend; an invalid existing file fails instead of being treated as a skip. This acceptance follows the application loader: common `app.toml` is optional, while selected `app.test.toml` is required. Absence is frozen at capture, private copies do not create empty placeholders, and later appearance or drift stops the import. Fixtures retain the scaffold’s reviewed incremental lock-file registration instead of resolving all dependencies again; compilation remains `--locked`. Supported configuration includes `package`, `models`, `tables`, `source`, `storage`, `strip_table_prefix`, and `sync_frontend`. `resource --models Order,OrderItem` overrides the model list, and `import --tables biz_order,biz_order_item` selects a complete table batch. `run` selects import or model generation according to whether tables is empty; import requires `--features schema-import`. After the tool starts, `--plan` only lists the same execution plan without compiling business descriptors, connecting to databases, creating locks, generation caches or reports, or writing generated targets. `cargo generate` and `cargo xtask` are existing `cargo run` aliases: on first use or after tool source changes, Cargo may first compile the tool and write to its build directory. To avoid those bootstrap writes, build explicitly first and then run the same tool executable reported by Cargo with `--plan`; no additional generator installation or entry point is needed. The scaffold has already updated `crates/ryframe/Cargo.toml` with the `order-business` dependency and updated `crates/ryframe/src/business.rs` so that `business_modules()` includes `order_business::module()`. API, Worker, and migration programs read the same list. Module names, resource names, table names, routes, OpenAPI operations/schemas, and dependency cycles are validated before startup. Generated `access.toml` and `access.rs` are maintained from the model, and the scaffold connects them through `.access_catalog(generated::access::CATALOG)`. Existing handwritten assembly must add this call before regeneration; registering resources without the access catalog is insufficient. The module's parent directory is generated automatically by default; `menu_parent` can reuse an existing framework directory. Directory, page, or permission conflicts stop the entire batch. After reviewing generated output, run `cargo migrate -- --config-dir ../ryframe-dev-config control up` and `cargo migrate -- --config-dir ../ryframe-dev-config control verify`; service startup does not automatically add menus or permissions. New tenant administrators receive tenant business CRUD by default; ordinary users and extension operations require manual grants. System-tenant-only business data is not copied to ordinary tenants. Existing tenants do not automatically receive additional role grants.
The three maintenance roles also use `generator.target_dir` from the execution backend: read shared `config/tools.toml`, then overlay `.local-tests/tools.toml`. An explicit value shares the generator cache; without one, the default remains `target/ci/backend`. The builder and all maintenance receipt readers use the same Rust resolver, without a host `CARGO_TARGET_DIR` override. After changing the cache configuration, retain old evidence and explicitly build new artifacts rather than treating old receipts as builds of the new configuration.

Reverse import reads only selected tables. It preflights names, models, files, and the explicit vec list in `descriptors()` for the whole batch, compiles models in a candidate workspace, and proceeds to generate CRUD and migrations. Any conflict stops the whole batch without overwriting handwritten models. `--strip-table-prefix biz_` only changes resource, module, and type names while preserving physical table names; tenant catalogs require this table prefix. Original column types, defaults, indexes, foreign keys, and schema are retained in `.ryframe/imports/`. `source=primary`, `sources.legacy`, or `tenant_data.targets.<key>` selects the read-only source; `storage=control|tenant` selects the runtime scope independently. With frontend synchronization enabled, this batch's contract and pages are also validated. A mismatch between generated structure and source stops the entire batch without installing a partial model set. Physical foreign keys are retained through struct-level `resource(foreign_key(...))` attributes; they do not generate page relations, joins, or cross-table transactions. Generation does not create or adopt source tables; their purpose still requires review and explicit migration or adoption. Unknown types, views, and unreadable columns are rejected; `tinyint(1)` is not guessed to be Boolean. Boolean, text/textarea, integer, date, datetime, Decimal, and JSON fields produce type-appropriate standard form controls; JSON query filtering requires a strongly typed extension. Run the Rust [example](../crates/ryframe-generator/examples/generate.rs) with `cargo run --locked -p ryframe-generator --example generate` or an IDE; import requires `--features schema-import`. The Builder's `plan()` is read-only, `execute()` performs execution, and only `.write(true)` updates files. For an existing database, first use `cargo generate --features schema-import -- import --package order-business --connection primary --database tenant --tables biz_order,biz_order_item --config-dir ../ryframe-dev-config --plan` to read tool defaults and list the task graph without loading application configuration, connecting to databases, reading migration metadata, or executing candidate generation. Removing `--plan` reads the source read-only and generates and validates models, CRUD, migrations, contracts, and optional frontend assets in an isolated candidate workspace, without updating either repository. Review `.ryframe/imports/`, differences, and compilation results before adding `--write`. If imported tables already exist in the runtime target, after `--write` you still cannot use ordinary `up` to guess adoption.

The model-level `#[resource(collation="utf8mb4_0900_ai_ci")]` declares table collation; string fields can override it with `#[resource(collation="utf8mb4_bin")]`. Undeclared tables use `utf8mb4_general_ci`, and undeclared columns inherit the table collation. Import reads actual table and column collations and preserves them in Rust models; DDL, structure fingerprints, copy catalogs, and adoption checks share these declarations. Only safe utf8mb4 collation names are accepted, and actual availability is verified against the target MySQL instance. Other character sets require migration review or an extension. Changing the collation of an existing model stops automatic migration for the entire batch: first review comparison semantics, unique indexes, and existing data; conversion is not automatic.

Physical foreign-key attributes declare `name`, ordered physical `columns`, `referenced_table`, ordered `referenced_columns`, `update_rule`, `delete_rule`, and `match_option`, for example `#[resource(foreign_key(name="fk_note_customer", columns=["customer_id"], referenced_table="legacy_customer", referenced_columns=["id"], update_rule="RESTRICT", delete_rule="SET NULL", match_option="NONE"))]`. References must stay in the same storage scope and database and resolve within the current managed resource set. The local table must explicitly declare an index with the same column prefix; referenced columns must exactly match a primary or unique key in order, with compatible types and string collations. Tenant constraints must include corresponding `tenant_id` columns, not only business IDs. Supported rules are `CASCADE`, `RESTRICT`, `SET NULL`, `NO ACTION`, and `MATCH NONE`; `SET NULL` requires nullable local columns. Unknown actions, cross-database or target references, duplicate names, unresolved targets, and dependency cycles reject the whole batch. Fresh tables are created in verified parent-first order. Adding, removing, or changing an existing foreign key requires review of a safe incremental migration; historical migrations are not rewritten and constraints are not dropped automatically.

The persistence target in a `resource` plan comes from each resource model and is resolved and validated during execution; one business package may contain both control and tenant resources. An `import` plan shows the schema source, selected tables and target type for generated models. Each uses its own target declaration, and both validate every registered business module before installation: with frontend synchronization disabled, they reuse `export_openapi`, so backend-only generation also requires the composition root's `bin-api` feature to compile; with synchronization enabled, they reuse existing contract validation without a duplicate export. Preflight starts no services or database connections, and failures install no formal assets. If scaffolding, backend resource generation, or backend preflight fails, the tool reports the path to the retained backend candidate and any recovery files. If frontend candidate generation fails, both candidates and their nested recovery backups remain at the reported paths. Inspect the failure site and formal files first; clean only those exact directories after resolution, without automatic replay. `--plan` only displays the plan and executes neither candidate generation nor preflight.

### Adopting Existing Tables

Adoption requires an exact match between the model, migrations, and physical database structure. First import or handwrite the model in the business crate and register its descriptor. Preview with `cargo generate -- resource --package order-business`, review the result, then add `--write`. Imported field types, collations, indexes, foreign keys, and migration history must be retained. Stop API, Worker, and scheduled writes on the target, and complete framework initialization in the control database first. Tenant tables must select one target key; `adopt` does not accept `--all`. To generate an adoption plan for the control database, run `cargo migrate -- --config-dir ../ryframe-dev-config control adopt --module order --output .local-tests/order-adopt.json --write`. For a tenant database, replace `control` with `tenant-data`, add `--target business-shared`, and select a different new output file. Saving the plan creates the artifact's parent directory. `.local-tests/order-adopt.json` is a private plan generated by the command. First use `--inspect` on that plan to check physical instance, database, tables, migration prefix, and fingerprints read-only; then use the same plan with `--apply ... --write` and the corresponding `verify`. A `--module` preview with `--plan` does not read configuration or databases. `--output` requires `--write`, and `--inspect` rejects writes. Partial registration, mismatched before-images, different sources, or structure drift all fail closed. For an unknown outcome, inspect the original plan first; do not replay with a different plan. If the target is empty and existing tables are only used as structure templates, adoption is unnecessary; create tables with normal `up`.

### Evolving Model Structure

After editing the Rust model, continue to preview with the same `cargo generate -- resource --package order-business`, review the result, and add `--write`. The generator retains the original bytes and digests of all historical migrations and only appends new migrations with stable numbering. `src/generated/migrations/history.json` and ownership retain the before/after structure chain together; this step does not connect to or modify databases. Fields can preserve physical types with `#[resource(sql_type="VARCHAR(32)")]`. Import writes this attribute automatically, and DDL, copy catalogs, and adoption checks share it. Currently supported types, matched to Rust types, are CHAR/VARCHAR, the TEXT family, signed integers and `u8/u16/u32/u64` unsigned integers, Boolean, DATE, DATETIME (0–6 fractional digits), and JSON. Character lengths, text byte capacities, and integer ranges are derived; contradictory validation, unknown declarations, or SQL clauses produce errors before writing. Integer CRUD preserves Rust width and signedness; defaults and enum values must fit that type. Physical SQL capacity must fully accommodate the model, and incremental conversions are checked against physical ranges. Ordinary `u64` fields retain their full unsigned capacity and are transmitted as strings; defaults above i64 use decimal strings. Primary keys support `i64/u64`, with consistent types across auto-increment and Snowflake strategies, URLs, and persistence. Decimal requires an explicit `DECIMAL(p,s)` declaration (1≤p≤28, 0≤s≤p) and uses the SDK's `rust_decimal::Decimal`; request bodies, queries, responses, and text forms all transmit strings. Values exceeding column capacity or scale are rejected; neither API nor SDK use cases round automatically. FlatCrud generates model-appropriate text or textarea, integer, switch, date, datetime, enum single-select, and exact Decimal text controls. JSON uses an editable textarea and is strictly parsed into a structured value before submission; empty nullable or optional text submits null or omission, respectively. JSON does not support standard query-parameter filtering; use a strongly typed extension for structured queries.

Declare composite indexes with the struct attribute `#[resource(index(name="idx_code",fields=["code","id"]))]`, adding `unique` for unique indexes. Import preserves index names, field order, and uniqueness, while rejecting prefix, descending, functional, invisible, and non-BTREE indexes. Only the necessary id-leading index for an auto-increment composite primary key is added; no redundant indexes are added for fields already covered by the primary key. A field's `#[resource(sql_comment="Database comment")]` is independent of its UI label. Import, DDL, model digests, and appended migrations preserve it, while structure fingerprints still check structure only. Quotes, backslashes, and newlines are retained as-is; field comments cannot contain NUL or exceed 1024 characters. Literal defaults use the field attribute `default="value"`; database clocks use `sql_default="CURRENT_TIMESTAMP(6)"` and `sql_on_update="CURRENT_TIMESTAMP(6)"`. Clocks only support 0–6 digits of precision consistent with the DATETIME column, and do not accept arbitrary SQL. `default` and `sql_default` cannot be combined. Import preserves both types of defaults and update-time expressions. Business fields with explicit database clock expressions are excluded from create/update forms. A typed insert input omits values that the database has not generated yet; repositories omit these columns on insert and do not write database-managed columns on update, returning the actual persisted values. Records, entities, and responses keep their declared non-null types. Audit fields without database expressions retain application-managed clocks; nullable replacement semantics for editable fields remain unchanged. Date and Decimal literal defaults must fit the current CRUD-supported range; other expressions require explicit migration extensions.

Omitting a non-null optional update retains the original value. Use an explicit extension for three-state patches. Business `i64/u64` values are transmitted as strings by default; bodies, queries, return values, and text forms retain exact decimal values and do not use number controls. Empty text submits null for nullable fields or omission for optional fields; required fields remain validated by forms and the server. Finite enums retain string values without conversion to floating-point numbers. ### Cargo tool source verification

Per-file metadata, link checks, and digest reads for complete source inventories use at most four standard Rust scoped threads and merge results in their original order. Results are never cached; the complete file set and all before/after Git and fingerprint checks remain in place. Reads stay serial while the recovery dataset static authority read window is active, including its final verification, to preserve protection of every actual input. Thread creation failures, read failures, and worker panics fail closed. After loading the same explicit settings, native cache tool capture first serially validates field formats and absolute, link-safe paths before running three independent read-only checks concurrently in fixed Image/Git/Manifest order. Image still performs full validation, including a second path check and all ELF/header/hash checks. It joins every worker before returning, reports failures in the original order, and constructs the binding only from the complete manifest whose digest matches. An active read window retains serial execution and stops at the first error; IO error classification is preserved. Inner per-file reads still use at most four threads without caching results. This optimization does not change acceptance deadlines or verification protocols. The remaining Python cache protocol reads one frame per explicit permission: another read starts only after the current port is handled and replied to; a complete terminal response does not wait for EOF from a long-lived service. Only the reader closes stdout, and the main thread waits for a bounded time. A timeout remains a failure that preserves unknown writes, intent, and locks without replay. If a read is already blocked, the daemon may remain until this short-lived CLI exits and the OS releases it; this does not prove that the reader exited or services were cleaned up. This transport is not used by a persistent controller that catches failure and continues running. See [Architecture: Cargo tool source verification](architecture.en.md#cargo-tool-source-verification) for the complete mechanism, failure handling, and managed-tool protocol. That section also covers the procedural-macro shared-cache regression and its command.
