## 部署与发布

生产镜像使用固定摘要的 Distroless Debian 13 运行层，只包含 API、迁移、Worker 及其运行依赖，不带 shell、包管理器、`curl`、生成器、文件维护或 reset。API 与 Worker 由自身的 `--healthcheck` 命令探测本机 `/readyz`。运行镜像仅设置应用环境变量 `APP_ENV=prod`，在工作目录 `/opt/ryframe` 下默认读取必须存在的明文 `config/app.prod.toml`，可用 `config/app.toml` 提供公共默认值；数据库、JWT、Redis、对象存储和监控凭据直接填写字段。真实文件保存在 Git 工作树之外的受控私有目录，并只读挂载到各实例容器的独立配置目录，CLI 用 `--config-dir <directory>` 选择；`scope_id` 保持稳定，各实例根字段 `snowflake_worker_id` 必须不同。镜像在部署配置中使用完整 `image@sha256:<digest>`，维护命令如提供镜像摘要选项则按其 CLI help 指定，不再使用项目环境变量传递。API、Worker、控制库迁移、租户数据迁移四角色模板及各自私有配置目录已集成，资产结构与 CI 工具测试通过；真实容器、镜像和部署整链仍未验收。若使用本地存储后端，在所选角色配置文件的 `object_storage.local_base_dir` 字段设置存储目录，不使用环境变量覆盖。下列命令是后续核对挂载、固定镜像和实际启动的示例，不代表运行验收已通过： 镜像构建使用 Docker 的 `SOURCE_COMMIT` 构建参数绑定 40 位小写提交 SHA。Dockerfile 校验后将它写入构建容器内的受管 `.local-tests/build/source-commit`，Rust 构建脚本只读取该文件；它不属于应用环境变量，也不会进入运行镜像。仓库内正式维护构建和恢复构建由 Rust/Python 协调器独占创建同一受管文件，完成后核对内容再清理；并发、漂移或未知清理结果会失败并保留现场。直接运行普通开发构建且没有该文件时，版本信息明确为 `development`，不能用于正式恢复证明。
```powershell
$sourceCommit = git rev-parse HEAD
docker build --build-arg "SOURCE_COMMIT=$sourceCommit" -f deploy/Dockerfile .
```
将公开的 `deploy/compose.prod.yml` 样例复制到自己的工作树外部署目录。使用该副本设置真实镜像摘要，并将四个角色的配置和共享 TLS 挂载的宿主机 `source` 改为实际目录的绝对路径。保留容器内挂载目标、只读设置和 `create_host_path: false`。CI 在后端仓库根目录校验受版本控制的模板，实际部署使用上述工作树外的副本。配置解析、固定镜像和实际启动需要分别验证。
```powershell
docker compose -f "D:/deployments/ryframe/compose.prod.yml" config
docker compose -f "D:/deployments/ryframe/compose.prod.yml" up -d
```
四角色部署顺序是先更新控制库与租户库，再启动 Worker 和 API；模板结构检查不替代真实环境的启动和升级验收。启动后检查 API `/livez`、`/readyz`，以及 Worker 健康端口的 `/readyz`。Nginx 只代理 API 的 edge 网络端口，MySQL、Redis 和对象存储保持在内部网络。直接在主机运行时，先创建空数据库并设置 `APP_ENV` 与配置，再按 `control up`、`control verify`、`tenant-data up --target shared-control`、`tenant-data verify --target shared-control`、`cargo serve` 的顺序执行。默认单租户也有控制库和 `shared-control` 两套迁移账本；`verify` 只校验，新空库必须先 `up`。完整步骤见[数据指南](data.md#全新环境初始化)；完整 SQL 导入同一物理控制库后，直接执行 `control verify` 与 `tenant-data verify --target shared-control`，无需补 `up`；其他独立 MySQL 租户目标仍须各自 `tenant-data up/verify`。生产默认且只允许 `jobs.mode="external"`，不能只启动 API；为 API、Worker 分别准备含 `app.prod.toml` 的私有目录，在两个终端均显式设置 `APP_ENV=prod`，以各自的 `--config-dir <directory>` 先启动 Worker 再启动 API；两角色使用不同 `snowflake_worker_id`，指向同一控制库和 scope。 本机沿用 README 的仓库外配置目录时，本文默认 `config` 的 Cargo 别名示例须在 `--` 后传 `--config-dir ../ryframe-dev-config`，例如 `cargo migrate -- --config-dir ../ryframe-dev-config control verify` 或 `cargo serve -- --config-dir ../ryframe-dev-config`；后续校验、导出和运行继续选择同一目录，避免连接另一份未初始化配置。 完整 SQL 的结构断言失败会输出迁移、阶段与类别；保存原始结果和现场，不因账本仍为空就认定 DDL 已回滚。先只读核对，禁止自动重放或补写完成标记。 当前版本只接受全新生产库。已有真实生产旧库需要先设计并演练非破坏升级方案，不能使用 reset 代替升级。 生产 API 还必须通过 TOML 的 `app.locales_dir` 提供完整 `zh-CN.toml` 与 `en-US.toml`；默认目录为 `locales`，普通应用相对进程当前工作目录解析，不读取 `APP_LOCALES_DIR`。缺失或加载失败会严格拒绝生产启动；开发环境的内嵌回退不能替代生产资源部署。

## 非生产重建

重建仅用于非生产环境。完整配置、双阶段命令、账本及失败恢复规则见[架构说明：非生产重建](architecture.md#非生产重建)；生产环境永久拒绝该入口。重建核验保留每个当前租户唯一的规范数据范围投影 bootstrap outbox 种子，严格核对版本、载荷和未投递状态；其他运行时资源表仍须为空。种子不符时保留现场，不通过清空事件绕过核验。 参考夹具的 `environment prepare` 配置输出应选择保留服务根旁的独立新目录，例如服务根 `run-copy-<id>` 与配置目录 `env-copy-<id>`。配置输出不得等于 `review.future_root` 或位于其内部；工具在创建配置文件或输出目录前拒绝该布局，且不会启动服务。发生错误后保留已有环境和失败证据，通过正式审阅入口确定新布局，不覆盖或自动重放原现场。 环境准备由原生入口直接生成本机文件，成功前重验来源、维护构建和秘密文件，最后发布 `bootstrap.json`；不启动服务或写入数据库。显式 `--secrets-dir` 必须属于 `execution-source.json` 中 `original.paths.backend` 指向的原生成业务树 G，而配置输出属于发布执行树 P。非默认秘密集需要完整的 `secret-set.json`；用 `cargo xtask check recovery fixture environment rotate-secrets --fixture <fixture.json> --output <new-secret-set> --write` 创建。 夹具计划与已准备环境的每次只读核验使用一个输入窗口：读取前后分别完整核对原生成与发布的前后端四个源码根，并在首读前保护 `execution-source.json` 与原 `fixture.json` 的字节和文件身份。没有活动的静态权威读取窗口时，四个源码根的完整观察最多使用四个线程并行；活动权威窗口内仍由所有者线程串行消费并保护全部实际输入。所有已创建的观察线程都会结束并收集其结果，单根或线程失败仍保留其余来源与文件后验；来源检查、跨调用边界和既有期限不变。 中间只复算同一纯计划，不跨调用缓存；原计划 JSON、SHA-256 与输入投影保持不变。bootstrap 从首读前受保护，配置目录、私有环境和秘密文件在读取后重新核对；同字节替换也会被阻止或拒绝。已建立有效窗口后，即使业务读取或某一来源失败，仍执行其余可做的来源和文件后验，并保留同时失败的原因。原输入无效、缺失或无法建立完整来源前像时直接拒绝，不生成文件、启动服务或重放操作；既有期限不变。 各启动角色独立执行读取窗口，既有时限和失败不重放规则保持不变。

## HTTP 5xx 与高延迟

应用日志过滤级别使用配置中的 `logger.level`；`RUST_LOG` 不会覆盖该级别。排查时修改所选配置文件并重启对应进程。 先按请求 ID 检查 API 日志和 trace，再检查数据库、Redis、对象存储与 Worker。确认是单一依赖故障后按降级策略处理；不要通过扩大重试放大故障。

## Redis 与对象存储约定

- Redis `timeout_secs` 统一约束连接、响应和事务，范围 1–60 秒；兼容 S3 后端使用 `object_storage.request_timeout_secs`，范围 1–300 秒。不得在调用点叠加无上限重试。Redis 故障时检查连接模式、TLS、ownership marker 和 scope 前缀；授权缓存不可用时必须失败关闭或按配置禁用缓存，禁止清空共享 Redis DB。
- 就绪探针只执行 Redis `PING` 和对象存储私有桶检查，并受独立短超时保护；`required` 依赖失败才阻断就绪，可选依赖明确进入降级状态。
- `ryframe_connector_operations_total` 与 `ryframe_connector_operation_duration_seconds` 只使用 connector、固定 operation 和 result 三类低基数标签。端点、租户、Redis 键、桶名和对象键禁止进入指标标签。
- Redis 与 S3 配置的 `Debug` 输出会隐藏密码、访问密钥和客户端私钥。S3 非成功响应只保留稳定操作名和 HTTP 状态，直接丢弃远端响应体；传输错误移除请求 URL。文件维护错误只携带内部文件 ID，不记录桶名、对象键、Authorization、签名或负载。
- 确定性测试使用本地实现或离线协议样本；真实协议测试必须显式启用，并使用唯一 schema/namespace 与精确清理，禁止 `FLUSH`、`KEYS` 和模糊对象前缀删除。

## Refresh Token 重放与异常账号恢复

立即撤销 token family 和当前会话，核对用户授权版本、客户端 IP 与审计事件。确认泄露后轮换相关凭据并保留证据。旧开发版普通账号无法登录且密码未知时，使用[显式账号恢复流程](api.md#异常账号恢复)；不要重复初始化或直接修改密码哈希。停用与改密要求独立，重置成功不会自动启用账号。

## 依赖与任务排障

| 现象 | 核对与处理 |
| --- | --- |
| 限流拒绝 | 区分租户配额、账号策略和基础设施故障。只在确认业务容量允许后调整配置，不删除限流键或绕过租户边界。 |
| 数据库连接、启动与容量 | 必需数据库启动失败诊断区分连接池建立与 PING 阶段，标明安全目标、`database.primary` 或 `database.sources[i]` 及 source name，并保留脱敏后的底层原因；本次进程启动已中止，尚未进入服务监听阶段。核对所选配置的 host/port/database、MySQL 服务监听、网络、账号及数据库访问权限、TLS/证书和连接/获取超时与池容量，修复后重新启动；pool timeout 本身不证明密码错误。日志不输出用户名、密码、凭据 URL 或私钥。连接容量按控制库、租户目标和 Worker 分别统计；优先处理泄漏、慢查询和错误并发，再调整池上限，总连接预算不得超过数据库限制。 `cargo migrate` 的 stderr 区分配置、连接、预检、执行、关闭和文件发布；同时保留操作与关闭错误。迁移阶段失败时不能套用启动前零写入结论，先用原配置执行 `status`、`verify` 并核对账本；独立目标不可用不等于 `1045`，不得猜测未保留的底层原因或自动重放。 建议命令中的 `--config-dir` 占位必须替换为原配置目录并正确引用，不能省略后改查默认库。 独立 MySQL 目标的底层原因只以脱敏文本进入内部诊断，不进入公开 API 响应。 |
| 数据库副本与读回退 | 检查复制延迟、连接健康和 read consistency。授权、任务、导出与状态变更必须回到主库；不要把强一致读临时改为副本读。 |
| 后台任务 | 检查 lease、heartbeat、attempt、公开错误和死信状态。数据库会拒绝重复领取；修复原因后使用受控重试，不直接改任务终态。用 `background_job` span 的 `job_id` 和 `claim_sequence` 关联持久化的任务尝试，并查看 `outcome`。|
| 定时调度 | 核对表达式、时区、misfire 策略和下一次运行时间。夏令时回拨时，预览保留原有的本地时刻顺序，调度执行只选取 UTC 时间严格晚于计算起点的触发时刻。避免同一业务任务由多个 scheduler 重复创建。 |
| 消息中心投递 | 检查 outbox、分发任务、目标受众和多语言参数。先恢复幂等消费，再处理积压；不要跳过租户或权限过滤。 |
| OpenTelemetry 导出器 | 导出失败不应阻断业务请求。检查 endpoint、TLS、超时和队列丢弃指标，恢复后确认 traceparent 继续传播。 |
| 磁盘容量与离线缓存 | 检查 `target`、日志、临时 XLSX、上传暂存和本地对象目录。只删除已确认的构建缓存或已过期产物，保留最新调试符号和 reset ledger。pnpm 离线失败出现 `ERR_PNPM_NO_OFFLINE_META` 或 `ERR_PNPM_META_FETCH_FAIL` 时，核对工具文件的 `verification.pnpm_cache_dir`；在独立目录使用同一 registry 联网准备所需缓存/元数据和冻结依赖，并确认策略检查及真实 `--offline --frozen-lockfile` 安装通过。保留失败夹具，修复后使用新输出目录；不关闭供应链校验、不改锁文件或自动重放。原生全栈失败日志保留退出状态和操作目录，只提取已知错误码，不回显任意子进程原文。 |

## 备份失败或过期

业务表复制目录由原生业务目录加载器从执行后端的显式 Workspace 成员读取，统一核验受管生成资产、内容摘要、模块归属及完整表描述；返回表顺序保留 Workspace 与机器目录的声明顺序。业务迁移账本的完整列和类型来自同一 Rust 校验入口读取的正式 SDK DDL。普通源导出同样使用该完整目录进行结构核验，包含已登记业务的迁移账本，不再单独拼装完整表清单；用于数据复制的受审查目录与用于结构核验的完整目录仍分别保留其职责。验收调用方通过显式绑定当前工具的只读协议取得结果；Python 桥接不再单独解析或接受片段目录。目录或归属被拒绝时，应核对执行工作树，并通过正式生成入口修复受管资产；账本结构被拒绝时，应核对执行树的 SDK 版本及 DDL。不能过滤未知表或绕过校验继续复制。 普通源导出的逻辑库存先逐项核对常规业务像和逐目标原始业务像，再纳入 `biz_data_scope_owner`、`biz_data_scope_dept` 和 `biz_data_scope_projection` 的实际行数与摘要；这些投影非空时不能把遗漏目标补作空目标。账本和 ownership 不因此成为业务数据。多库转储目录在本次批次开始时仅独占创建一次；已有目录或载荷不会被覆盖，失败后保留原 attempt，先核对完整现场再使用正式恢复入口。

参考复制工具由 Rust 读取和精确解码完整 SQL 转储，再向现有协调调用方提供受管分块结果，不逐行启动子进程。即使只选取租户声明表，也先校验完整表目录、全部列和未选表的数据；数字保留精确值，JSON 拒绝重复键和非有限数字。结果目录绑定原转储、目录摘要、文件身份和完整结果摘要；每块读取继续核对这些绑定，只有完整消费并核对 EOF、行数和来源后才精确删除该次结果。创建、读取或关闭失败时保留失败现场，不自动重试或删除原转储。 正式复制失败时，命令提示本次阶段记录和运行清单；复制目录的 failure.json 保存失败阶段、完整调用位置与可用系统码，不保存异常正文、参数或源码行。先核对完整前后像，不能仅凭失败类别重放。 来源快照提示无法执行 Git 时，核对本机 Git 安装和操作系统 PATH；协调器切换应用环境时保留安全白名单中的 OS 变量，应用配置仍仅由 APP_ENV 选择文件。 全栈构建与运行核验共用原生来源事实，同时核对模型文件、完整 Git 快照和适用的 CI 运行身份；来源不符时保留现场，不手工改写原来源收据。报错指向的 `.local-tests/sql-row-streams/sql-rows-*` 是本地派生结果，不表示已完成远端复制；先保存诊断并核对来源及完整目标像，再通过正式恢复入口继续。 停止依赖无效备份的迁移操作，检查目标、校验和、采集时间和保留策略。恢复后重新生成并验证备份，不手工标记为成功。外部工具负责备份与还原字节，RyFrame 只负责清单采集、登记、恢复验证、状态和告警。 源导出与后续代次核验共用完整物理绑定：数据库连接身份、目标模式、对象存储公开元数据及整体摘要均须一致，不包含凭据。绑定不完整或不一致时保留原导出和失败证据；核实源数据与目标后像后，通过正式入口在新运行目录重新只读导出，不改写、补签旧导出或自动重放复制。

### 参考环境与一致性

参考演练采用系统租户和 10 个普通租户，覆盖共享与独立数据目标，至少 10 万条代表性业务记录和 1 GiB 对象数据。外部运维调度每 12 小时执行完整备份，保留至少 7 天。演练报告必须记录 Windows 机器、MySQL/RustFS 版本、存储和网络条件；24 小时恢复点、60 分钟恢复时间是该规模下需要实际验证的目标。 开始采集前暂停业务写入，停止 API 写入入口、Worker、scheduler 和消息等生产者。在整个清单采集、数据库转储和对象复制期间保持静止，避免把多个时间点的数据登记为一致备份。数据库按完整主键顺序计算摘要，对象采用流式 SHA-256；清单包含源码 SHA、schema 指纹、物理数据库身份、租户 placement、对象前缀、字节数和摘要，不包含密钥。

复制后的管理员会话使用独立的当前凭据文件。先通过正常账号流程完成首次改密，再在后端忽略目录中创建私有文件，例如绝对路径 `<backend>/.local-tests/clone/administrator.toml`：
```toml
[administrator]
tenant_id = "system"
username = "admin"
password = "<current-password-after-first-change>"
```

post-copy 注册请求的 `source_admin` 仅包含 `subject_id`、`tenant_id`、`username`、`client_address` 四项元数据；另以 `administrator_credentials` 登记该 TOML 的 `path`、`bytes` 和 `sha256` 文件绑定，不把密码写入请求、公开登记或收据。文件中的租户和用户名必须与元数据一致，文件及各级路径不得经过链接或越出当前后端的 `.local-tests`。注册和会话启动在读取前后核对文件绑定；内容或绑定变化、字段错误和 TOML 解析失败均拒绝继续，诊断不回显文件原文。登录后还要求权威 `SessionContext` 顶层的 `password_change_required` 明确为布尔值 `false`，为 `true`、字段缺失或类型错误时拒绝进入业务动作。此密码独立于 `bootstrap.admin_password`，工具不自动改密、不回退初始化密码，也不重放业务写入。未完成首次改密时，先完成明确的账号流程，不能将初始化密码作为当前凭据登记。

继续通过 `cargo xtask check recovery clone post-copy --run-dir <run> --operation register --request <request.json> --write` 显式登记；后续产生写入的操作仍需 `--write`。`api_environment` 的应用选择仅允许 `APP_ENV=test`。原目标环境若绑定 OS `TEMP` 和 `TMP`，API 环境须原样保留两者，并在业务核验时确认两者指向同一个现有的受管私有目录。初始和 API 两映射必须完全一致，不传递管理员凭据或其他项目配置。地址、Worker 模式和 CORS 等设置来自各自绑定的应用 TOML。amendment 仅可在既有停止证明和失败核对流程后重新绑定环境选择文件，不能借环境字段修改项目配置。 post-copy 的 pacing 绑定只读采用显式请求的 `frontend_root`，不要求固定目录名或与后端同级，也不从 `tools.toml` 二次选择前端。请求的 `pacing` 包含 `contract`、`bindings` 和 `login_budget_module_sha256`。其中 `bindings` 仅包含 `login_budget_state`，须指向当前 run 的 `post-copy/login-budget.json` 绝对路径。原生入口两次核对所选前端 `scripts/browser-login-budget.mjs` 的 SHA-256，并拒绝链接、越界路径、未知字段及绑定漂移。该校验不创建或覆盖预算状态。`contract` 的业务语义仍由原会话阶段校验。 会话的 `app_config_dir` 由已冻结目标登记通过现有配置目录核验器解析，不从环境或 post-copy 请求另取目录。 未显式登记 `execution_backend` 时，工厂与交接共用绑定维护收据的 `backend_root`，只接受当前后端规范路径或其 `.local-tests` 内的现有无链接执行目录。根缺失、越界或收据摘要漂移即拒绝；保留原收据，核对已登记执行树与文件绑定，不猜测根、不创建目录或自动重放。 这两项只读校验失败会给出固定阶段和原因；能可靠取得的原始 IO 系统码会保留，诊断不回显输入值或原始收据。

`schedules`、`reconcile`、`verify` 与 `recover-session` 通过同一 Rust 入口执行。`schedules` 为每次写入保留前像和意图。遇到结果不明时，`reconcile` 先以原始数据库全行和实际 API 行核对意图。完整行等于原前像时，后续 `schedules` 可以另建一次尝试。完整行符合预期停用后像时，沿用核对结果并保留原意图。`verify` 使用同一数据集和复制账本，逐个完整读取业务验证未覆盖的对象。源血缘核对整份原对象清单，已登记的独立探针也核对其完整字节和元数据。`recover-session` 使用 `--producer-binding <binding.json>` 选定原阶段的进程收据，只回收该已登记生产者。整个阶段保持 Worker 停止。 复制后业务验证通过后，使用 `cargo xtask check recovery clone seed-runtime --run-dir <run> --operation register --request <request.json> --write` 绑定同一运行的业务核验和身份计划。登记由 Rust 控制器持有目标代次、存储及复制账本的互斥。登记通过后仍保持 Worker 停止，后续启动需由 seed 阶段单独授权。同一 `seed-runtime` 入口先执行 `--operation quotas-plan --write`，再执行 `--operation quotas-apply --write`。如果更新结果不明，先执行 `--operation quotas-reconcile --write`，以完整租户配置和用量核对原意图。历史会话可用 `--operation recover-session --producer-binding <binding.json> --write` 回收，随后继续核对已有意图。配额全部确认后，在原 API 运行且 Worker 停止时执行 `--operation identities-apply --write`，准备固定身份账本。随后部门阶段使用 `--operation departments-plan --write`、`--operation departments-apply --write` 和 `--operation departments-verify --write`。若写入结果不明，先用 `--operation departments-reconcile --write` 核对完整前后像。十个租户及其模板身份来自已登记计划。部门只读验证通过后，仍在原 API 运行且 Worker 停止时执行 `--operation identities-verify --write`，核验完整身份账本及其发布收据。身份核验通过后，使用 `--operation prepare --write` 复用原 API 和 Worker 配置及产物，发布 seed 运行交接。此操作只登记文件，Worker 端口须关闭。最新准备通过且新 seed 尚未尝试启动时，执行 `cargo xtask check recovery clone runtime --run-dir <run> --side target --operation stop --roles api --write`，按原进程收据关闭 post-copy API 监督树，保留原 `api.json`。随后 seed 启动核对同一准备结果与退场收据，并要求原 API PID 已不存在、API 和 Worker 端口均关闭。启动按 API、Worker 顺序执行。seed 的启动、状态、显式停止和原操作回收由 Rust 入口直接执行。启动控制器持有原目标代次、存储锁和复制账本保护，在启动前后核对身份、容量、调度与交接。状态只读，显式双停按 Worker、API 顺序执行。业务关闭由 Rust 正式阶段持有原目标和运行锁。先停 API，核对同一 Worker 的稳定排空检查点后再停 Worker，最后读取共享控制库并核对完整闭口。中断后沿用同一运行交接和原阶段结果或连续检查点。 同一 Close 的成功停止经显式 recover 核对后，可以按原检查点继续 close。续作校验 recover 阶段、原停止预留、归档摘要和已停止的原进程代次。若 recover 在写入停止历史后、发布阶段结果前中断，先按原控制器收据恢复运行锁，再次执行同一运行的 recover。它根据写入历史前原子发布的标记重核同一归档和已停止代次，不重复追加历史。只有随后发布的非空成功停止证据才能跨过该中断。其它中间阶段或只有空恢复结果时拒绝续作。未知角色结果保留原意图与监督树收据，恢复只核对原操作。归档结果具备独立的同代监督树证明时可补齐历史。 显式停止和业务关闭在操作前登记角色的原启动编号和创建身份。若停止已归档但尚未写入历史，恢复核对原控制器、停止编号、完整成员退场与原端口关闭后补齐历史，不重放角色动作。 启动第二个角色在发布启动意图前失败时，若已核对完整闭口，回滚先启动的 API。回滚绑定同一阶段的原 API 启动收据，归档恢复只补记启动回滚事件。显式双停遇到单侧待定锁时，只收尾能独立核实的另一侧。两个角色均完整关闭后才可重新启动。排空和最终快照从原登记共享控制库只读取得。

若首个用户创建请求已经成功，身份账本仍停在该请求的 `started`，先核对原身份生产者和控制器已退出并完成锁释放。维护人员用原运行中已绑定的失败、进程、锁释放、原账本摘要和 API 日志摘要，以及经验证的独立后继工具构建收据准备和解请求。
```powershell
cargo xtask check recovery clone seed-runtime --run-dir <run> --operation identities-reconcile --request <request.json> --write
```

Rust 控制器在原运行锁下核对实际 API 代次和唯一 HTTP 200 记录，再只读核对同一 SQL 快照中的用户、首次改密、角色及成功审计。该阶段保留原账本前像与失败证据，按同一确认意图原子更新账本并追加后继工具登记。成功后由已登记的后继工具显式执行 `identities-apply`，从原已确认前缀接续。保持原 API 在线、Worker 关闭，并完成原身份、部门及正式恢复核验。 若身份核验中断后已确认唯一遗留会话，先完成并确认同一运行的第二代 API 接续，再通过上面的 `identities-reconcile` 命令提交独立会话收口请求。请求类型为 `devex-clone-identity-verification-session-reconcile-request`，绑定原核验失败、已发布的第二代 API 和原 Redis 会话前像。控制器通过系统管理员发出一次强退，核对 Redis 后像、同一服务端请求的成功审计和管理员会话关闭。结果不明时只核对已登记的原请求。

### 采集和登记

在 Windows 维护机通过 `cargo xtask data` 执行备份和恢复登记；备份与恢复使用受控的私有配置，框架维护验收证据按对应命令登记。该维护能力不包含在生产运行镜像中。 Windows 历史生产者的停止核验先读取内核身份：进程不存在，或同一 PID 的创建时间严格晚于登记时间，才证明旧代次已经结束。仅在内核查询返回拒绝访问（错误码 `5`）时，使用受管 Rust 子进程查询本机 CIM；查询超时预算为 15 秒。CIM 保留微秒精度，创建时间必须严格晚于旧时间加 10 个 100 ns tick 的边界。同一代次、相邻精度边界、重复身份、未知时间或查询失败都拒绝登记，不再回退 PowerShell/PDH，也不会向占用该 PID 的进程发送信号。 若错误包含 CIM 的 HRESULT，先用 `Get-Service Winmgmt` 查看本机服务状态，并检查 `ROOT\CIMV2` 的读取权限。修复后重新执行原核验命令；保留已有阶段结果和局部文件，按实际状态恢复，不手工改写“已停止”或自动重放数据写入。`Get-Service Winmgmt` 仅用于人工排障，不是运行时回退。
```powershell
cargo xtask data backup inventory --output <absolute-new-file-in-backend-workspace/.local-tests> --source-sha <exact-backend-sha> --quiesced-at <writes-quiesced-at-rfc3339>
```
`backup inventory` 与 `target inventory` 都是显式选择的只读库存操作，只在当前后端 `.local-tests` 内以 create-new 语义原子创建新证据文件，不修改数据库、对象或登记状态，因此不使用 `--write`；输出文件必须事先不存在。随后由外部工具按清单中的精确数据库、表和对象前缀完成复制与校验，再补齐 `id`、`completed_at`、`retention_until` 和 `artifacts`，形成 `BackupManifest`。每个 `db:<logical-target-key>` 与 `objects:<bucket>` 至少对应一个文件产物，登记其 `relative_path`、`bytes`、`sha256`；相对路径不得越出备份根目录。结构定义见 `crates/ryframe-application/src/ports/backup/manifest.rs`。 需要检查尚未分配租户的目标或初始化前后状态时，使用 `cargo xtask data target inventory --target <configured-target-key> --output <absolute-new-file-in-backend-workspace/.local-tests>`。该命令只连接明确配置的数据库，校验 schema 和精确全表目录，并在只读事务中计算完整行摘要；`target.database` 保存业务表与 placement，`target.preserved_tables` 单独保存 ownership、迁移账本和备份恢复登记表。它不访问对象存储、不修改目标，也不把未使用的目标遗漏为“空清单”。控制库与独立目标之间的一致性仍要求外部停止所有生产者；单份目标清单不表示备份或恢复成功。
```powershell
cargo xtask data backup register --manifest <absolute-manifest-in-backend-workspace/.local-tests> --backup-root <registered-external-absolute-backup-directory> --write
cargo xtask data backup status
```
登记会重新读取文件验证大小及 SHA-256，缺失或损坏会登记为无效并返回失败。同一备份 ID 只允许重复验证相同清单，不允许替换数据。登记成功表示已校验备份文件，尚不能表示恢复成功。状态查询只读取控制库，不依赖对象存储当前是否可连接。

### 隔离恢复与验收

1. 准备全新的隔离数据库和对象前缀，先按当前基线初始化并建立目标 ownership。首次初始化自动登记归属；既有未登记库须先停止生产者，按[数据指南](data.md#首次初始化与既有数据库归属接管)审阅并执行 `ownership-adopt`，不能手工补 marker、重跑 `up` 认领或用 `reset` 替代；提交未知先 `inspect` 原计划。逻辑 target key 保持一致，物理数据库、scope、JWT 密钥和 Redis namespace 必须与原环境不同，Worker 使用 external 模式。维护命令的 `--config-dir <directory>` 选择源侧登记库配置，`--restore-config-dir <directory>` 只选择隔离恢复目标配置；核对两份明文文件中的物理身份、scope 和端点，避免混用源与目标。应用相对配置目录以命令当前工作目录解析，建议使用绝对路径。产品 `backup-register`、`restore-begin` 和后续验证状态均写入源侧登记库。
2. 按 `crates/ryframe-application/src/ports/backup/restore.rs` 的 `RestorePlan` 填写完整目标、故障时间、前端 SHA、API/Worker 就绪地址和新对象前缀。物理数据库身份必须匹配，不能指向任一原业务库。
3. 在开始外部还原之前执行 `restore-begin`。重复相同 plan 不重置计时。外部还原仅覆盖该 plan 中已核验的隔离资源，保留目标自己的 ownership 和备份登记元数据；数据库转储只含清单中的业务表，不执行指向源库的 `USE`、数据库创建或跨库语句。对象路径仅替换 scope 前缀，不能复制源 ownership 标记。
4. 停止目标业务写入，执行 `restore-verify-data`。它重新验证备份文件、当前 schema、完整表内容、租户关系和完整对象集合，缺失、多余、损坏或错误 ownership 都会失败。
5. 使用全新 Redis 临时状态启动 API、Worker 和前端，完成真实浏览器业务验收，再提交绑定演练 ID、plan hash、源码 SHA、scope 和时间范围的 `RestoreBusinessProof`。`restore-verify` 使用单独绑定精确源码和程序摘要的 Rust xtask，从原协调根独立复核浏览器证据与三端运行代次，随后再检查 API 与 Worker 就绪探针。只有数据与业务验证均通过且总计时不超过 60 分钟、备份恢复点距离故障不超过 24 小时才记录成功。

依次运行 `cargo xtask data restore begin --plan <absolute-reference-plan> --backup-root <absolute-backup-root> --target-plan <absolute-target-plan> --runtime-registration <absolute-runtime-registration> --maintenance-root <absolute-maintenance-source-root> --maintenance-build <absolute-maintenance-build-receipt> --output <absolute-new-running.json> --write`、`cargo xtask data restore verify-data --id <drill-id> --backup-root <absolute-backup-root> --output <absolute-new-data-verified.json> [--config-dir <absolute-source-registry-configuration>] --restore-config-dir <absolute-target-configuration> --write` 和 `cargo xtask data restore verify --id <drill-id> --proof <absolute-business-proof> --tests-receipt <absolute-test-details> --runtime-receipt <absolute-runtime-receipt> --target-plan <absolute-target-plan> --coordinator-root <absolute-coordinator-worktree> --coordinator-sha <full-coordinator-sha> --runner-root <absolute-clean-test-runner-worktree> [--config-dir <absolute-source-registry-configuration>] --restore-config-dir <absolute-target-configuration> --write`。数据核验和最终业务核验可用 `--config-dir` 选择来源登记库配置，省略时仍使用调用工作树的 `config` 目录。`--coordinator-root` 与 `--coordinator-sha` 分别指定原协调证据根和精确提交；最终核验的目标计划必须位于该协调根的 `.local-tests`。维护程序在当前核验工具的编译源码根构建，协调源码、核验源码和测试 runner 分别核对干净提交。`--restore-config-dir` 选择恢复目标配置。演练计划、目标计划与后端输出位于当前后端 `.local-tests` 子目录。业务证明、测试明细和运行收据副本使用指定 runner 的 `.local-tests/playwright-real` 下的 `restore-<drill-id>.json`、`restore-<drill-id>-tests.json` 和 `restore-<drill-id>-runtime.json`。备份根、隔离配置和干净 runner 可以使用已登记的外部绝对目录。所有路径都不能经过符号链接或重解析点；输入文件和目录必须存在，输出父目录必须存在且目标文件必须不存在。这些条件及 `--write` 在启动维护二进制和连接资源前核验。业务成功后先在同目录写入并同步临时文件，再以 create-new 语义原子发布并重读规范字节、JSON 和路径。参数错误、业务失败或已有目标不会创建或截断成功记录；若业务写入成功后发布或复核失败，保留登记库状态和任何已发布文件，先运行只读状态核对，不得盲目重放。`restore-begin --output <new-file>` 发布的运行中记录继续传给外部恢复阶段。

恢复开始登记在参考演练目录、运行登记与存储锁内执行。控制器使用参考计划中的原登记库配置和隔离运行登记中的目标配置，复核前像后由标准输入交给已登记的维护程序。运行记录写入本参考演练目录；控制器另存一份绑定原初始化、备份、维护产物和运行记录的收据，参考恢复在导入前复核这两份记录。开始结果未确认时保留收据，并在原登记库中只读核对状态后再接续。

存储布局及完整代次核对通过受管 Rust `__target-evidence` 端口；Windows 参数只返回摘要，并在读取前后核对创建身份及绑定收据。status 不创建观察目录或文件，执行阶段的布局证据继续独占新建；原生 CIM 查询失败须修复权限或服务后重新核对，不能回退 PowerShell、猜测参数或自动重放。 原生 fresh-target 静态校验只从所选明文配置文件读取连接、凭据、Redis 和 Worker 地址，环境映射仅用 `APP_ENV=test` 选择测试文件。新 fresh-target 初始化在首次资源写入前，从原 E 派生 reset 专用私有原子配置快照；仅补已绑定维护来源的 reset.source_sha、已核验受控目标的停机断言和精确 target/reset-state，显式冲突拒绝覆盖。原 --output <原运行目录> --resume --write` 续接本地登记。入口只接受 `artifacts` 中原四个程序、`source-pair.json`、`binaries.json`、`build-evidence.json`、`backend-build.json`，以及原 `<运行目录名>-configuration` 下各含 `app.toml` 和 `app.test.toml` 的 `config`、`worker-config`。它在与普通构建共用的目录互斥内，保护并重验原来源、发布清单、四产物、工具链、构建环境、并发和角色配置；只读取 Cargo/Rustc 版本，不重新编译、复制配置、启动服务或连接业务资源。验证通过后由正式登记器新建 `runtime.json` 与 `runtime-evidence.json`，再执行完整本地运行合同核验。已有失败、运行、控制或未知文件、部分前缀、链接和任意漂移均拒绝；原文件和失败证据不覆盖，未知结果不重放，已登记后也不能再次续接。未带 `--resume` 的普通构建仍只接受新目录。

完成同一 source_to_seed run 的复制、post-copy、seed 验证和 close 后，使用正式来源登记入口：
```powershell
cargo xtask check recovery clone seed-runtime --operation source-register --run-dir <absolute-run> --write
```

`<absolute-run>` 必须是当前后端 `.local-tests` 内已登记且无链接的运行目录。该操作必须显式传入 `--write`，不接受 `--request`、`--output` 或手工指定 attempt；它读取固定运行清单和阶段历史，由统一 Rust 阶段控制器分配 attempt 并直接执行来源登记，不启动 Python materialize 或登记脚本。执行期间实际持有目标 Generation 和复制账本 guard，要求完整历史生产者已停止，并进行两轮来源锚点、请求和 generation 验证。每个历史运行代次绑定其已发布准备收据，并核对原产品构建的登记根。有 API 后继时，登记逐代核对其发表收据和停止身份。历史原生复制后核验按该次登记的工具、配置与命令收据核实。后继导出沿用原配置文件和已登记的成对 TEMP/TMP，不需要将配置复制到产品工作树。六项本地证据按固定顺序发布；失败保留已写前缀，不自动清理、重放或猜测多个旧目录。同一 run 已有其他成功来源登记时拒绝再次发布。正常收尾会核验并释放本次实际持有的控制锁，guard 文件可以继续保留；锁校验或释放失败时保留现场和异常残留锁，不手工删除后强行重试。

成功 stdout 的顶层 `status` 是 `stage_finished`，同时包含 `stage="seed-runtime"`、`mode="source-register"`、控制器分配的 `attempt`、内层 `result` 和 `restore_qualified=false`。内层 `result.status` 才是 `seed_source_registered`；`result.registration`、`result.source_request`、`result.source_storage`、`result.generation_verified` 均为含 `path`、`bytes`、`sha256` 的文件绑定，另外包含 `remote_writes=0`、`outbox_drained=true`、`restore_qualified=false`。后续调用应消费这些内层绑定，不能读取顶层 `registration`。`<run>/results/NNNN.json` 保存内层结果，NNNN 对应本次 attempt；六文件证据可续接唯一旧前缀目录，实际位置以返回绑定为准。私有 source request 保留在受控文件中，不把配置凭据复制到公开登记。登记成功不表示完整端到端恢复或正式演练已通过，也不授权远端写入。source-register 遇到 `HistoricalProducerCimUnavailable` 时会记录失败阶段并返回安全诊断，不返回成功的 `stage_finished` 结果。 执行 `cargo xtask check recovery fixture successor relationship` 时，`--predecessor-review` 必须是 `--predecessor-request` 精确绑定的原 seed 审阅。已就绪前驱复核完整预检及其来源，历史 pending 只在显式绑定的关系内用于只读核对。`--successor-review` 仍须由 pending 计划签发为 ready，三侧请求使用同一服务代次并保持原有资源隔离。关系由 Rust 独占写入，必须显式指定 `--write` 和新 `--output`。已登记关系通过同一规则只读重验。

`cargo xtask check recovery` 调用私有的本机 MySQL、mysqldump、原生 Rust S3 客户端和 Node 阶段程序准备演练数据与外部备份。参考计划只能通过 `inputs reference` 从已发布共享导出、对应侧 arm 和 fresh-target 完整前像推导，不能手工拼接源、工具或目标字段。入口固定来源和工具摘要、目标侧、fresh ownership 及独立工作目录；MySQL 使用计划内明确的客户端配置文件及其摘要；原生 S3 客户端直接读取计划绑定的受控明文配置，不启动 AWS CLI 子进程，也不通过环境变量传递访问密钥。凭据值不得进入计划或公开收据。工具不创建或扫描数据库，源目标均需事先初始化。 参考计划的源对象配置仅从绑定 runtime 的 `api_config_dir`、`api_configuration_sha256` 和 `APP_ENV=test` 推导；目标对象配置从 fresh 请求必需的 `config_dir` 及 `configuration_sha256` 推导。两侧公开配置只包含端点、region 和 `app_env/directory/files/sha256` 文件绑定；私有 `source.s3` 仅保存 `configuration` 文件绑定，不接受内联访问密钥或秘密密钥；源端点和 region 从已核验文件推导，并核对绑定属于实际 API 运行配置。目标配置仍核对 TOML 与 fresh 私有请求的连接字段完全一致，返回前复核配置、runtime 与 arm 文件，任何缺失或漂移均拒绝，不创建或修补配置。参考规模为 system 加十个普通租户、至少十万条实际岗位记录及至少 1 GiB 已登记上传对象，租户分布覆盖共享和独立目标；例如 256 个 4 MiB 对象。岗位记录属于控制库，租户业务表复制另由隔离业务 crate 生成资源验收覆盖。岗位批量写入由 Rust 同进程使用已绑定 MySQL 工具和配置文件执行，SQL 通过 stdin 传递；完整校验受管输入后按固定批次独立提交，共享原 900 秒预算。失败保留输入与安全摘要收据；可能写入时先核对完整前后像，禁止自动重放。先用 `inputs reference --arm-input <side-arm-result> --fresh-target-verify <side-observation-directory/verify.json> --side base|candidate --id <backup-id> --work-dir <new-side-directory>` 预览参考计划，再追加 `--output <side-reference-plan.json> --write` 发布。

数据准备计划的 `dataset.request_interval_ms` 必须为 1000 至 5000 毫秒，限制每个固定客户端的实际 HTTP 请求启动频率；十一个租户可并发准备，每个租户使用自己的身份与地址。`dataset.timeout_seconds` 显式设置整阶段时限（1 至 604800 秒），例如参考规模预留 21600 秒；其他外部命令仍使用 1800 秒超时。收到 429 时保留失败，不通过重试或更换地址绕过限流。数据准备发生在备份与恢复开始之前，其耗时不计入恢复时间。

所有命令从对应干净后端工作树执行；`cargo xtask check recovery` 固定当前 `--backend-dir`，以下基于参考计划的阶段共用 `--plan <plan-json>`。公开入口在连接资源前完成严格参数解析：未知、重复、缺失或跨阶段参数均以参数错误拒绝。计划、输入、备份目录、工作目录和输出都必须位于当前后端 `.local-tests`，不得包含 `..`、经过链接或重解析点，也不能覆盖已有输出。外部数据库、对象存储和工具路径只从已经绑定的参考计划及收据读取，不能另传路径绕过 ownership。Rust `plan` 在完整预览或复核已保存目标计划时核对原备份与停止证明、只读构建比较和已登记的维护构建。备份收据与共享导出必须绑定同一份停止代次文件，包括路径、大小和 SHA-256。这些模式和 `check-dataset`、`check-existing` 均为只读，不接受 `--write`。发布目标计划须同时提供新的 `--output` 和 `--write`，输出父目录须已存在，并位于备份和初始化证据目录之外。两项检查由 Rust 直接核对绑定的数据库身份、ownership 与 API 监听归属；`check-dataset` 另要求源侧无非 system 租户。检查不修改远端资源，但在已有且 owner 匹配的工作目录保留 MySQL 原始输出及失败／有限重试收据；不得删除失败现场后自动重放。`inputs reference|product|bindings` 在 Rust 进程内只读推导并复核完整来源链，默认只在标准输出预览，只有同时给出新的 `--output` 和 `--write` 才发布证据。`dataset`、`backup`、`restore`、`copy`、`damage` 会创建会话、阶段证据或修改明确登记的隔离资源，必须显式传入 `--write`；该授权不放宽账本、前后像、ownership、幂等和未知结果核验。 Rust `dataset` 持有原参考工作目录锁，核对源侧仅有 system 租户，并单次启动当前原生数据准备工具。保留原预检、工具和结果证据。进程树关闭未确认时同时保留原锁，供现场对账。

随后用 `inputs product --reference-plan <side-reference-plan> --backup-receipt <same-backup.json> --comparison-sources <two-version-source-manifest> --arm-input <side-arm-result> --fresh-target-verify <side-observation-directory/verify.json> --side base|candidate --id <restore-id> --fault-at <utc-time>` 预览产品计划，追加 `--output <side-product-plan.json> --write` 发布。工具核验 fresh 登记中的原存储账本和精确状态前缀，并要求 arm 结果与复制清单使用同一有效存储代次。夹具目标冻结服务账本证明的首代或合法重启，历史重读沿用原证明，实际复制、目标核验和 API 交接须复核同一可用代次及实际服务。目标核验在原复制运行锁内先锁定外部存储，再取得目标代次锁，直到发布核验收据后才释放外部存储锁。 `seed_to_arm` 的只读目标权威只接受实际 base/candidate 请求，并要求清单绑定同一初始化工作区的原登记、环境和完整文件谱系；此观察不取得外部存储锁。用 `cargo xtask check recovery fixture successor arm-request --successor <relationship> --source-export-result <shared-export-result> --workspace <fresh-target-workspace> --id <arm-id> --side base|candidate --copy-directory <new-copy-directory>` 预览目标 arm 请求；追加 `--output <new-request.json> --write` 才独占发布。预览和发布都只核对本地证据，核定同一共享导出、目标初始化、当前可用账本代次及目标执行根的维护构建与并发设置。共享导出的原构建桥接按协调工作树核对，目标维护工具仍按实际产品工作树核对。该入口从同一备份、比较来源、arm、fresh 目标和对应侧产品 SHA 推导原生 `RestorePlan`，生成和重读已保存的产品计划时均以原备份的实际采集时间校验 `fault_at`。恰好 24 小时有效，超出 1 微秒即拒绝，故障时间不能在未来。`--output` 与 `--write` 必须同时出现。参考计划的源侧只记录备份所需 API，目标侧另记录 API、Worker 和前端三个端点。 数据库和对象的复制步骤标识按计划顺序由原生工具批量生成，已有账本标识和继续条件保持一致。 SQL 恢复提交的原始字节必须同时匹配备份产物绑定和 Rust 语法核验的摘要，期间变化会在启动 MySQL 命令前拒绝。

对已完成初始化的独立 Windows B1 测量目标，运行上述 `arm-request` 时使用 `--side candidate --independent-b1`，通过 `--workspace` 选择其隔离工作区。`--successor` 和 `--source-export-result` 绑定原比较关系及其唯一共享导出结果。默认只预览。追加 `--output <new-request.json> --write` 后，工具将隔离目标、原共享导出、独立审阅和碰撞投影的绑定写入新请求文件。此命令的写入范围限于该请求文件。

用 `cargo xtask check recovery fixture successor arm-input --request <independent-b1-request.json> --run-dir <new-independent-run-directory> --write` 消费已发布的独立请求。登记目录必须位于当前协调工作树的 `.local-tests` 下，父目录已存在，登记目录与复制路径分离。等原共享导出账本中的进行中阶段收尾后再登记。工具持本地登记锁及原独立目标存储锁，核对同一共享导出、原目标初始化和当前存储代次，发布 `manifest.json`、原账本字节快照 `source-state.json`、`intent.json` 和 `result.json`，并保留未确认状态的失败证据。登记目录已存在时保留原件并拒绝重跑。 登记成功后可[预览并发布独立 B1 参考计划](architecture.md#独立-b1-参考计划)。

- 已经开始复制后业务核验的 Windows 运行发生 API 监督清理事故时，先沿原夹具账本完成 Redis 接续和该事故绑定的目标标记确认。`cargo xtask check recovery clone runtime --run-dir <原运行> --side target --operation restart-api --write` 仅启动 API。独立后继目录继承原二进制和配置，启动前绑定旧停止失败、原运行身份、标记收据及唯一预留 ID。旧角色、业务登记和种子历史仍保留原文件。 若身份核验因第一代后继 API 的监督故障中断，在同一账本的 `restart-api` 命令中加入 `--request <api-restart-request.json>`。请求绑定原已通过的 API 接续阶段结果和身份核验失败收据。控制器只读核验并复用原 Redis 代次和归属标记，随后在原登记端口启动 API。
- 启动结果未知时先核对原阶段和预留。外层控制器遗留运行锁时，用现有 `clone recover` 绑定该阶段的 `controller-NNNN.json` 收口原控制器。随后用 `cargo xtask check recovery clone runtime --run-dir <原运行> --side target --operation reconcile-api --write` 核对原预留的成功结果和实际进程及监听归属。若结果仍未知，保留现场。后继发布后，`status` 查询实际代次。Seed 启动前仍须按原顺序完成准备和后继 API 的受管关闭，核对后继监督树及原角色保留证据。 第二代启动结果未知时，在 `reconcile-api` 命令中传入同一 `--request` 文件，核对原启动意图及结果。
- 原部门规划在会话初始化时失败并已完成零写入回收的，继续执行原运行的 `departments-plan`。控制器登记已发布后继 API 对应的执行器。部门计划正式通过后，应用、和解和核验复用同一执行器，并核对已发布计划及其生产者证明。各阶段子进程沿用原身份计划和私有配置，在只读数据库检查前后复核同一运行合同及实际 API 创建身份。
- 若该执行器在部门会话初始化时失败，保留原计划及失败、启动和进程收据。已启动的会话先用 `recover-session` 确认零写入。续作可用 `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation departments-plan --request <department-tool-build.json> --write` 单独登记经过验证的冻结部门工具，已发布的 API 后继继续运行。使用第一代 API 后继时，部门核验通过后，首次使用 `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation identities-verify --request <identity-tool-build.json> --write` 单独登记身份核验工具，绑定原身份准备和最新通过的部门后像。两种构建请求都绑定实际控制器二进制、冻结记录和通过的测试结果。原启动和回收收据继续解析原执行器。
- 第二代 API 发布且原身份核验会话和解通过后，用 `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation identities-verify --request <identity-verification-successor-request.json> --write` 在同一运行首次登记后继工具。请求绑定原身份核验工具登记、已通过的会话和解结果和新工具的冻结构建登记。启动前失败时，只有登记未发布、没有启动或生产者证据，且原 `verifying` 账本逐字节一致，才可接续。若后继已启动，须先证明它在执行核验业务前被拒绝授权，再用 `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation recover-session --producer-binding <binding.json> --write` 回收该生产者。回收通过后，保留原控制器、启动和进程收据，确认未获执行授权且原账本逐字节一致，再用 `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation identities-verify --request <identity-verification-recovery-request.json> --write` 单次登记新工具。新请求沿用原工具登记和会话和解结果，绑定新工具的冻结构建登记、原回收结果及旧子入口源码。恢复工具登记已发布而生产者明确未启动时，只有紧接的下一次正式核验可通过 `devex-seed-identity-verification-recovery-retry-request` 接续。此请求沿用恢复核验请求的字段，以 `previous_recovery` 绑定原固定登记，并绑定不同的已冻结工具。控制器保留前次失败、原账本与原登记，在当前阶段目录发布新登记。启动或执行结果不明时保留证据、核对原操作，禁止重放。
- `departments-verify` 为原件加载、登记、配置、API 绑定和首次存储布局等前置检查返回固定的失败类别。按阶段和可公开的系统错误码核对原始证据，保留已确认的部门应用收据。
- 若已登记的部门修正工具在首次规划的认证前因 Tokio 就绪探针失败，保留原启动与进程收据、标准错误、注销错误及正式失败记录。确认同一生产者已完成零写入回收，且没有认证或部门意图后，才可用同一 `departments-plan --request` 命令登记独立验证的探针修正构建。该登记继续使用同一 API 后继，原两代工具及各自的运行证据继续参与历史核对。

### 指标与告警

- API 与 Worker 的备份采集器每 60 秒读取控制库汇总，整次采集最多等待 10 秒，输出到现有 Prometheus 指标接口。运行时监控页显示采集状态、必需及异常资源、最近恢复结果与耗时；未知、失败和陈旧状态不表示当前数据可用，保留的有效快照仅供诊断。备份故障独立展示和告警，不改变 API readiness。 `ryframe_backup_last_success_timestamp_seconds` 取所有必需目标的最旧有效备份采集时间，重新登记旧备份不会刷新恢复点。`ryframe_backup_resources` 使用固定的 required/missing/expired/invalid 维度，`ryframe_backup_collector_up` 表示采集成功与否，`ryframe_backup_collector_last_success_timestamp_seconds` 记录最近成功读取汇总的时间；后者缺失或超过 150 秒会触发采集告警，不能用它替代备份恢复点。恢复指标包括最新完成结果、耗时、恢复点年龄和 running/overdue 汇总。指标没有租户、端点或对象键标签。
- `deploy/prometheus/ryframe-alerts.yml` 在 23 小时预警、24 小时告警，并分别检查缺失、过期、校验失败和采集失败。收到恢复失败或超时告警时先查看登记状态和保留的演练证据，不通过改登记时间消除告警。 将该规则文件只读挂载或复制到现有 Prometheus 的 `/etc/prometheus/rules/ryframe-alerts.yml`，在其配置中显式加载这个文件。下例中的两个 HTTPS 地址应替换为现有监控入口，分别转发到 API 的 `/api/v1/monitor/metrics` 和 Worker 健康端口的 `/metrics`；生产 Compose 中的 Worker 默认只在后端网络可见，需要由现有监控网络或反向代理提供访问。密钥文件只保存与 RyFrame 明文配置 `monitor.metrics_bearer_token` 相同的 token 内容；这是 Prometheus 自身的凭据文件读取，路径以 Prometheus 所在主机或容器为准。

完整抓取与规则加载配置见 [Prometheus 配置示例](../deploy/prometheus/prometheus.example.yml)。
沿用现有 `alerting.alertmanagers` 配置，并将 `service=ryframe` 的 warning/critical 告警路由到运维通知渠道。先执行 `promtool check config /etc/prometheus/prometheus.yml` 与 `promtool check rules /etc/prometheus/rules/ryframe-alerts.yml`，通过后按现有平台的配置重载方式生效；Prometheus 支持 `SIGHUP`，也支持在启用生命周期接口后通过 `POST /-/reload` 重载。[配置与重载方式](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)

重载后在 Targets 中确认两个抓取目标均为 UP，在 Rules 中确认 `ryframe.application` 规则组加载且健康，并查询 `ryframe_backup_collector_up`、`ryframe_backup_resources` 和 `ryframe_backup_last_success_timestamp_seconds` 检查实际采集结果。API 与 Worker 各暴露一份部署汇总，按 Prometheus 的 `job`、`instance` 区分采集进程，不能将两份计数相加。最后通过隔离演练产生真实失败状态，核对告警进入 Alertmanager 并送达通知渠道；仅通过配置检查不作为通知送达证据。正式恢复的隔离演练统一使用 `cargo xtask check recovery monitoring`：先创建只含权限已收紧 `metrics-token.txt` 的新 run 目录，以 `bind --help` 核对参数，再用 `bind ... --write` 绑定同一次正式恢复的 `runtime.json`、目标计划、唯一 run ID、Prometheus/promtool 3.5.0、Alertmanager/amtool 0.34.0、四个工具绝对路径及三个互异的非特权回环端口，生成不可覆盖的 `binding.json` 和当前干净提交的不可变 staging；token 必须与运行中的 API、Worker 指标凭据一致，内容不得进入命令行或收据。Rust xtask 在监控进程启动前复核目标计划与存活的运行代次，并执行监控绑定、输入 staging、回环 HTTP、webhook、Prometheus/Alertmanager 进程树管理、观测和关闭。`status` 与 `result` 原生读取阶段证据。`bind|start|observe|close` 通过同一 Rust xtask 的固定标准输入协议，复核冻结导出、备份库存以及同一登记下三端的存活代次。绑定同时记录当前 xtask 可执行文件摘要；阶段执行期间保留凭据、工具、规则和协调程序的文件句柄，并在结束时复核身份与摘要。Windows 凭据要求受保护的显式 DACL，仅允许当前用户、System 和 Administrators。当前用户的显式允许项合计必须包含 `FILE_READ_DATA` 和 `SYNCHRONIZE`。标准 Read 权限包含两项，仅授予 `RC,RD` 无法打开 ACL 核验所需的同步句柄。Unix 要求当前用户拥有且其他用户无访问权限。Windows 权限读取由同一维护工具的短生命周期 Rust 子进程完成，使用系统 `whoami.exe` 获取数值 SID，再通过以 `READ_CONTROL | SYNCHRONIZE` 打开的句柄直接读取 owner/DACL。整个调用最多运行 10 秒，超时回收完整进程树。MySQL 临时凭据仅在新建空目录通过系统 `icacls.exe` 收紧权限并完整后验后写入密码。无需 PowerShell 或额外配置；权限无法核验时失败关闭，不自动放宽。后续只对该绑定依次执行只读的 `status --binding <absolute-path>`，以及显式写入的 `start|observe|close|result --binding <absolute-path> --write`，每次只执行 `status` 返回的 `next_action`，失败、中断、未知发布结果或 `*-failure.json` 必须保留并转入其指示的关闭或人工核对，禁止删除证据后重放。start 管理回环 webhook、Alertmanager、Prometheus 三棵进程树；observe 核对 API/Worker bearer 拒绝与成功响应、targets、固定规则、精确 firing/resolved probe 及 promtool 23/24 小时边界，receiver 只允许 `ryframe-local-webhook` 且外部联系数必须为零；close 等待全部后代退出和端口释放；result 只在 start、observation、close 均成功后排他发布并重验全部摘要，遗留 pending 时先核对文件身份和内容，不能用重跑猜测结果。

日常 CI 与协调版本的发布故障见[发布门禁排障](architecture.md#发布门禁排障)。

## TLS 证书

检查到期时间、主机名、完整链和私钥权限。轮换后验证 MySQL、Redis、对象存储、OTLP 与 Nginx；不要关闭证书校验作为长期修复。

全栈 Extended CI 的 core 与业务 crate 任务使用 Rust 和前端构建工具。全栈 API 控制器非零退出时，外层 CI 日志会显示通过核验的固定拒绝原因或监督准备阶段。候选发布失败时显示对应准备阶段。原监督子进程在候选登记前退出时，日志可显示其真实退出码或信号。按阶段核对原控制收据和诊断产物。遇到超时、取消或无法辨认的响应时，仍按原收据核对未知结果。在原始检出中先记录双仓来源，再生成业务夹具；随后由 `cargo xtask check ci full-stack-config` 读取 `config/ci-full-stack.toml` 与业务根公共 `config/app.toml`，选择并在发布期间持有回环 Worker 健康端口，校验配置后发布 `.local-tests/full-stack-config/` 和既有格式 `.local-tests/full-stack-control.json`，不启动服务。`--source-backend`、`--source-frontend` 指向原始干净检出；运行目录必须仅含经原验证器复核的 `source-pair.json`，运行身份、提交、容器及目录通过显式操作参数绑定，不能拿生成业务根替代原来源。`--plan` 只打印同一任务图，不读应用模板、核验 Git、绑定端口或落盘；Cargo 启动构建边界不变。实际准备需 `--write`；已有输出、链接或未知内容拒绝，完整配置校验失败保留局部文件且不发布 control，不覆盖或自动重放。参数以[扩展工作流](../.github/workflows/extended-ci.yml)和 CLI 帮助为准。全栈 prepare 使用这两份已冻结 TOML 绑定非本地对象存储。探测前核对文件字节数和摘要，逐桶创建后执行 HEAD 确认。配置漂移或远端结果未知时保留阶段收据，由操作者核对现场。启动时 Rust xtask 用本次运行目录的 config 和 worker-config 核验已登记的源码与构建产物；仅在 runtime.json 和 runtime-evidence.json 均缺失时首次登记。两份收据均存在时，完整核验并确认原收据绑定同一对配置目录；部分收据、链接、非普通文件或读取错误均保留现场并拒绝继续。Rust 监督器最多用 120 秒登记启动候选，再用 180 秒等待 API 就绪；外层控制预算为 300 秒。只有就绪探针和监听均属于同一已登记进程后才启动 Worker。只有本次 API 启动已确认、后续观察或 Worker 启动失败时才自动回收。API 启动未确认时保留现场，核对原启动收据后显式执行 collect。收尾仅停止有完整归属的 API 进程树，未知控制锁和孤立成员收据保留。收尾始终采集诊断，并按绑定配置独立检查 API 端口释放，最多 5 秒。无法从绑定配置确定端口时，记录配置问题并使收尾失败。API 日志按操作编号保存。正式 CI integration 的 `business_initialization_mysql` 测试目标显式组合 `bin-api,bin-migrate` 并保留 `--no-default-features`，以运行已有副本监督器用例；这不改变产品 migrate 的构建能力。该用例复用 `.local-tests/mysql/config` 的完整文件配置，要求回环 MySQL 地址并保留 TLS 校验，通过同一实例上的两个归属 schema 和本地代理验证准入、摘除、回退、恢复及业务结构漂移拒绝，不代表已验收真实主从复制部署。配置目录缺失导致的跳过不能作为验收。Redis 一般协议、Redis TLS、S3 HTTPS 和 OTLP HTTPS 真实测试分别使用后端根目录下 `.local-tests/service-tests/{redis,redis-tls,s3-https,otlp-https}/config` 中的显式 `AppConfig` 测试配置。公共 `app.toml` 可缺省，`app.test.toml` 必须存在；仅目录缺失会明确跳过并标记真实链路未验收，已有目录缺文件、配置非法、无权限或任何路径层级含链接/重解析点均失败。Redis 必须配置 `mode="required"`，TLS 角色还须 `tls=true`；连接、密码、DB、池和超时来自文件。每次测试在独占运行目录派生 scope cache 两项生命周期原语保留独立进程的整次 180 秒边界和原 4 MiB 私有输入输出。原语超时或输出超限时只回收该确切进程。若仍缺少监督器和 Redis 退出证明，保留现场与 unknown，按原账本显式核对。 API/Worker 候选准备最多 120 秒，覆盖完整来源核验、监督器登记和授权等待；候选或授权文件已存在也须检查原单调期限，授权写入后超时仍保留收据并显式核对，不自动重放。产品启动后的业务就绪仍为 60 秒，外层交接仍最多 300 秒；最终恢复 RPO/RTO 门槛不变。 API/Worker monitor 在原操作锁内仅追加 `preparation-failed.json` 准备失败旁证，区分 runtime/input、请求合同、成员创建、成员身份及 ready 发布阶段；只记录固定原因、可取得的底层 IO 系统码和原因摘要，不记录原始错误或私有配置。父授权仅在已登记 monitor 退出后，核对同一 role、operation ID、source、owner/request 摘要及此前实际 monitor 创建身份，才显示固定处理建议；旁证缺失、损坏或绑定不符仍返回原候选前退出失败。未取得可信原操作绑定、实际 monitor 身份或旁证发布失败时不补签，保留原失败及现场；旁证不证明就绪或停止，不授权重试。 Linux 全栈监控通过同一 pidfd 采集成员身份并核对退出。采样读取成员的 `/proc/<pid>/exe` 返回 `ENOENT` 且同一 pidfd 尚未证明退出时，最多等待该句柄 20 毫秒。只在该句柄确认退出后跳过本次成员观测，到期则保留原始 `ENOENT`。若活动启动锁仍可核验，成员观测失败记录为 member_observation；已确认退出的成员身份保留在整组关闭收据中。控制器核对整组关闭证明时，先校验原 monitor 的创建身份，再用同一 pidfd 确认它退出。 API、Worker 与 frontend 共用的角色原子收据发布支持 Windows 长路径：仅文件系统操作分别解析暂存目录与目标父目录，保留原生长路径前缀；JSON 与 portable 路径事实不变。控制收据仍在 runtime 根目录暂存、发布到原 control.lock；保持写入同步、原子替换和禁止覆盖发布。持久化失败保留底层 IO 类型与系统码供既有脱敏诊断使用，并清理本次暂存文件；不删除未知目标，不重放操作。 结果收取与来源、身份及归档核验共用本次控制器300秒绝对预算，不在循环中续时。收到“后台启动结果未知”时保留原owner/request/result，先用正式fixture runtime status只读核验；角色锁的显式reconcile使用既有角色控制协议，公共fixture runtime没有reconcile子命令。不得重放start或把晚到成功收据改判为原公共启动通过。 已发布执行来源在同一个四根前后窗口内复核实际产物和运行收据。角色监督进门复用本次已核验的运行值，进度收据只复核原操作、授权、配置及来源收据；产品启动前、接受就绪后和控制器收尾仍执行完整来源核验。

Windows 本地夹具在首次审阅前，通过工具配置的 `[verification.windows_redis]` 绑定绝对 `redis-server.exe` 路径、SHA-256 及全部同目录依赖 DLL。原生 v3 启动、观察与关闭使用 Windows 进程创建身份、监督 Job、独占回环端口和同一认证连接；正常关闭须有原 Job 清空及精确进程退出证明。未就绪、超时或未知结果保留原收据，按同一账本显式核对。首次 RustFS、Redis 和五桶初始化在正式恢复演练内连续执行，后续阶段沿用已登记的隔离资源。现行生命周期使用已登记的 Windows 工具和运行代次。旧 Redis 收据仅用于只读历史核对，保留原始文件、摘要与前后关系。认证就绪、进程身份、监督树及对外 ready 必须绑定同一代次。按实际阶段核对超时或失败，保留原收据及尚未确认的进程状态。停止失败后只读核对原退出证据。 Windows Redis v3 的原 Job 退出记录为非零退出码，且 Redis 与 RustFS 的原退出证明都早于一次失败的服务关闭时，先检查 `services status`。仅当返回 `reconcile`，才用 `cargo xtask check recovery fixture services reconcile --review <review-receipt> --environment <bootstrap.json> --owner-binding <state.json> --write` 接续，其中 owner 使用状态返回的当前原文件。工具核对原关闭阶段未发布停止结果、原 Redis 进程及 Job 完整退出和 RustFS 已停止的完整成员，并复核三处端口。和解记录保留原退出码与证明，两个服务均不再接收停止请求。和解成功后，按状态返回的 `restart` 在同一账本追加新代次。 若 Windows 重启前的同一登记代次留有 Redis 已接受但 Job 清理未确认的失败收据，以及 RustFS 资源不足（1450）的监督和成员关闭失败收据，先查看 status。只有工具确认原身份早于内核启动刻度、原进程不再运行、三个登记端口空闲、全部原证据和资源绑定一致并给出 recover 后，才用返回的当前 owner 追加事故核对；原失败收据保留，仍无正常关闭证明。按新状态执行 restart 后复用原资源；第三次重启用于原复制的 Redis 标记恢复时，必须有这条直接前驱，且其他代次无写入意图。完整空前像才允许一次原子写入，失联只核对原意图。不会据此认定正式恢复完成或重新初始化数据库和对象桶。 Windows 来源夹具的 RustFS 原整树已关闭且复制仍绑定原对象存储时，可在原 `source_to_seed` 运行用 `cargo xtask check recovery clone storage --run-dir <原运行> --side source --operation restart --request <原绑定请求> --write` 单独启动来源 RustFS。原请求、夹具审阅、已通过的服务代次、完整成员停止、配置摘要和数据目录必须一致；Windows 以不继承调用端句柄的短时控制器执行启动，由控制器通过受管文件回传结果，并记录新内核身份和核验后的独占监听。若无法确认控制器结果，保留原票据和阶段收据，按实际进程身份与端口状态核对后接续。该步骤不启动 Redis、不重做对象桶或数据库初始化；原复制仍须按原导出核对来源对象。

死亡控制器通过同一入口的 `recover --review <review-receipt> --environment <bootstrap.json> --owner-binding <owner-file-binding-json-from-status> --write` 显式恢复。它只清理已核对的本地控制锁并追加账本，不停止服务或重放未收尾操作；PID 已复用、来源改变、未知启动或关闭结果均须保留现场核对完整前后像。已关闭代次不能再签发 fresh-target 请求；已登记目标只接受严格核验过的已收尾生命周期追加。隔离参考夹具的 Redis 禁用持久化。服务重启后须另行核对已初始化目标的完整前像。若 owner 或 sentinel 已丢失，保留原初始化和失败证据，按服务状态判断是否满足下述显式接续和标记恢复条件。其余场景仍按原流程关闭服务树并新建隔离目标。

当原 RustFS 仍以登记身份运行且 `status` 返回 `restart-redis` 时，使用该结果中的当前账本路径显式接续 Windows Redis。原 Job 完整关闭的场景使用退出与清理收据。同一次 Windows 启动期间发生清理未确认事故时，工具绑定原启动和失败收据，在原端口实际确认可绑定前后各查一次原 Redis 和监督器的进程身份，均须确认退出。历史记录保留该事故及其关闭证明的实际状态。
```text
cargo xtask check recovery fixture services restart-redis --review <review-receipt> --environment <bootstrap.json> --owner-binding <state.json> --write
```

每次接续只创建一个 Redis 后继。原 RustFS 进程、数据目录、数据库和对象数据继续沿用。随后用原复制账本的 `target-cache-markers` 核对此前已确认的标记结果及新代的完整初始像。已完成复制并登记复制后准备时，接续须核对原复制完成收据和此前确认的标记链。准备失败的场景须确认运行配置未发布、产品从未启动。准备通过而 API 尚未启动的，接续须有启动前拒绝的结果，API 与 Worker 原端口均已关闭且现场不存在启动意图或进程记录，同时保留原失败准备的回收证据、运行配置、二进制及交接收据。复制后业务中的 Windows API 监督清理事故，须以失败的部门规划、已关闭的原生产者、原 API 失败收据和此前的标记链绑定同一次接续。原 API 与 Worker 端口均须关闭。若历史 PID 仍可打开，工具使用同一 Windows 进程句柄核对创建、退出刻度及退出状态，同代进程还须吻合原映像。仅在新代的两个标记和受管 namespace 均为空时执行原子写入。写入结果未知时，用 `target-cache-markers` 的 `reconcile` 模式读取确认。

记录时间线、影响租户、请求或任务 ID、根因、处置和验证结果。配置字段以配置结构为准，指标和告警以部署资产为准，不在本文维护重复清单。

监控绑定中的 `environment` 保留为正式启动私有配置文件的描述符，文件内容必须直接写明文 `metrics_bearer_token`、`scope_id`、`api_config_dir` 和 `worker_config_dir`，例如：
```json
{
  "metrics_bearer_token": "<plaintext metrics token matching the running API and Worker>",
  "scope_id": "<scope of this formal recovery>",
  "api_config_dir": "D:/workspace/backend/.local-tests/restore/api-config",
  "worker_config_dir": "D:/workspace/backend/.local-tests/restore/worker-config"
}
```

该文件只接受这四个字符串字段；旧环境变量键、旧 `environment` 包装、额外字段、非字符串、scope 或令牌不匹配均被拒绝，不读取父进程环境作为回退。文件路径、摘要和内容持续绑定原正式启动来源，不能仅为监控另建或替换该文件。Prometheus 继续通过受保护的 `metrics-token.txt` 和 `credentials_file` 读取同一令牌；scope、角色及运行路径通过固定参数或 supervisor 标准输入协议传递。所有监控子进程清空项目与凭据环境，仅白名单保留操作系统变量和固定的回环代理设置；预检 stdin 的受管文件位于后端 `.local-tests`，退出后自动删除，预检错误不透传子进程原始诊断。 API 与 Worker 各自通过 `--config-dir` 接收绝对配置目录，并使用 `APP_ENV=test` 选择必需的 `app.test.toml`；可选公共 `app.toml` 先加载。文件中的 scope、指标令牌必须与私有文档一致，API、Worker 端点必须匹配登记值，任务模式必须为 external；两侧 `snowflake_worker_id` 必须有效且互不相同。启动收据绑定目录路径和配置文件摘要，不复制凭据；后续文件修改、增加或删除均导致核验失败。恢复运行子进程只继承必要 OS 变量，后端角色另显式设置 `APP_ENV`。启动控制器通过绑定描述向原生监督器交接，监督器复核原启动 owner、角色操作 ID 与已写代次。旧环境控制请求与按角色覆盖的项目环境字段均不再读取。 恢复生命周期的代次状态、首次目录 intent 和启动收据由绑定 Rust 工具处理；首次 intent 或成功收据已存在、文件集合异常或冻结前像不符时保留现场，先通过现有 status/recover 核对，不覆盖结果或自动重放。
