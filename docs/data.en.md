# Data

## Initializing a New Environment

Create an isolated empty MySQL database, select `dev`, `test`, or `prod` through `APP_ENV`, and prepare plaintext database passwords, JWT and `[bootstrap] admin_password` as described in [README: First run after downloading](../README.en.md#first-run-after-downloading). `config/app.toml` is optional; the selected `config/app.<environment>.toml` must exist and supply every required setting when the common file is omitted. Application-relative paths resolve from the current working directory. Default single tenancy still has separate control and `shared-control` ledgers. Follow the README sequence to initialize and verify both before starting the backend. When using the external configuration directory from the README, add `--config-dir ../ryframe-dev-config` after `--` to this guide's aliases that otherwise use default `config`, for example `cargo migrate -- --config-dir ../ryframe-dev-config control verify` or `cargo serve -- --config-dir ../ryframe-dev-config`. Keep the same directory for verification, export and runtime commands to avoid connecting through a different, uninitialized configuration.

Failures from `cargo migrate` go to stderr with the actual phase, selected configuration files, configuration keys, and a redacted cause; successful output keeps its existing contract. Connection or configuration failures precede migration execution. After entering `up` or `adopt --apply`, DDL or ledger changes may be partially committed; this does not imply an overall rollback. Preserve the evidence, fix the cause, and use the same `--config-dir` and `APP_ENV` for `status` and `verify` before deciding on writes; never replay automatically. Export failures also require checking any created directories, temporary files, or final file. Independent MySQL targets retain redacted connection, health, and schema causes for internal diagnostics; public API responses exclude these causes, and unavailability without an underlying error does not establish an authentication error. For tenant-data access returning 503, correlate `request_id` with the service log category `tenant_data_error` to distinguish projection versions, targets, placement, and connection budgets. Logs retain only safe causes and do not trigger automatic write replay. Generated business persistence reuses the same conversion entry, and projection locking within transactions also reports missing or stale versions. Every suggested command explicitly includes a directory placeholder for `--config-dir`. Replace it with the parent directory of the displayed configuration files and quote it for the current shell; double any single quote inside a PowerShell single-quoted path. Do not execute the placeholder or omit the directory and inspect a different default database.

The migration path uses `control up` to create or upgrade the control database; a new empty physical database may instead use the complete SQL initialization below. `control verify` only validates the ledger, structure, and compile-time business catalog; it cannot replace initialization on a new empty database. First-time initialization requires `[bootstrap] admin_password` in configuration. The API and Worker only validate at startup and do not execute DDL. Non-production configurations default to `jobs.mode="embedded"`, so `cargo serve` already consumes background tasks. To validate separate processes, follow the [development guide](development.en.md#starting-the-backend) to create private API and Worker configurations, both using `jobs.mode="external"`, with different instance IDs and explicitly selected configuration directories. For every MySQL tenant target, first create an empty database, register its configuration, and run `tenant-data up/verify` separately. If the first `up` reports an unknown ownership commit result, preserve the database state and run read-only `status` and `verify` using the same configuration. From a separate connection, confirm the physical database and the corresponding `scope_id` and marker in `ryframe_resource_ownership` before running `up` again.

## Control Database Initialization SQL

- Preview: `cargo migrate -- control export-sql --output .local-tests/control-init.sql --plan`
- Export: `cargo migrate -- control export-sql --output .local-tests/control-init.sql --write`

`control export-sql --plan` reads no passwords, application configuration or database and writes no files. Actual export with `--write` creates the artifact's parent directory as needed and loads file configuration selected by `APP_ENV` and `--config-dir <directory>` and reads `[bootstrap] admin_password` to generate hashes, without connecting to a database. The formal `control export-sql` derives control and tenant-data ownership from the selected configuration's `scope_id` and covers the control plane and `shared-control` tenant data plane in the same physical database: control structures, post-creation constraints, system data, fence/slot/projection tables and initial rows, both framework migration ledgers, and registered Control and Tenant business initialization migrations with one business ledger, without plaintext passwords. Handwritten business migrations must provide schema and initialization SQL from the same source as `up`. The export contains password hashes and must be protected as credential material; the output must be a new file and cannot overwrite an existing one. Select an empty database and configure the client to stop on errors; do not use `--force`. The following example connects to a local database. Client host, port, user and database must match the selected configuration; for remote production connections, explicitly enable hostname verification with the matching CA instead of relying on client TLS defaults. In PowerShell, use:

- `mysql --default-character-set=utf8mb4 -h 127.0.0.1 -P 3306 -u ryframe_app -p ryframe_dev --execute="source .local-tests/control-init.sql"`

bash can use `< .local-tests/control-init.sql`. PowerShell does not support this redirection, so do not use the bash command unchanged in PowerShell. After importing, run:

- Verify the control plane: `cargo migrate -- control verify`
- Verify the tenant data plane: `cargo migrate -- tenant-data verify --target shared-control`

After successful import, run both verifications above directly without an additional `up`. Independent MySQL tenant targets are outside this physical-database export and still use their own `tenant-data up/verify`. `sql/ryframe_config.sql` is a review snapshot containing placeholder hashes and no ledger; it cannot be deployed. After an interrupted import, do not guess how to complete it by repeating `up` or automatically delete objects. Confirm their purpose, then create another isolated database. MySQL DDL cannot rely on an outer transaction to roll back the entire operation. Imports run actual metadata assertions before and after each migration, covering column order, defaults, collations, indexes, foreign keys, and `CHECK` expressions and `enforced`; only successful verification permits its business ledger entry. Final verification rechecks framework and business structures and ownership/ledgers, then records both framework completion markers in a transaction holding metadata locks. Ownership is registered only after all applicable initialization and final verification succeed. A previous initialization success or historical HTTP 200 does not establish current ownership acceptance. Previously completed migrations and DDL may remain after failure. Inspect the reported migration, phase, category and actual state before taking action; do not replay automatically.

## Data Boundaries and Migrations

Business model date fields use MySQL `DATE` to store a calendar day. Nullable columns retain SQL `NULL`. An existing date with a valid month and day, such as `0001-01-02`, is read back with its original year. The control database stores identity, authorization, products, the tenant directory, tasks, file metadata, and placement. By default, control database business data without `tenant_id` is accessible only to the system tenant. Tenant business data is routed through placement to `shared-control`, a shared business target, or a dedicated tenant target. The control database and tenant data plane use different ledgers. The compile-time catalog records tables, columns, cursors, and schemas. Startup, `verify`, and the generator fail closed when they find missing items, drift, unknown ledgers, or ownership conflicts; they do not automatically create tables or rewrite authorization. `shared-control` verification excludes only business tables formally registered as control tables by the composition root; `control verify` still validates their structure. They do not enter the tenant copy catalog or the dedicated MySQL target allowlist. Unknown or missing business tables are listed by name. If verification fails after `tenant-data up` has completed DDL, preserve the database and use read-only `control verify` and `tenant-data verify` to check ownership and ledgers; do not delete the database or automatically replay migrations.

The current `0.x` versions support only new isolated databases. Old structures or invalid capability codes are not converted automatically. After `v1.0.0`, frozen migrations permit only additions and roll-forward. Migration accounts need access to business table metadata. DDL may commit implicitly, and ledger transactions do not guarantee rollback of the entire migration. If validation fails after execution, preserve the state; do not assume rollback or replay automatically. Common checks are:

- Control database: `cargo migrate -- control status`, then `cargo migrate -- control verify`
- Registered tenant targets: `cargo migrate -- tenant-data status --all`, then `cargo migrate -- tenant-data verify --all`

Framework maintainers can use `cargo xtask data migrate check` to validate the migration catalog, registration order, generated migration wiring, and digests in `catalog/migrations.lock.toml` without writing. Use `cargo xtask data migrate check --require-frozen` for pre-commit checks. Explicit baseline consolidation in a development version uses `cargo xtask data migrate baseline --write`. Stable versions freeze only new migrations in the current working tree, using `cargo xtask data migrate freeze`. `cargo xtask data migrate reconcile --write` selects baseline or freeze according to the current version phase, and the full-stack fixture reuses it. These commands do not connect to or modify databases. The control database migration for notice versions initializes `revision = 1` for existing notices and preserves their content. New notices also start at version `1`.

## Adopting Existing Tables

Existing tables require explicit adoption. If unregistered business tables are added to an initialized control database, startup rejection of unknown tables is expected. Preserve the tables and data; generating models and immediately running `serve` does not establish adoption. Stop producers including API/Worker, prepare registered modules with matching models and migrations, and use a current migration binary containing that registration. Adoption prechecks read-only verify the control framework ledger, complete physical schema and target boundary, without requiring new business permissions/menus to be seeded first. The adoption plan still checks business schema, physical identity, source digests and other ledger constraints at each operation. Saving a preview and inspecting do not write the database; apply registers only verified adopted ledger metadata without historical business DDL or business-row changes. Inspect the original plan after application. When new access entries or reviewed subsequent migrations are needed, explicitly run `up` for the corresponding scope, followed by full verification. The new-module example below uses `control up` to initialize access entries before verification; API/Worker startup still requires complete business permissions and menus, with no relaxed startup path:

```powershell
cargo migrate -- control adopt --module order --output .local-tests/order-adopt.json --write
cargo migrate -- control adopt --inspect .local-tests/order-adopt.json
cargo migrate -- control adopt --apply .local-tests/order-adopt.json --write
cargo migrate -- control adopt --inspect .local-tests/order-adopt.json
```

For tenant tables, adoption and inspection use `tenant-data adopt` with one explicit `--target business-shared`; `--all` is not accepted. Subsequent `tenant-data up`, `verify`, and `status` may select one `--target` or explicitly use `--all` for every registered target. Business permissions/menus still require `control up` and `control verify` on the control database; migrating only the tenant target does not replace that step. `--output` must be used with `--write`, while `--inspect` prohibits writes. Plans may use only new paths within `.local-tests`. Saving the plan creates the artifact's parent directory. Keep ordinary development configuration in a private directory outside the working tree. `adopt --plan` does not read application configuration, connect to databases, or write; it differs from `adopt --output ... --write`, which reads actual structure and saves an adoption plan. Adoption only registers the existing structure; it does not execute historical DDL or change business rows. For partial registration, structural drift, or unknown outcomes, inspect the original plan first rather than replaying with a different plan. When the target is empty, create tables through normal `up` execution.

Authorization, task claiming, export requests, deletion acceptance, and configuration transfers use the primary database and explicit transactions. Eventual consistency is used only for list reads that can tolerate stale data; pre-execution validation, downloads, and state transitions use strong consistency. Tenant data scope is driven by `sys_tenant.data_scope_version`: a control database transaction writes to the outbox, and the Worker publishes and atomically switches the projection at the active placement target. If the authenticated principal's version is behind or the projection is unavailable, the operation fails closed. User creation, updates, deletion, and import batches that actually insert users advance the tenant authorization epoch in the same transaction that records the data-scope change, writing the existing mirror outbox when caching is enabled. After commit, the tenant authorization cache is synchronized to invalidate old snapshots for other subjects and rebuild them on the next request. Updates and deletion still advance authorization versions for target users and reject old tokens; import batches without inserts and rolled-back transactions do not advance the epoch. Mirror synchronization failures after commit follow the existing cache policy; committed writes are not replayed, and the persistent outbox provides recovery.

A data migration advances the data-scope version and records the outbox in the same control transaction that saves the new target and generation during cutover; retries do not advance it again. Placement remains in maintenance. After the migration enters activating, it first activates the exactly matching target fence, then publishes the projection directly to the approved target using a consistent identity and organization snapshot from the control database. The target transaction verifies projection metadata together with digests and counts of the actual Owner and department rows. Placement becomes active only after the control database confirms that the current data-scope version and original placement/fence identity remain unchanged. Actual activation still advances the runtime and authorization epochs, records the mirror outbox according to the existing cache policy, and synchronizes the new authorization epoch and publishes a context-change notification after commit. It no longer advances the data-scope version at that point, keeping the verified projection valid. Publication failure or version/identity drift leaves the migration in maintenance/activating. An existing publication with the same version and fence can continue idempotently after revalidation; a higher projection version or mismatched contents in the same generation cannot be accepted as success. When migrating back to a previous target, a valid older-generation projection can be rebuilt from the current snapshot after the migration, lease, and target fence match exactly; future generations, a wrong token in the same generation, or invalid prior identity are rejected. If the target commit outcome is unknown, or the target committed but the control database did not, a subsequent retry reads and revalidates the published projection without assuming that target writes were rolled back. Ordinary outbox publication still requires active placement and does not add a control-database fallback. Repeated succeeded calls and rollback do not advance epochs again; an activating migration with placement outside maintenance is rejected; maintenance and cutover retain their existing runtime-epoch, fence, and lease constraints. There is no distributed transaction between the two databases, and the control database cannot roll back writes that have already entered the tenant database concurrently.

## Backup, Recovery, and Retention

Stop the API, Worker, scheduler, and message producers before a formal backup. The inventory uses `--quiesced-at` to indicate that the external system has been quiesced. `--observed-at` records only the start of observation and does not establish eligibility for a formal backup. Backup registration validates file sizes and SHA-256. Recovery data validation compares the current schema, complete table digests, placement, ownership, and object manifests; resources and registration metadata are excluded from business digests. An isolated recovery must use a new scope, databases, and object prefix while retaining target ownership. Success is registered only after data validation, API/Worker readiness, and real business proof pass. The reference objectives are a 24-hour recovery point and a 60-minute RTO; actual results cannot be inferred from a plan or a single inventory. The following inventory commands record backup and recovery evidence. Pass absolute paths to new files in the `.local-tests` subdirectory already prepared for the drill. For detailed recovery commands, see the [Operations Guide](operations.en.md#failed-or-expired-backups). When inventory table sets differ, retain each raw target inventory, the complete table list, ownership queries and original failure receipts; check the product catalog and tool provenance without filtering unknown tables. In the product's raw inventory, `biz_data_scope_owner`, `biz_data_scope_dept` and `biz_data_scope_projection` are preserved metadata. Copy observations still record their row counts and digests through the existing tenant business catalog; they must not be omitted. Successful migration `up` receipts must include `ownership=verified`; `verify` continues to use `migration_ledger=current schema=verified`. If rebuild and all migrations completed and only inventory capture failed, first run `cargo xtask check recovery fresh-target --operation status --workspace <original-workspace>` for the same workspace. Only when existing rules explicitly permit inventory continuation, run `cargo xtask check recovery fresh-target --operation resume-initialize --workspace <original-workspace> --write`. This path captures inventory again while retaining original failure material and never replays rebuild or migrations. Without continuation eligibility, preserve the scene and do not manufacture receipts.

```powershell
cargo xtask data backup inventory --output <absolute-new-inventory-file> --source-sha <40-character-sha> --quiesced-at <RFC3339>
cargo xtask data target inventory --target <target-key> --output <absolute-new-target-inventory-file>
```

For development copying, first freeze a plan with `cargo xtask check recovery clone plan --input <manifest> --output <new-plan> --write`, then perform a read-only recheck with `cargo xtask check recovery clone verify --plan <plan>`. Both entry points execute natively in Rust, without starting Python or accessing databases, networks, or shared services. They strictly validate input object fields, the 16 MiB limit, schemas and the business catalog, SQL data dumps, object sizes and SHA-256, tenant placement/fences, task relationships, and deterministic plan hashes. `bridge --build <receipt> --inventory <manifest> --output <new-bridge-file> --write` registers the reuse boundary only after Rust validates the explicit build receipt, complete source snapshot, file set, artifact bytes, build context, and current product inputs. It does not compile, modify old receipts, or establish recovery eligibility; the output must use create-new. `maintenance --operation build --output <new-directory> --write` uses the unified process layer and Cargo offline mode to build the three maintenance CLIs `reset`, `migrate`, and `tenant-data` individually, freezing the binaries, Cargo JSON events, logs, source, toolchain, and target receipts. Failures leave `failed.json` and original logs; successful receipts do not conceal partial writes. `maintenance --operation verify --output <directory-or-build.json>` rechecks frozen receipts, current source, and the toolchain without writing. Rebuilding into an existing output is rejected before Cargo starts. `storage` is also handled by Rust: fixed RustFS requests, data directory identity, original startup and actual process generations, listening ports, service logs, failed and unknown startup receipts, service identity changes, and precise process cleanup are validated at native entry points. `storage status` does not create attempts or evidence files; other operations require explicit `--write`. The successor and previous-tool replacement paths for `cache` have not been fully migrated, so this version continues to use the original state machine and does not retain a partially completed Rust entry point.

Rust runs `init`, read-only `status` and `stage` for both `source_to_seed` and `seed_to_arm`. It checks the run directory, kernel mutual exclusion, controller identity, stage number, provenance and result publication. `stage export` reads the fixed source request, environment, build, runtime and producer receipts. It verifies MySQL and object ownership, migrations, full schemas, inventories before and after export, SQL dumps, object bytes, scheduling relationships and generations. `stage target-verify` checks databases, objects, Redis, initialization history and runtime process identity read-only. `stage copy` holds the same target and ledger locks for initial copy, explicit reconciliation or resume. It checks the original intent and complete before-image before each write and independently observes the after-image. The registered execution backend supplies the target TOML. Evidence is saved in the coordinator backend run directory. Run directories, evidence and outputs live under `.local-tests` for the coordinator backend. The tool rejects duplicate fields, links, out-of-bound paths, overlapping source and target paths, and unregistered resources. Plans, bridges, registration directories and new stage evidence use exclusive creation. Status receipts are published atomically. After an interruption, use read-only `clone status` or `storage status` and complete before/after-images to decide the next action. Use the original ledger for explicit `reconcile`, `resume` or `recover` bound to the creation identity. Reconcile unknown writes first. API, Worker, Redis and storage restarts register configuration, credential references, ports, process identity and data directories separately. After a source-generation start or stop failure, check `source-generation-status` first. Ordinary recovery reclaims only registered processes of the same generation and retains the original evidence. The same bound Rust tool checks frozen source requests, paired build equivalence, complete ordinary-recovery before-images and C69 receipt types read-only. Environment digests and maintenance build logs follow the established normalization rules. Stages that still use a private protocol receive one bounded UTF-8 JSON message on stdin and keep business arguments out of argv and the child environment. Long-running recovery adds no overall timeout. An interruption or exit preserves the evidence for explicit reconciliation. When a Windows host reboot interrupts the original source generation, first run `cargo xtask check recovery clone seed-runtime --run-dir <registered-run> --operation source-generation-reboot-status` read-only against the same run. The tool checks the original failed verification prefix, host boot time, process creation identities and listeners. It records normal Windows Redis exits separately from external termination after reboot. Use `--operation source-generation-reboot-close --request <original-request> --write` with the same command to bind the original request and publish a local receipt in the unique stage immediately after the original START. Build receipt drift is reported separately. Subsequent stages still verify their own build registrations. Closure preserves the original verification qualification and resource data. Preserve the evidence if an orphaned output or an occupied stage is found.

Rust validates migration initialization resume state and successful confirmation without writing resources. The Python controller submits the fixed request, prepare snapshot, and lock state through a private standard-input protocol. Validation binds the continuous migration prefix, complete stage file set, trusted service restart generation, Redis marker rebind, and the single permitted predecessor with a failed read-only operation. Failure preserves the original evidence and does not replay unknown writes. External runtime generation sources continue to use the independent trusted-source validator rather than embedded started values; native evidence is checked again after source validation.

Before reading credentials or starting business operations, native identity, quota, and department producers validate the latest passed seed registration and its original file digest within the same run directory. A failed or unfinished latest registration prevents fallback. Before startup authorization finishes, the fixed manifest, complete stage records, and registration result are checked again. Source drift stops execution and preserves the original evidence. Registration file validation and publication also run in the bound Rust tool. The outer controller retains the original run/target locks while the native entry verifies the current attempt, live controller, target lock identity, latest post-copy generation, and explicitly bound configuration files. An identical registration can be rechecked and reused; conflicting or partial files are never overwritten. A registration written before the outer stage finishes still grants no startup eligibility: preserve the evidence and inspect the stage and locks first. Existing orchestration continues to validate the complete copy history and resource guards for `prepare/start`; successful registration does not replace those checks. Identity producers recheck the fixed post-copy registration, plan, and live controller before execution, at identity publication boundaries, and at completion; quota and department protocols verify the same generation before and after each business operation. Truncated input, duplicate fields, oversized requests, or a broken output channel still close held sessions. Explicit logout does not require later sources to remain valid, and simultaneous business and cleanup failures never produce success.

Rust validates read-only commands, native S3 receipts, owner contents, MySQL output, and the closed guard artifact set for department plan adoption, publishing the manifest with create-new. Unregistered files, source drift, or partial evidence reject adoption and preserve the original state. Identity prerequisites reuse the same Rust ordered ledger projection, checking all 622 writes, 11 roles, and 200 users. Rust also performs read-only validation of the ten-tenant plan, complete department paths in bounded XLSX workbooks, directory and template before/after images, idempotent intents, individual reconciliations, unique confirmations, and identity authorization evidence. The existing stage selector still selects the latest trusted stage. Model requests use digest-bound managed temporary input files, rechecked after processing, without increasing the stdin limit or adding environment inputs. Session cleanup budgets cover ten administrators, ten template sessions, and pacing cleanup, so later source drift does not block logout. Existing locked stages still orchestrate remote department operations and failed-plan adoption; passing evidence validation grants no write, Worker, or recovery authorization.

Export tasks freeze canonical filters, the authorization fingerprint, `snapshot_at`, and `upper_id`. Specified IDs remain subject to tenant and data permissions. Default limits are 500,000 rows, 1000 rows per batch, 1800 seconds, 512 MiB, and two running tasks per tenant. Deletion first writes `delete_pending_at`, then idempotently removes objects and records. A missing object is treated as success; a storage failure retains the tombstone for retry. Each deployment uses a stable, unique `scope_id`, and Redis, objects, and databases all validate ownership. `FLUSHDB`, `KEYS`, broad bucket deletion, and scanning shared servers are prohibited.

## File Configuration and Credentials

`APP_ENV` is the only project configuration environment entry and accepts exactly `dev`, `test`, or `prod`, without case variants or whitespace. Ordinary API, Worker and migration processes default to `dev` when it is unset; reset requires it explicitly. Operational examples always select the environment explicitly. API, Worker, migration and reset read optional common `app.toml` from the directory selected by `--config-dir <directory>`, then recursively merge the mandatory `app.<environment>.toml`. If the common file is genuinely absent, the environment file must supply every required field; an existing malformed, unreadable or dangling-link common file still fails. The default directory is `config`, and relative paths resolve from the current working directory. Production connection, secret strength, TLS, instance ID and resource isolation validation remain in force. Localization uses TOML field `app.locales_dir`, defaulting to `locales`, resolved from the process current working directory for ordinary applications; `APP_LOCALES_DIR` is not read. Missing resources or loading failures fail strictly in production, while development can use an embedded fallback.

Set database, Redis, object storage, JWT, monitoring token and initial administrator credentials directly in their plaintext fields. Keep real configuration only in private directories outside the working tree, excluding it from logs, public receipts and version control. The root `snowflake_worker_id` must differ for each instance in the same deployment; `[bootstrap] admin_password` explicitly supplies the initial administrator password. The initial ordinary user `user`, newly created ordinary users and imported ordinary users still use `123456` and must change it on first login. Arrays are replaced as a whole in environment files: `cors.allow_origins` and `proxy.trusted_cidrs` use TOML string arrays; `database.replicas`, `database.sources` and `tenant_data.targets` use complete TOML table arrays, without patching individual entries. The product's S3-compatible client and default OTLP HTTP client use `object_storage.endpoint` and `telemetry.endpoint` respectively; they ignore `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` and their lowercase forms, and do not automatically use system proxies. Credentials, region and export settings remain file-configured.

The generator's `--config-dir <directory>` and Builder `.configuration_directory(path)` resolve relative paths from the backend Workspace root; running from a business crate's `src` does not change the `workspace/config` default. Priority is explicit CLI/Builder, local `.local-tests/tools.toml`, common `config/tools.toml`, then `workspace/config`; `[generator] config_dir` in tool files is optional. Shared MySQL tests use the fixed backend-root directory `.local-tests/mysql/config`, where common `app.toml` is optional and `app.test.toml` is mandatory. All connection and TLS parameters come from `database.primary`, and Disabled is rejected. A missing directory only skips tests without acceptance; existing invalid or linked paths, a missing environment file and invalid configuration fail. File `scope_id` participates in unique schema names; see [integration verification](development.en.md#integration-verification) for the opt-in and evidence boundaries. Only cases actually run provide evidence for the corresponding service; configuration or gate entry points alone do not establish complete real-service acceptance. Structure checks and CI tool tests for deployment templates and private configuration directories have passed. Real containers, images and the complete flow remain unaccepted; partial tests do not replace a complete gate.

## Tenant Routing

`database.primary` is the control database's sole writable database and the source for strongly consistent reads and `shared-control`. `database.replicas` contains read-only replicas of that same control database. `database.sources` contains named MySQL sources explicitly selected by business code. None of these replaces tenant placement. The following database topology fragment must be merged into a complete application configuration; it is not a standalone configuration file. Replace password placeholders, and note that certificate paths are resolved according to the platform of the running process:

```toml
scope_id = "orders-production"
snowflake_worker_id = 1

[multi_tenancy]
enabled = true

[database]
migration_mode = "verify"

[database.primary]
host = "mysql-control.internal"
port = 3306
database = "ryframe_control"
username = "ryframe_app"
password = "replace-with-primary-password"
max_connections = 20
min_connections = 2
tls_mode = "verify_identity"
tls_ca = "/run/secrets/mysql-ca.pem"

[[database.replicas]]
name = "control-read-east"
host = "mysql-control-read.internal"
port = 3306
database = "ryframe_control"
username = "ryframe_reader"
password = "replace-with-replica-password"
max_connections = 8
min_connections = 1
tls_mode = "verify_identity"
tls_ca = "/run/secrets/mysql-ca.pem"

[[database.sources]]
name = "legacy"
host = "mysql-legacy.internal"
port = 3306
database = "legacy_orders"
username = "legacy_reader"
password = "replace-with-source-password"
max_connections = 4
min_connections = 0
tls_mode = "verify_identity"
tls_ca = "/run/secrets/mysql-ca.pem"

[tenant_data]
default_target = "business-shared"
max_open_targets = 4
max_total_connections = 24
idle_pool_secs = 300

[[tenant_data.targets]]
key = "business-shared"
kind = "mysql"
mode = "shared"
host = "mysql-business.internal"
port = 3306
database = "ryframe_business"
username = "business_app"
password = "replace-with-shared-target-password"
max_connections = 8
tls_mode = "verify_identity"
tls_ca = "/run/secrets/mysql-ca.pem"

[[tenant_data.targets]]
key = "tenant-acme"
kind = "mysql"
mode = "dedicated"
host = "mysql-acme.internal"
port = 3306
database = "ryframe_tenant_acme"
username = "acme_app"
password = "replace-with-dedicated-target-password"
max_connections = 6
tls_mode = "verify_identity"
tls_ca = "/run/secrets/mysql-ca.pem"
```

Primary, replicas, sources and MySQL tenant targets use the `password` field directly, without credential environment overrides or DSNs. Empty passwords must still be explicit; authentication depends on the server. Replica and source names must be unique without cross-category conflicts, and sources cannot use `primary`. A MySQL tenant target’s host, port and database tuple must not overlap the control database, replicas, sources or other targets. Different servers may use the same database name; names alone do not establish identity. A named source may explicitly alias primary, subject to tenant-target independence checks. TLS defaults to `required`, which requires encryption only. `verify_ca` validates the certificate chain, while `verify_identity` also checks the hostname; both require a CA. All such remote production connections and targets require `verify_identity`. mTLS certificates and private keys must be configured together. Isolated development may explicitly disable TLS, but shared real MySQL tests reject Disabled. For primary, replicas and sources, `acquire_timeout_secs` and `connect_timeout_secs` default to 10 seconds and must be positive; `idle_timeout_secs` defaults to 600 seconds and `max_lifetime_secs` to 1800 seconds. These are per-pool control-topology settings, not new `tenant_data.targets` fields or a cross-process budget.

Replicas serve only explicit `ReadConsistency::Eventual` reads. Healthy replicas are selected round-robin, falling back to primary during pool selection when all are unavailable; failed SQL is not automatically replayed on primary. `Strong`, read-after-write, authorization, tasks, exports, and state transitions use primary. Startup does not wait for replicas: background reconnection and checks of health, framework ledger/schema, access catalog and currently registered control-business table structures precede routing; control-business schema drift removes a replica immediately, and recovery still requires two consecutive complete successful checks. Failure to connect primary or a configured named source blocks startup. RyFrame does not establish MySQL replication or wait for replicas to catch up; operations staff manage lag and failover. `database.sources` is accessed through `control_database.source("<name>")`, which returns `Option`, and does not participate in automatic read routing. Each source has its own connection pool and transactions; its commits and rollbacks are independent of primary. Databases are not sharded automatically, and there are no distributed transactions across databases. MySQL tenant targets have no replica configuration; even eventual reads use the target’s own pool. A schema source used by the generator does not automatically become a runtime target.

| Layout | placement target | Boundary |
| --- | --- | --- |
| Shared control database | Implicit `shared-control`, `kind="control"`, `mode="shared"` | Default single-tenant mode and the system tenant; reuses control pools and the explicit read-consistency policy, while tenant business data still has an independent migration ledger |
| Shared business database | `kind="mysql"`, `mode="shared"` | Multiple tenants share `biz_*` tables; queries remain isolated by `tenant_id` |
| Dedicated business database | `kind="mysql"`, `mode="dedicated"` | One active tenant at a time, with separate accounts, capacity, and backups available |

New configurations default to `multi_tenancy.enabled=false`. Tenant selection and management are exposed only when explicitly set to `true` in the configuration file. `tenant_data.targets[].key` is the stable identity used by migrations, health checks, the API, and placement; a database name cannot replace it. The generator's `source="local"` is shorthand: when `database=control`, it reads primary; when the storage scope is tenant, it reads `tenant_data.default_target`. That key must therefore refer to a MySQL target, and implicit `shared-control` cannot be used as a local schema source. Specify `primary` or `tenant_data.targets.<key>` directly to remove ambiguity. Provisioning a new tenant still explicitly submits `data_target_key`, and runtime routing uses only placement in the control database. Missing placement, unknown or unreachable targets, and fence or generation mismatches fail closed without falling back to `default_target` or `shared-control`.

When evolving from single-tenant `shared-control`, first add a shared or dedicated target to the configuration, create an empty database, set its target `password` field, run `cargo migrate -- tenant-data up --target <target-key>` and `verify`, and complete a live probe in “Platform Management → Data Targets.” Select the target key when provisioning a new tenant. Existing non-system tenants use the tenant data placement/migration flow: first preview and validate the placement generation, plan hash, and idempotency key, then copy the data and switch placement. Changing `default_target`, DNS, or copying a schema does not migrate existing data. The system tenant cannot migrate business data, and an occupied dedicated target must first be migrated or cleaned up.

Independent target pools are created on demand. Each pool defaults to the integer quotient `max_total_connections / max_open_targets`, overridden by target `max_connections`. Both budgets apply only to MySQL tenant targets, excluding primary, replicas, sources and `shared-control`, which reuses control pools. API and Worker count independently. When a budget is reached, only idle pools without active leases can be reclaimed; if capacity remains insufficient, the new pool is refused without displacing active sessions. `tenant-data up/verify/status` uses target keys, and `--all` processes only registered targets. For multiple targets, check physical instances and schemas first. Physically identical shared aliases are merged only under the compatible routing and slot rules below; dedicated aliases, multiple existing routes, and fences outside the alias group fail before DDL. Check status after a failure; completed targets are not replayed automatically.

## Initial ownership registration and explicit adoption of existing databases

`control up` and `tenant-data up` register ownership automatically only for a first initialization established before this invocation writes. An independent fresh schema must contain no tables, views, routines, events, or triggers. A shared-control tenant plane may coexist with a verified control plane whose ownership matches, but its tenant ledger and tenant-only tables must not yet exist. Complete or partial existing tenant objects without ownership are never claimed automatically. Matching ownership permits normal upgrades and new business modules; conflicting ownership is rejected without replacement. Replicas and sources are not claimed.

Use explicit physical adoption for an existing unowned database. Do not use up to fill in markers or reset as a substitute:

```powershell
cargo migrate -- --config-dir <directory> control ownership-adopt --output .local-tests/control-ownership.json --write
cargo migrate -- --config-dir <directory> control ownership-adopt --inspect .local-tests/control-ownership.json
cargo migrate -- --config-dir <directory> control ownership-adopt --apply .local-tests/control-ownership.json --write
cargo migrate -- --config-dir <directory> tenant-data ownership-adopt --target <key> --output .local-tests/tenant-ownership.json --write
cargo migrate -- --config-dir <directory> tenant-data ownership-adopt --target <key> --apply .local-tests/tenant-ownership.json --write
```

- Stop the API, Worker, scheduler, and all other producers first, and declare `reset.services_stopped=true` in the bound configuration. This command uses that field solely as an operational stop declaration; it does not run reset or obtain an automatic process-stop proof. `--plan` prints the task graph only. Preview without write options reads the database and prints the plan. Saved plans must be new files under the current backend's `.local-tests`. With `--output ... --write`, the command creates missing parent directories as needed. The `.local-tests` paths in the examples store the generated adoption plans. Review the physical UUID/schema, scope, configuration fingerprints, complete schema and ledgers, ownership before-image, and fence/placement bindings before applying explicitly. Unknown objects, partial initialization, in-flight or unexplained fences/placements, configuration drift, and conflicting ownership fail closed. The command does not repair business data or replay historical DDL.
- Physical `ownership-adopt` is separate from business `adopt --module`: the latter adopts business migration metadata, while the former requires the applicable business ledger and schema to be valid already. After an unknown commit result, inspect the original plan against the complete before/after images; do not edit the plan or replay automatically. Consistency between a separate control and target database depends on the external producer-stop boundary; no cross-database atomic commit is claimed.
- Physically identical shared aliases are merged only when routing and slot semantics are compatible. Choose a deterministic representative only when no fence route exists; existing fences must identify exactly one configured route key in the group. Dedicated aliases, multiple routes, and fences outside the group are rejected. Recheck the choice under the migration mutex instead of selecting the first key alphabetically.
