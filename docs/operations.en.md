# Operations

## Deployment and Releases

Production images use a digest-pinned Distroless Debian 13 runtime layer containing only API, migrations, Worker and their runtime dependencies, without a shell, package manager, `curl`, generator, file maintenance or reset. API and Worker use their own `--healthcheck` command to probe local `/readyz`. The runtime image sets only the application environment variable `APP_ENV=prod` and, from its working directory `/opt/ryframe`, reads the mandatory plaintext `config/app.prod.toml` by default; `config/app.toml` may provide common defaults. Set database, JWT, Redis, object storage and monitoring credentials directly in their fields. Keep real files in a controlled private directory outside the Git working tree and mount them read-only into a separate configuration directory for each container instance, selected by CLI `--config-dir <directory>`. Keep `scope_id` stable and use a different root `snowflake_worker_id` for each instance. Use complete `image@sha256:<digest>` references in deployment configuration; where maintenance commands provide image digest options, use their CLI help rather than project environment variables. Four-role templates for API, Worker, control database migrations and tenant-data migrations, each with a private configuration directory, are integrated and have passed asset structure checks and CI tool tests. Real containers, images and the complete deployment flow remain unaccepted. When using the local storage backend, set its directory through `object_storage.local_base_dir` in the selected role configuration file, without an environment override. Image builds bind a 40-character lowercase commit SHA through Docker build argument `SOURCE_COMMIT`. After validating it, the Dockerfile writes it to managed file `.local-tests/build/source-commit` inside the build container, and Rust build scripts read only that file. It is not an application environment variable and is not copied into the runtime image. Formal maintenance and recovery builds inside the repository use Rust/Python coordinators to create the same managed file exclusively, verify its contents, and clean it after completion. Concurrent controllers, drift, or an unknown cleanup result fail and preserve evidence. An ordinary development build without the file reports its source as `development` and cannot produce formal recovery proof.
```powershell
$sourceCommit = git rev-parse HEAD
docker build --build-arg "SOURCE_COMMIT=$sourceCommit" -f deploy/Dockerfile .
```
Copy the public `deploy/compose.prod.yml` example to your deployment directory outside the working tree. In that copy, set the real image digest and use the absolute host directory paths as the mount `source` for each of the four role configurations and the shared TLS directory. Retain the mount targets inside the containers, read-only settings, and `create_host_path: false`. CI checks the version-controlled template from the backend repository root. Use the external copy above for deployment. Verify configuration resolution, the pinned image and startup separately.
```powershell
docker compose -f "D:/deployments/ryframe/compose.prod.yml" config
docker compose -f "D:/deployments/ryframe/compose.prod.yml" up -d
```
The four-role deployment sequence updates control and tenant databases before starting Worker and API. Template structure checks do not replace startup and upgrade acceptance in a real environment. After startup, check API `/livez` and `/readyz`, and `/readyz` on the Worker's health port. Nginx only proxies the API port on the edge network; MySQL, Redis, and object storage remain on internal networks. When running directly on a host, first create an empty database and set `APP_ENV` and configuration, then execute `control up`, `control verify`, `tenant-data up --target shared-control`, `tenant-data verify --target shared-control`, and `cargo serve` in that order. Default single-tenant mode also has two migration ledgers: control and `shared-control`. `verify` only checks; a new empty database requires `up` first. See the [Data Guide](data.en.md#initializing-a-new-environment) for the full procedure. After importing the complete SQL into the physical control database, run `control verify` and `tenant-data verify --target shared-control` directly without another `up`; other independent MySQL tenant targets still require their own `tenant-data up/verify`. Production defaults to and permits only `jobs.mode="external"`; starting API alone is insufficient. Prepare separate private directories containing `app.prod.toml` for API and Worker, explicitly set `APP_ENV=prod` in both terminals, and start Worker before API with each role’s own `--config-dir <directory>`. Use different `snowflake_worker_id` values while sharing the control database and scope. When continuing with the external configuration directory from the README, add `--config-dir ../ryframe-dev-config` after `--` in this guide's Cargo alias examples that otherwise use default `config`, for example `cargo migrate -- --config-dir ../ryframe-dev-config control verify` or `cargo serve -- --config-dir ../ryframe-dev-config`. Keep selecting the same directory for verification, export and runtime commands to avoid connecting through a different, uninitialized configuration. A structure assertion failure in the complete SQL reports the migration, phase and category. Preserve the original output and state; an empty ledger does not establish that DDL rolled back. Inspect read-only first, without automatic replay or manually adding completion markers. The current version only accepts new production databases. Existing real production databases from older versions require a non-destructive upgrade design and rehearsal first; reset cannot replace an upgrade. Production API instances must also receive complete `zh-CN.toml` and `en-US.toml` resources through TOML field `app.locales_dir`. The default is `locales`, resolved from the process current working directory for ordinary applications; `APP_LOCALES_DIR` is not read. Missing resources or loading failures strictly reject production startup; the development embedded fallback does not replace production resource deployment.

## Non-production Rebuilds

Rebuilds are restricted to non-production environments. See [Architecture: non-production rebuilds](architecture.en.md#non-production-rebuilds) for complete configuration, two-stage commands, ledgers, and failure recovery rules. Production permanently rejects this entry point. Rebuild verification preserves exactly one canonical data-scope projection bootstrap outbox seed for each current tenant and strictly checks its version, payload, and undelivered state; other runtime resource tables must remain empty. Preserve the scene on a seed mismatch rather than clearing events to bypass verification. For reference-fixture `environment prepare`, choose an independent new configuration directory beside the reserved service root, for example service root `run-copy-<id>` and configuration directory `env-copy-<id>`. Configuration output must not equal `review.future_root` or lie within it. The tool rejects this layout before creating configuration files or output directories and does not start services. Retain existing environments and failure evidence, use the formal review entry to select a new layout, and do not overwrite or automatically replay the original scene. The native preparation entry writes local files directly, rechecks source, maintenance builds and secret files before success, and publishes `bootstrap.json` last; it starts no service and writes no database. An explicit `--secrets-dir` must belong to the original generated business tree G identified by `original.paths.backend` in `execution-source.json`, while configuration output belongs to published execution tree P. A nondefault secret set requires a complete `secret-set.json`; create it with `cargo xtask check recovery fixture environment rotate-secrets --fixture <fixture.json> --output <new-secret-set> --write`. Each read-only verification of a fixture plan or prepared environment uses one input window: fully check the original generated and published backend/frontend roots before and after reading, and protect the bytes and file identities of `execution-source.json` and the original `fixture.json` before their first read. Without an active static-authority read window, complete observations of the four source roots use at most four parallel threads; an active authority window still consumes and protects every actual input serially on its owner thread. Join every created observation thread and collect all results; a root or thread failure retains the other source and file postchecks. Source checks, call boundaries and existing deadlines remain unchanged. Intermediate work only recalculates the same pure plan without caching across calls; plan JSON, SHA-256 values and input projections stay unchanged. Protect bootstrap before its first read and recheck the configuration directory, private environment and secret files after reading; replacing a file with identical bytes is also prevented or rejected. Once a valid window exists, a business-read or individual-source failure still performs the other available source and file postchecks and preserves concurrent failure reasons. Invalid or missing original inputs, or failure to establish complete source before-images, are rejected without creating files, starting services or replaying operations. Existing deadlines remain unchanged. Each launch role uses its own read window; existing deadlines and refusal to replay failures remain unchanged.

## HTTP 5xx and High Latency

Application log filtering uses the configured `logger.level`; `RUST_LOG` does not override it. To change the level while troubleshooting, edit the selected configuration file and restart the corresponding process. First inspect API logs and traces by request ID, then check databases, Redis, object storage, and Worker. After confirming a failure in a single dependency, follow the degradation policy; do not amplify the incident by increasing retries.

## Redis and Object Storage Conventions

- Redis `timeout_secs` consistently limits connections, responses, and transactions, within 1–60 seconds. S3-compatible backends use `object_storage.request_timeout_secs`, within 1–300 seconds. Do not layer unbounded retries at call sites. For Redis failures, check connection mode, TLS, ownership marker and scope prefix. If the authorization cache is unavailable, fail closed or disable caching according to configuration; never clear a shared Redis DB.
- Readiness probes only execute Redis `PING` and private object-storage bucket checks, protected by independent short timeouts. Only failures of `required` dependencies block readiness; optional dependencies explicitly enter a degraded state.
- `ryframe_connector_operations_total` and `ryframe_connector_operation_duration_seconds` only use three types of low-cardinality labels: connector, fixed operation, and result. Endpoints, tenants, Redis keys, bucket names, and object keys must not appear in metric labels.
- `Debug` output for Redis and S3 configuration hides passwords, access keys, and client private keys. Non-success S3 responses retain only a stable operation name and HTTP status and discard the remote response body; transport errors remove the request URL. File maintenance errors contain only an internal file ID, without bucket names, object keys, Authorization, signatures, or payloads.
- Deterministic tests use local implementations or offline protocol samples. Real protocol tests must be explicitly enabled and use unique schemas/namespaces with precise cleanup. `FLUSH`, `KEYS`, and deletion by ambiguous object prefixes are prohibited.

## Refresh Token Replay and Abnormal Account Recovery

Immediately revoke the token family and current session, and check the user's authorization version, client IP, and audit events. After confirming a leak, rotate the relevant credentials and retain evidence. If an ordinary account from an older development version cannot log in and its password is unknown, use the [explicit account recovery procedure](api.en.md#recovering-accounts-with-unknown-passwords); do not repeat initialization or edit password hashes directly. Disabled status and mandatory password changes are independent; a successful reset does not automatically enable the account.

## Failed or Expired Backups

The native business catalog loader reads the copy catalog from explicit Workspace members in the execution backend and consistently validates managed generated assets, content digests, module ownership, and complete table descriptors. Returned tables retain the declaration order of the Workspace and machine catalog. The complete business migration ledger column names and types come from the formal SDK DDL read by the same Rust validation entry point. Ordinary source export uses that same complete catalog for structural verification, including the ledger for registered business modules, rather than assembling another full table list. The reviewed data-copy catalog and the complete structural-verification catalog retain their respective responsibilities. Verification callers obtain results through the read-only protocol with an explicitly bound current tool; the Python bridge no longer parses catalogs independently or accepts catalog fragments. If catalog or ownership validation fails, check the execution worktree and repair managed assets through the formal generation entry point. If ledger structure validation fails, check the SDK version and DDL in the execution worktree. Do not filter unknown tables or bypass validation to continue copying. Ordinary source export first compares the ordinary and raw per-target business images, then includes the actual row counts and digests for `biz_data_scope_owner`, `biz_data_scope_dept`, and `biz_data_scope_projection` in its logical inventory. An omitted target with nonempty projections cannot be supplied as empty. This does not turn ledgers or ownership into business data. The multi-database dump directory is exclusively created once at the beginning of the batch; existing directories or payloads are never overwritten. After failure, retain the original attempt, inspect the complete scene, and use the formal recovery entry point.

The reference copy tool reads and precisely decodes complete SQL dumps in Rust, then supplies managed chunks to the existing coordinating callers without launching a subprocess for each row. Even when selecting only the tenant declaration table, it first validates the complete table catalog, all columns, and data in unselected tables. Numbers retain their exact values, and JSON rejects duplicate keys and nonfinite numbers. The result directory binds the original dump, catalog digest, file identities, and complete result digest. Each chunk read rechecks those bindings; only complete consumption followed by EOF, row-count, and source checks permits precise deletion of that result. Creation, reading, or closing failures preserve the failure scene without automatically retrying or deleting the original dump. On a formal copy failure, the command identifies its stage record and run manifest; failure.json in the copy directory records the failed phase, complete call locations and available system codes, omitting exception text, arguments and source lines. Compare complete before/after images before continuation; an error category alone does not authorize replay. If a source snapshot cannot execute Git, check the local Git installation and operating-system PATH. Application-environment switching retains allowlisted OS variables; APP_ENV still only selects application configuration files. Full-stack build and runtime verification share native source facts, checking the model file, complete Git snapshots and applicable CI identity together. Preserve the scene on a mismatch instead of manually changing original source receipts. A reported `.local-tests/sql-row-streams/sql-rows-*` directory is a local derived result, not evidence that remote copying completed. Save diagnostics and check the source and complete target image before continuing through the formal recovery entry point. Stop migration operations that depend on invalid backups, and check targets, checksums, collection times, and retention policies. Regenerate and verify backups after recovery rather than marking them successful manually. External tools back up and restore bytes; RyFrame only handles manifest collection, registration, recovery verification, state, and alerts. Source export and subsequent generation verification share the complete physical binding: database connection identities, target modes, public object-storage metadata and the overall digest must agree, without including credentials. Preserve the original export and failure evidence when a binding is incomplete or inconsistent. After checking source data and the complete target image, perform a new read-only export through the formal entry point in a new run directory; do not rewrite or re-sign the old export or automatically replay copying.

### Reference Environment and Consistency

The reference drill uses the system tenant and 10 ordinary tenants across shared and dedicated data targets, with at least 100,000 representative business records and 1 GiB of object data. External operations scheduling performs a full backup every 12 hours with at least 7 days of retention. Drill reports must record the Windows machine, MySQL/RustFS versions, storage, and network conditions. A 24-hour recovery point and 60-minute recovery time are targets that require actual verification at this scale. Before collection starts, pause business writes and stop API write entry points, Worker, scheduler, messaging, and other producers. Maintain quiescence throughout manifest collection, database dumping, and object copying, so data from different times is not registered as a consistent backup. Database digests follow the complete primary-key order, and objects use streaming SHA-256. Manifests include source SHA, schema fingerprints, physical database identities, tenant placements, object prefixes, byte sizes, and digests, without secrets.

### Collection and Registration

Use `cargo xtask data` on a Windows maintenance machine for backup and recovery registration. Use controlled private configuration for backup and recovery, and register framework maintainer acceptance evidence through the corresponding commands. The production runtime image excludes this maintenance command. Historical producer checks on Windows first read the kernel identity. Only an absent process or a strictly later creation time for the same PID proves that the recorded generation has ended. A managed Rust child queries local CIM only when the kernel query reports access denied (error code `5`), with a 15-second query timeout budget. CIM retains microsecond precision: its creation time must be strictly later than the recorded time plus 10 ticks of 100 ns each. The same generation, an adjacent precision boundary, duplicate identities, unknown timestamps, and query failures reject registration. This path no longer falls back to PowerShell/PDH and never signals the process currently using that PID. When an error includes a CIM HRESULT, inspect the local service with `Get-Service Winmgmt` and check read access to `ROOT\CIMV2`. After repair, rerun the original verification command. Preserve existing stage results and partial files, and recover according to their actual state; never manually mark a process as stopped or automatically replay data writes. `Get-Service Winmgmt` is for manual troubleshooting only, not a runtime fallback.
```powershell
cargo xtask data backup inventory --output <absolute-new-file-in-backend-workspace/.local-tests> --source-sha <exact-backend-sha> --quiesced-at <writes-quiesced-at-rfc3339>
```
`backup inventory` and `target inventory` are explicitly selected read-only inventory operations. They only atomically create new evidence files with create-new semantics inside the current backend's `.local-tests`, without modifying databases, objects, or registration state, so they do not use `--write`; the output file must not already exist. External tools then copy and verify the exact databases, tables, and object prefixes from the manifest, and fill in `id`, `completed_at`, `retention_until`, and `artifacts` to form a `BackupManifest`. Every `db:<logical-target-key>` and `objects:<bucket>` must have at least one file artifact recording its `relative_path`, `bytes`, and `sha256`; relative paths must not escape the backup root. See `crates/ryframe-application/src/ports/backup/manifest.rs` for the structure definition. To inspect targets without assigned tenants or state before and after initialization, use `cargo xtask data target inventory --target <configured-target-key> --output <absolute-new-file-in-backend-workspace/.local-tests>`. This command connects only to explicitly configured databases, validates schema and the exact complete table catalog, and calculates full row digests in a read-only transaction. `target.database` stores business tables and placements; `target.preserved_tables` separately stores ownership, migration ledgers, and backup/recovery registration tables. It does not access object storage or modify the target, and does not omit unused targets as an "empty manifest."
