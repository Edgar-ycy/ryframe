# Operations

## Deployment and Releases

Production images use a digest-pinned Distroless Debian 13 runtime layer containing only API, migrations, Worker and their runtime dependencies, without a shell, package manager, `curl`, generator, file maintenance or reset. API and Worker use their own `--healthcheck` command to probe local `/readyz`. The runtime image sets only the application environment variable `APP_ENV=prod` and, from its working directory `/opt/ryframe`, reads the mandatory plaintext `config/app.prod.toml` by default; `config/app.toml` may provide common defaults. Set database, JWT, Redis, object storage and monitoring credentials directly in their fields. Keep real files in a controlled ignored directory and mount them read-only into a separate configuration directory for each container instance, selected by CLI `--config-dir <directory>`. Keep `scope_id` stable and use a different root `snowflake_worker_id` for each instance. Use complete `image@sha256:<digest>` references in deployment configuration; where maintenance commands provide image digest options, use their CLI help rather than project environment variables. Four-role templates for API, Worker, control database migrations and tenant-data migrations, each with a private configuration directory, are integrated and have passed asset structure checks and CI tool tests. Real containers, images and the complete deployment flow remain unaccepted. When using the local storage backend, set its directory through `object_storage.local_base_dir` in the selected role configuration file, without an environment override.

Image builds bind a 40-character lowercase commit SHA through Docker build argument `SOURCE_COMMIT`. After validating it, the Dockerfile writes it to managed file `.local-tests/build/source-commit` inside the build container, and Rust build scripts read only that file. It is not an application environment variable and is not copied into the runtime image. Formal maintenance and recovery builds inside the repository use Rust/Python coordinators to create the same managed file exclusively, verify its contents, and clean it after completion. Concurrent controllers, drift, or an unknown cleanup result fail and preserve evidence. An ordinary development build without the file reports its source as `development` and cannot produce formal recovery proof.
```powershell
$sourceCommit = git rev-parse HEAD
docker build --build-arg "SOURCE_COMMIT=$sourceCommit" -f deploy/Dockerfile .
```
The following commands are examples for subsequent mount, pinned-image and startup verification, not evidence of runtime acceptance:

```powershell
docker compose -f deploy/compose.prod.yml config
docker compose -f deploy/compose.prod.yml up -d
```
The four-role deployment sequence updates control and tenant databases before starting Worker and API. Template structure checks do not replace startup and upgrade acceptance in a real environment. After startup, check API `/livez` and `/readyz`, and `/readyz` on the Worker's health port. Nginx only proxies the API port on the edge network; MySQL, Redis, and object storage remain on internal networks. When running directly on a host, first create an empty database and set `APP_ENV` and configuration, then execute `control up`, `control verify`, `tenant-data up --target shared-control`, `tenant-data verify --target shared-control`, and `cargo serve` in that order. Default single-tenant mode also has two migration ledgers: control and `shared-control`. `verify` only checks; a new empty database requires `up` first. See the [Data Guide](data.en.md#initializing-a-new-environment) for the full procedure. SQL import still requires `control verify`, and actual tenant targets require `tenant-data up/verify`. When continuing with the ignored directory from README, add `--config-dir .local-tests/dev-config` after `--` in this guide's Cargo alias examples that otherwise use default `config`, for example `cargo migrate -- --config-dir .local-tests/dev-config control verify` or `cargo serve -- --config-dir .local-tests/dev-config`. Keep selecting the same directory for verification, export and runtime commands to avoid connecting through a different, uninitialized configuration.

The current version only accepts new production databases. Existing real production databases from older versions require a non-destructive upgrade design and rehearsal first; reset cannot replace an upgrade. Production API instances must also receive complete `zh-CN.toml` and `en-US.toml` resources through TOML field `app.locales_dir`. The default is `locales`, resolved from the process current working directory for ordinary applications; `APP_LOCALES_DIR` is not read. Missing resources or loading failures strictly reject production startup; the development embedded fallback does not replace production resource deployment.

## Non-production Rebuilds

Rebuilds are restricted to non-production environments. See [Architecture: non-production rebuilds](architecture.en.md#non-production-rebuilds) for complete configuration, two-stage commands, ledgers, and failure recovery rules. Production permanently rejects this entry point.

## HTTP 5xx and High Latency

Application log filtering uses the configured `logger.level`; `RUST_LOG` does not override it. To change the level while troubleshooting, edit the selected configuration file and restart the corresponding process. First inspect API logs and traces by request ID, then check databases, Redis, object storage, and Worker. After confirming a failure in a single dependency, follow the degradation policy; do not amplify the incident by increasing retries.

## Redis Degradation

Check connection mode, TLS, ownership marker, and scope prefix. If the authorization cache is unavailable, fail closed or disable caching according to configuration. Never clear a shared Redis DB.

## Redis and Object Storage Conventions

- Redis `timeout_secs` consistently limits connections, responses, and transactions, within 1–60 seconds. S3-compatible backends use `object_storage.request_timeout_secs`, within 1–300 seconds. Do not layer unbounded retries at call sites.
- Readiness probes only execute Redis `PING` and private object-storage bucket checks, protected by independent short timeouts. Only failures of `required` dependencies block readiness; optional dependencies explicitly enter a degraded state.
- `ryframe_connector_operations_total` and `ryframe_connector_operation_duration_seconds` only use three types of low-cardinality labels: connector, fixed operation, and result. Endpoints, tenants, Redis keys, bucket names, and object keys must not appear in metric labels.
- `Debug` output for Redis and S3 configuration hides passwords, access keys, and client private keys. Non-success S3 responses retain only a stable operation name and HTTP status and discard the remote response body; transport errors remove the request URL. File maintenance errors contain only an internal file ID, without bucket names, object keys, Authorization, signatures, or payloads.
- Deterministic tests use local implementations or offline protocol samples. Real protocol tests must be explicitly enabled and use unique schemas/namespaces with precise cleanup. `FLUSH`, `KEYS`, and deletion by ambiguous object prefixes are prohibited.

## Refresh Token Replay and Abnormal Account Recovery

Immediately revoke the token family and current session, and check the user's authorization version, client IP, and audit events. After confirming a leak, rotate the relevant credentials and retain evidence. If an ordinary account from an older development version cannot log in and its password is unknown, use the [explicit account recovery procedure](api.en.md#recovering-accounts-with-unknown-passwords); do not repeat initialization or edit password hashes directly. Disabled status and mandatory password changes are independent; a successful reset does not automatically enable the account.

## Dependency and Task Troubleshooting

| Symptom | Checks and handling |
| --- | --- |
| Rate-limit Rejections | Distinguish tenant quotas, account policies, and infrastructure failures. Adjust configuration only after confirming that business capacity permits it; do not delete rate-limit keys or bypass tenant boundaries. |
| Database Replicas and Read Fallback | Check replication lag, connection health, and read consistency. Authorization, tasks, exports, and state changes must return to the primary database; do not temporarily replace strongly consistent reads with replica reads. |
| Background Tasks | Check lease, heartbeat, attempt, public errors, and dead-letter state. The database rejects duplicate claims. After fixing the cause, use controlled retries rather than directly editing a task's terminal state. |
| Scheduled Execution | Check the expression, time zone, misfire policy, and next run time. Avoid multiple schedulers creating the same business task repeatedly. |
| Message Center Delivery | Check the outbox, dispatch tasks, target audience, and multilingual parameters. Restore idempotent consumption before processing the backlog; do not skip tenant or permission filtering. |
| OpenTelemetry Exporters | Export failures should not block business requests. Check endpoint, TLS, timeout, and queue-drop metrics, and confirm traceparent propagation continues after recovery. |
| Database Connection Capacity | Measure pool usage separately for the control database, tenant targets, and Worker. Address leaks, slow queries, and incorrect concurrency before increasing pool limits; the total connection budget must not exceed database limits. |
| Disk Capacity | Check `target`, logs, temporary XLSX files, upload staging, and local object directories. Delete only confirmed build caches or expired artifacts, retaining the latest debug symbols and reset ledgers. |

## Failed or Expired Backups

Stop migration operations that depend on invalid backups, and check targets, checksums, collection times, and retention policies. Regenerate and verify backups after recovery rather than marking them successful manually. External tools back up and restore bytes; RyFrame only handles manifest collection, registration, recovery verification, state, and alerts.

### Reference Environment and Consistency

The reference drill uses the system tenant and 10 ordinary tenants across shared and dedicated data targets, with at least 100,000 representative business records and 1 GiB of object data. External operations scheduling performs a full backup every 12 hours with at least 7 days of retention. Drill reports must record the Windows machine, MySQL/RustFS versions, storage, and network conditions. A 24-hour recovery point and 60-minute recovery time are targets that require actual verification at this scale.

Before collection starts, pause business writes and stop API write entry points, Worker, scheduler, messaging, and other producers. Maintain quiescence throughout manifest collection, database dumping, and object copying, so data from different times is not registered as a consistent backup. Database digests follow the complete primary-key order, and objects use streaming SHA-256. Manifests include source SHA, schema fingerprints, physical database identities, tenant placements, object prefixes, byte sizes, and digests, without secrets.

Post-copy administrator sessions use a separate file containing current credentials. Complete the first password change through the normal account flow, then create a private file in the backend's ignored directory, for example the absolute path `<backend>/.local-tests/clone/administrator.toml`:

```toml
[administrator]
tenant_id = "system"
username = "admin"
password = "<current-password-after-first-change>"
```

The post-copy registration request's `source_admin` contains only four metadata fields: `subject_id`, `tenant_id`, `username`, and `client_address`. Register the TOML separately as `administrator_credentials` using its `path`, `bytes`, and `sha256` file binding. Never copy the password into requests, public registrations, or receipts. The tenant and username in the file must match the metadata. The file and every path component must have no links and remain inside the current backend's `.local-tests`. Registration and session startup verify the file binding before and after reading. Content or binding changes, invalid fields, and TOML parsing failures stop execution without echoing the source text. After login, the authoritative session must explicitly report `password_change_required=false`; a true or missing field prevents business actions. This password is independent of `bootstrap.admin_password`: tools never change passwords automatically, fall back to initialization passwords, or replay business writes. If the first password change is incomplete, finish the explicit account flow rather than registering the initialization password as current credentials.

Continue to register explicitly through `cargo xtask check recovery clone post-copy --run-dir <run> --operation register --request <request.json> --write`; subsequent operations that write still require `--write`. The file bound by `api_environment` accepts only `{"environment":{"APP_ENV":"test"}}`, with no administrator credentials or other project configuration. Addresses, Worker mode, CORS, and other settings come from their bound application TOML files. An amendment may rebind the environment selector only after the existing stop-evidence and failure-reconciliation flow; environment fields cannot modify project configuration.

### Collection and Registration

Use `cargo xtask data` on a Windows maintenance machine for backup and recovery registration. Keep configuration and secrets in a controlled ignored directory. This maintenance capability is not included in production runtime images.
```powershell
cargo xtask data --help
cargo xtask data backup inventory --output <absolute-new-file-in-backend-workspace/.local-tests> --source-sha <exact-backend-sha> --quiesced-at <writes-quiesced-at-rfc3339>
```
`backup inventory` and `target inventory` are explicitly selected read-only inventory operations. They only atomically create new evidence files with create-new semantics inside the current backend's `.local-tests`, without modifying databases, objects, or registration state, so they do not use `--write`; the output file must not already exist. External tools then copy and verify the exact databases, tables, and object prefixes from the manifest, and fill in `id`, `completed_at`, `retention_until`, and `artifacts` to form a `BackupManifest`. Every `db:<logical-target-key>` and `objects:<bucket>` must have at least one file artifact recording its `relative_path`, `bytes`, and `sha256`; relative paths must not escape the backup root. See `crates/ryframe-application/src/ports/backup/manifest.rs` for the structure definition.

To inspect targets without assigned tenants or state before and after initialization, use `cargo xtask data target inventory --target <configured-target-key> --output <absolute-new-file-in-backend-workspace/.local-tests>`. This command connects only to explicitly configured databases, validates schema and the exact complete table catalog, and calculates full row digests in a read-only transaction. `target.database` stores business tables and placements; `target.preserved_tables` separately stores ownership, migration ledgers, and backup/recovery registration tables. It does not access object storage or modify the target, and does not omit unused targets as an "empty manifest." Consistency between the control database and dedicated targets still requires externally stopping all producers; a single target inventory does not establish successful backup or recovery.

```powershell
cargo xtask data backup register --manifest <absolute-manifest-in-backend-workspace/.local-tests> --backup-root <registered-external-absolute-backup-directory> --write
cargo xtask data backup status
```
Registration rereads files to verify size and SHA-256; missing or corrupted files are registered as invalid and return failure. Repeated verification under the same backup ID is only allowed for the same manifest, without replacing data. Successful registration means backup files have been verified, not that recovery has succeeded. Status queries only read the control database and do not depend on current object-storage connectivity.

### Isolated Recovery and Acceptance

1. Prepare new isolated databases and object prefixes, initialize them against the current baseline, and establish target ownership. Keep logical target keys consistent, but physical databases, scope, JWT secrets, and Redis namespaces must differ from the original environment; Worker uses external mode. The maintenance command's `--config-dir <directory>` selects source-side registration database configuration, while `--restore-config-dir <directory>` selects only isolated recovery target configuration. Check physical identities, scope and endpoints in both plaintext files to avoid mixing source and target. Application-relative configuration directories resolve from the command's current working directory; absolute paths are recommended.
2. Following `crates/ryframe-application/src/ports/backup/restore.rs` and its `RestorePlan`, fill in the complete targets, fault time, frontend SHA, API/Worker readiness addresses, and new object prefixes. Physical database identities must match and must not point to any original business database.
3. Execute `restore-begin` before external restoration starts. Repeating the same plan does not reset timing. External restoration only overwrites the verified isolated resources in that plan and retains the target's own ownership and backup registration metadata. Database dumps contain only business tables in the manifest and must not execute `USE` targeting source databases, database creation, or cross-database statements. Object paths only replace the scope prefix and must not copy source ownership markers.
4. Stop target business writes and execute `restore-verify-data`. It revalidates backup files, current schema, complete table contents, tenant relationships, and the complete object set. Missing, extra, corrupted, or incorrectly owned data causes failure.
5. Start API, Worker, and frontend with entirely new Redis temporary state, complete real browser business acceptance, then submit a `RestoreBusinessProof` binding the drill ID, plan hash, source SHA, scope, and time range. `restore-verify` checks both readiness probes again and only records success when data and business verification both pass, total elapsed time does not exceed 60 minutes, and the backup recovery point is no more than 24 hours before the fault.

Run `cargo xtask data restore begin --plan <absolute-plan> --output <absolute-new-running.json> --restore-config-dir <absolute-target-configuration> --write`, `cargo xtask data restore verify-data --id <drill-id> --backup-root <absolute-backup-root> --output <absolute-new-data-verified.json> --restore-config-dir <absolute-target-configuration> --write`, and `cargo xtask data restore verify --id <drill-id> --proof <absolute-business-proof> --tests-receipt <absolute-test-details> --runtime-receipt <absolute-runtime-receipt> --target-plan <absolute-target-plan> --runner-root <absolute-clean-test-runner-worktree> --restore-config-dir <absolute-target-configuration> --write` in that order. Plans, proofs, receipts, and outputs must be descendants of the current backend's `.local-tests`; backup roots, isolated configurations, and clean runners may use registered external absolute directories. No path may traverse symbolic links or reparse points. Input files and directories must exist; output parent directories must exist and target files must not exist. These conditions and `--write` are checked before maintenance binaries start or resources are connected. After business success, a temporary file is written and synchronized in the same directory, atomically published with create-new semantics, then reread to verify canonical bytes, JSON, and paths. Argument errors, business failures, or existing targets do not create or truncate success records. If publication or revalidation fails after business writes succeed, retain registration-database state and any published files, perform a read-only status check first, and do not replay blindly.

Native fresh-target static validation reads connections, credentials, Redis, and Worker endpoints only from the selected plaintext configuration files; the environment map uses only `APP_ENV=test` to select the test file. A request may explicitly bind a configuration directory inside the execution backend through `configuration_directory`, defaulting to that backend's `config` directory. `app.test.toml` is required; common `app.toml` is optional. Former directory, endpoint, password, and `_FILE` environment overrides do not participate in this entry point's configuration or digests, and former object credential variable names cannot replace explicit credential fields in the request. Passing static validation does not replace process, port, actual ownership, or complete recovery-chain verification. Native source-object capture and target-object revalidation use a Rust S3 read port with file-bound credentials, AWS-LC TLS, and SigV4. Target listings check pagination completion, scope, duplicate keys, and continuation tokens. Object GET uses an explicit size limit, conditional ETags/versions, and exclusively created files; redirects, automatic retries, decompression, and partial-content responses are disabled. Interrupted reads retain partial files: inspect the attempt failure evidence and do not treat residual files as successful exports. Public `request.json` and `export.json` evidence retains only the S3 endpoint and region; credentials stay in the original private file, whose size and digest remain independently bound. Verification regenerates and compares the public projection. Native reads do not need an AWS subprocess; recovery steps still using Python capture or copy retain their own tool preflight requirements. Passing native reads does not replace complete recovery acceptance. The fresh-target CLI validates reviewed requests, tool sets, reset manifests, configuration directories, never-started history, private environments, and preflight reconciliation bindings through the current managed Rust tool using bounded standard input. A missing tool binding fails directly without discovering a program through PATH or Cargo. The CLI private environment file accepts only `APP_ENV`, `TEMP`, and `TMP`; the latter two must identify the same existing private directory. Connections, passwords, and other project settings belong in the bound TOML files. Validation failures preserve the scene and never authorize automatic replay or resource cleanup.

Before the first database or object write to a fresh target, run `cargo xtask check recovery runtime register --plan <reference-plan-json> --target-plan <target-plan-json> --output <new-runtime-registration.json> --write` to register that the target has never started. Under the ownership control lock, registration checks before and after writing that the target runtime directory contains no lifecycle, launch, process-tree, or unknown files, and proves that the three exact API, Worker, and frontend ports are free. Missing process receipts alone do not prove shutdown. The formal recovery executor holds the same registration lock throughout all writes and rechecks before each database or object write and on exit. The registration file binds both plans' absolute paths, sizes, and SHA-256 digests, plus zero-process observations. Recovery receipts bind that registration file. Changes to plans or runtime state require a new registration rather than overwriting the old file.

Complete acceptance retains original logs, verification results, traces, screenshots, and videos from successful recovery and from failure drills with corrupted or missing backups. Failures are not overwritten as successes during registration, and original business resources are not manipulated automatically. `running`, `data_verified`, `succeeded`, and `failed` mean started, data passed, all passed, and failed, respectively; overdue unfinished recovery still triggers alerts.

### Generating Recovery Business Proof

Use `cargo xtask check recovery inputs bindings --reference-plan <side-reference-plan> --target-plan <side-target-plan> --backup-receipt <same-backup.json> --record <data-verified.json>` to preview data bindings read-only; only adding `--output <new-bindings-file> --write` atomically publishes them. The entry point derives the unique `record` and `manifest` from verified records and the original backup manifest, without accepting manual excerpts or reconstruction. Frontend and backend must be clean source trees at the manifest-bound SHAs. Use `cargo xtask check recovery runtime build --source-backend <absolute-backend-worktree> --expected-head <full-backend-sha> --source-frontend <absolute-frontend-worktree> --expected-frontend-head <full-frontend-sha> --output <backend-worktree/.local-tests/restore/build.json> --write --frontend-dir <current-tools-frontend>` to generate and verify actual API, Worker, and frontend production build receipts together. Historical source need not provide the current CLI; the coordinator uses current clean tools to invoke the target worktree's own Vite and writes `.vite/restore-build.json` in that target frontend. Existing frontend receipts undergo the same strict verification before reuse; build facts are never overwritten or fabricated. Current backend build receipts use v2 and frontend build receipts use v3, separately binding product inputs calculated by artifact role, acceptance-tool inputs, complete source manifests, actual toolchains, and effective build arguments. The frontend selects `app.dev.toml`, `app.test.toml`, or `app.prod.toml` using the saved `configuration.environment`, binding paths and digests in read order: optional common `app.toml`, then the required selected environment file. It also binds the actual sources and precedence of `config/tools.json` and `.local-tests/frontend-tools.json`, the managed `.local-tests/build/source.json` identity, and the complete `dist` manifest. Verification does not depend on the current shell `APP_ENV` or legacy `VITE_*` variables. Real builds require an empty merged `api_origin`; formal source identity must equal the declared exact clean HEAD and match `dist/build-identity.json`. Older formats are retained only as historical files and cannot be used for current recovery.

`runtime start` requires runtime registration, the complete target plan, both source trees, build receipts, and data bindings together. It starts API, Worker, and frontend from plaintext configuration files or atomic configuration snapshots bound by the target plan, saving an operation intent for each role before registering the complete tree in the same Job Object or process group. Before first creating the runtime directory, it also writes a unique creation intent outside that directory. Therefore, if the controller exits at any cut point during directory creation, state writes, or process receipt publication, takeover is only possible through `runtime recover --write` bound to owner and generation. Each generation allows only logs and process, complete-tree, member, control, result, completion, and launch receipts for the current operation ID. Unknown files, directories, or links block further operations and retain the state. `runtime status` derives actual `registered_not_started`, `running`, `degraded`, `exited`, `interrupted`, or stopped states read-only; `runtime stop --generation <N> --write` reclaims all three trees in reverse order and proves port release.
After all three endpoints are ready, use `cargo xtask check recovery runtime bind --source-backend <execution-backend-worktree> --source-frontend <frontend-worktree> --build-receipt <build.json> --launch-receipt <generation-directory/runtime-launch.json> --bindings <bindings-file> --output .local-tests/restore/runtime.json --write` to issue a v3 runtime receipt. For an ordinary candidate, product and execution backends must use the same commit. B0 additionally requires explicit `--adapter-contract legacy-stable-readiness-b0-v1 --product-backend <815c5eaf-product-worktree>`, and the execution source must be the registered `c05114bc` adapter commit. Runtime receipts separately retain backup source, backend product source, backend execution source, adapter contract, frontend source, and the three-process generation. A backup manifest's source SHA cannot stand in for the running binaries' source. This entry point checks source code, binaries, process creation identities, complete trees, probe listening ports, and the frontend files actually returned; neither a correct configuration directory nor HTTP 200 alone proves provenance.

Register the bindings file, runtime receipt, strict target plan, current clean coordinator source path, full SHA of the current clean frontend test runner and full SHA of the current clean backend verifier together in isolated acceptance configuration, also binding the new scope and running production site. Fields and file selection arguments follow the configuration source of truth and CLI help, with wiring still subject to integration checks. Original data identities are recursively derived from the backup, same-generation STOP/START, and source-runtime bound by the strict target plan; then run `corepack pnpm check --stage browser --real --server preview`. The target plan and runtime receipt independently bind the actual product frontend and backend, so the B0 product frontend may differ from the current test runner. Before the first login, the test runner uses the absolute verified interpreter path registered in tool configuration to invoke the verified backend's read-only data preflight, completely revalidating the target plan, source generation, and lineage. It cross-binds the runtime receipt's canonical launch path and digest, lifecycle, build, endpoints, and process files for all three roles to obtain the unique in-memory file binding. The preflight does not access services or create control locks or Python bytecode. If it fails, login, logout, and business requests must not proceed; sampling a few receipt fields cannot replace complete verification. Sources are rechecked at both test start and end. Replacing processes or changing source or artifacts during execution prevents success proof generation. Files retain only digests and resource ownership, without secrets.

After all core recovery scenarios pass, together with console, network, and axe assertions, results are written to the runner's `.local-tests/playwright-real/restore-<drill-id>.json`; test details and a runtime receipt copy are saved alongside it with the same prefix. Proof explicitly records backup source, backend product and execution source, adapter contract, product frontend, test runner, and current backend verifier SHA. Test details also bind the drill, target plan, runtime receipt, both source trees, and test time, retaining complete file descriptions for the unique STOP source-generation and derived dataset-lineage; proof stores both files' SHA-256 digests. Existing results are not overwritten. Failures, skips, retries, missing scenarios, source mismatches, inconsistent details, or incomplete data verification prevent success proof generation. Final `restore verify` requires all three adjacent evidence files, the original target plan, and runner root together. The maintenance CLI constructs authoritative context from the registration database. From the registration bound by runtime launch, the current clean backend reads this side's reference plan, revalidates the target plan, all three running processes, complete build provenance, runner, and every digest, then registers success. Data lineage must match STOP, START, and current source-runtime for the same backup; a separate lineage or the other side's reference plan cannot substitute for this chain. This step still rechecks readiness and recovery time; browser success does not establish final successful recovery registration. Final verification uses the unified data entry point, binding the current backend SHA at compile time; directly running an old maintenance binary fails. Register the verified interpreter by absolute path in tool file configuration. The verifier reruns Python environment checks in isolated mode, binds interpreter file identity and digest, limits output and runtime, and rechecks the interpreter and both Git source trees before and after execution.

### External Acceptance Driver for the Reference Environment

The formally bound Rust tool executes reference-fixture environment-plan, configuration, and preflight-receipt guards; Python still orchestrates preparation, secret set rotation, and bootstrap file lifecycles. The formally bound Rust tool also executes seed close/rebind model and evidence guards; verification does not authorize remote writes or replay.

`cargo xtask check recovery` invokes private native MySQL, mysqldump, the native Rust S3 client, and Node stage programs to prepare drill data and external backups. Reference plans can only be derived through `inputs reference` from a published shared export, the corresponding side's arm, and the complete fresh-target before-image; source, tool, and target fields must not be assembled manually. The entry point pins source and tool digests, target side, fresh ownership, and an independent working directory. By default it previews only on standard output; `--output <new-file> --write` publishes without overwriting existing files. MySQL uses the explicit client configuration file and digest in the plan. The native S3 client reads the controlled plaintext configuration bound by the plan directly; it does not start an AWS CLI subprocess or pass access keys through environment variables. Credential values remain excluded from plans and public receipts. The tools do not create or scan databases; both source and target require prior initialization. The reference scale is system plus ten ordinary tenants, at least 100,000 actual post records, and at least 1 GiB of registered uploaded objects, distributed across shared and dedicated targets; for example, 256 objects of 4 MiB each. Post records belong to the control database; tenant business-table copying is separately covered by generated-resource acceptance using an isolated business crate.

The data preparation plan's `dataset.request_interval_ms` must be 1000–5000 milliseconds and limits actual HTTP request start frequency for each fixed client. All eleven tenants may prepare concurrently, each with its own identity and address. `dataset.timeout_seconds` explicitly sets the whole-stage limit (1–604800 seconds), for example 21600 seconds for the reference scale; other external commands retain a 1800-second timeout. On a 429 response, retain failure rather than bypassing rate limits through retries or address changes. Data preparation occurs before backup and recovery start, and its duration is not included in recovery time.

Run all commands from the corresponding clean backend worktree. `cargo xtask check recovery` fixes the current `--backend-dir`, and stages share `--plan <plan-json>`. Before connecting to resources, the public entry point strictly parses arguments; unknown, repeated, missing, or cross-stage arguments are rejected as argument errors. Plans, inputs, backup directories, working directories, and outputs must all be inside the current backend's `.local-tests`, contain no `..`, traverse no links or reparse points, and not overwrite existing outputs. External database, object-storage, and tool paths are read only from the bound reference plan and receipts; separate paths cannot bypass ownership. First preview the reference plan with `inputs reference --arm-input <side-arm-result> --fresh-target-verify <side-observation-directory/verify.json> --side base|candidate --id <backup-id> --work-dir <new-side-directory>`, then append `--output <side-reference-plan.json> --write` to publish.

Then preview the product plan with `inputs product --reference-plan <side-reference-plan> --backup-receipt <same-backup.json> --comparison-sources <two-version-source-manifest> --arm-input <side-arm-result> --fresh-target-verify <side-observation-directory/verify.json> --side base|candidate --id <restore-id> --fault-at <utc-time>`, and append `--output <side-product-plan.json> --write` to publish. ### Metrics and Alerts

## TLS Certificates

Check expiration, hostnames, the complete chain, and private-key permissions. After rotation, verify MySQL, Redis, object storage, OTLP, and Nginx; do not disable certificate verification as a lasting fix.
