# Operations

## Deployment and Releases

Production images use a digest-pinned Distroless Debian 13 runtime layer containing only API, migrations, Worker and their runtime dependencies, without a shell, package manager, `curl`, generator, file maintenance or reset. API and Worker use their own `--healthcheck` command to probe local `/readyz`. The runtime image sets only the application environment variable `APP_ENV=prod` and, from its working directory `/opt/ryframe`, reads the mandatory plaintext `config/app.prod.toml` by default; `config/app.toml` may provide common defaults. Set database, JWT, Redis, object storage and monitoring credentials directly in their fields. Keep real files in a controlled ignored directory and mount them read-only into a separate configuration directory for each container instance, selected by CLI `--config-dir <directory>`. Keep `scope_id` stable and use a different root `snowflake_worker_id` for each instance. Use complete `image@sha256:<digest>` references in deployment configuration; where maintenance commands provide image digest options, use their CLI help rather than project environment variables. Four-role templates for API, Worker, control database migrations and tenant-data migrations, each with a private configuration directory, are integrated and have passed asset structure checks and CI tool tests. Real containers, images and the complete deployment flow remain unaccepted. When using the local storage backend, set its directory through `object_storage.local_base_dir` in the selected role configuration file, without an environment override.

Image builds bind a 40-character lowercase commit SHA through Docker build argument `SOURCE_COMMIT`. After validating it, the Dockerfile writes it to managed file `.local-tests/build/source-commit` inside the build container, and Rust build scripts read only that file. It is not an application environment variable and is not copied into the runtime image. Formal maintenance and recovery builds inside the repository use Rust/Python coordinators to create the same managed file exclusively, verify its contents, and clean it after completion. Concurrent controllers, drift, or an unknown cleanup result fail and preserve evidence. An ordinary development build without the file reports its source as `development` and cannot produce formal recovery proof.
```powershell
$sourceCommit = git rev-parse HEAD
docker build --build-arg "SOURCE_COMMIT=$sourceCommit" -f deploy/Dockerfile .
```
Run the following commands from the backend repository root. `--project-directory .` resolves configuration and TLS mount paths relative to that root, consistently with formal CI. Configuration resolution, pinned images and actual startup require separate verification; these examples do not establish runtime acceptance.

```powershell
docker compose --project-directory . -f deploy/compose.prod.yml config
docker compose --project-directory . -f deploy/compose.prod.yml up -d
```
The four-role deployment sequence updates control and tenant databases before starting Worker and API. Template structure checks do not replace startup and upgrade acceptance in a real environment. After startup, check API `/livez` and `/readyz`, and `/readyz` on the Worker's health port. Nginx only proxies the API port on the edge network; MySQL, Redis, and object storage remain on internal networks. When running directly on a host, first create an empty database and set `APP_ENV` and configuration, then execute `control up`, `control verify`, `tenant-data up --target shared-control`, `tenant-data verify --target shared-control`, and `cargo serve` in that order. Default single-tenant mode also has two migration ledgers: control and `shared-control`. `verify` only checks; a new empty database requires `up` first. See the [Data Guide](data.en.md#initializing-a-new-environment) for the full procedure. After importing the complete SQL into the physical control database, run `control verify` and `tenant-data verify --target shared-control` directly without another `up`; other independent MySQL tenant targets still require their own `tenant-data up/verify`. Production defaults to and permits only `jobs.mode="external"`; starting API alone is insufficient. Prepare separate private directories containing `app.prod.toml` for API and Worker, explicitly set `APP_ENV=prod` in both terminals, and start Worker before API with each role’s own `--config-dir <directory>`. Use different `snowflake_worker_id` values while sharing the control database and scope. When continuing with the ignored directory from README, add `--config-dir .local-tests/dev-config` after `--` in this guide's Cargo alias examples that otherwise use default `config`, for example `cargo migrate -- --config-dir .local-tests/dev-config control verify` or `cargo serve -- --config-dir .local-tests/dev-config`. Keep selecting the same directory for verification, export and runtime commands to avoid connecting through a different, uninitialized configuration. A structure assertion failure in the complete SQL reports the migration, phase and category. Preserve the original output and state; an empty ledger does not establish that DDL rolled back. Inspect read-only first, without automatic replay or manually adding completion markers.

The current version only accepts new production databases. Existing real production databases from older versions require a non-destructive upgrade design and rehearsal first; reset cannot replace an upgrade. Production API instances must also receive complete `zh-CN.toml` and `en-US.toml` resources through TOML field `app.locales_dir`. The default is `locales`, resolved from the process current working directory for ordinary applications; `APP_LOCALES_DIR` is not read. Missing resources or loading failures strictly reject production startup; the development embedded fallback does not replace production resource deployment.

## Non-production Rebuilds

Rebuilds are restricted to non-production environments. See [Architecture: non-production rebuilds](architecture.en.md#non-production-rebuilds) for complete configuration, two-stage commands, ledgers, and failure recovery rules. Production permanently rejects this entry point. Rebuild verification preserves exactly one canonical data-scope projection bootstrap outbox seed for each current tenant and strictly checks its version, payload, and undelivered state; other runtime resource tables must remain empty. Preserve the scene on a seed mismatch rather than clearing events to bypass verification. For reference-fixture `environment prepare`, choose an independent new configuration directory beside the reserved service root, for example service root `run-copy-<id>` and configuration directory `env-copy-<id>`. Configuration output must not equal `review.future_root` or lie within it. The tool rejects this layout before creating configuration files or output directories and does not start services. Retain existing environments and failure evidence, use the formal review entry to select a new layout, and do not overwrite or automatically replay the original scene.

## HTTP 5xx and High Latency

Application log filtering uses the configured `logger.level`; `RUST_LOG` does not override it. To change the level while troubleshooting, edit the selected configuration file and restart the corresponding process. First inspect API logs and traces by request ID, then check databases, Redis, object storage, and Worker. After confirming a failure in a single dependency, follow the degradation policy; do not amplify the incident by increasing retries.

## Redis and Object Storage Conventions

- Redis `timeout_secs` consistently limits connections, responses, and transactions, within 1–60 seconds. S3-compatible backends use `object_storage.request_timeout_secs`, within 1–300 seconds. Do not layer unbounded retries at call sites. For Redis failures, check connection mode, TLS, ownership marker and scope prefix. If the authorization cache is unavailable, fail closed or disable caching according to configuration; never clear a shared Redis DB.
- Readiness probes only execute Redis `PING` and private object-storage bucket checks, protected by independent short timeouts. Only failures of `required` dependencies block readiness; optional dependencies explicitly enter a degraded state.
- `ryframe_connector_operations_total` and `ryframe_connector_operation_duration_seconds` only use three types of low-cardinality labels: connector, fixed operation, and result. Endpoints, tenants, Redis keys, bucket names, and object keys must not appear in metric labels.
- `Debug` output for Redis and S3 configuration hides passwords, access keys, and client private keys. Non-success S3 responses retain only a stable operation name and HTTP status and discard the remote response body; transport errors remove the request URL. File maintenance errors contain only an internal file ID, without bucket names, object keys, Authorization, signatures, or payloads.
- Deterministic tests use local implementations or offline protocol samples. Real protocol tests must be explicitly enabled and use unique schemas/namespaces with precise cleanup. `FLUSH`, `KEYS`, and deletion by ambiguous object prefixes are prohibited.

## Refresh Token Replay and Abnormal Account Recovery

Immediately revoke the token family and current session, and check the user's authorization version, client IP, and audit events. After confirming a leak, rotate the relevant credentials and retain evidence. If an ordinary account from an older development version cannot log in and its password is unknown, use the [explicit account recovery procedure](api.en.md#recovering-accounts-with-unknown-passwords); do not repeat initialization or edit password hashes directly. Disabled status and mandatory password changes are independent; a successful reset does not automatically enable the account.

## Failed or Expired Backups

The native business catalog loader reads the copy catalog from explicit Workspace members in the execution backend and consistently validates managed generated assets, content digests, module ownership, and complete table descriptors. Returned tables retain the declaration order of the Workspace and machine catalog. The complete business migration ledger column names and types come from the formal SDK DDL read by the same Rust validation entry point. Ordinary source export uses that same complete catalog for structural verification, including the ledger for registered business modules, rather than assembling another full table list. The reviewed data-copy catalog and the complete structural-verification catalog retain their respective responsibilities. Verification callers obtain results through the read-only protocol with an explicitly bound current tool; the Python bridge no longer parses catalogs independently or accepts catalog fragments. If catalog or ownership validation fails, check the execution worktree and repair managed assets through the formal generation entry point. If ledger structure validation fails, check the SDK version and DDL in the execution worktree. Do not filter unknown tables or bypass validation to continue copying. Ordinary source export first compares the ordinary and raw per-target business images, then includes the actual row counts and digests for `biz_data_scope_owner`, `biz_data_scope_dept`, and `biz_data_scope_projection` in its logical inventory. An omitted target with nonempty projections cannot be supplied as empty. This does not turn ledgers or ownership into business data. The multi-database dump directory is exclusively created once at the beginning of the batch; existing directories or payloads are never overwritten. After failure, retain the original attempt, inspect the complete scene, and use the formal recovery entry point.

The reference copy tool reads and precisely decodes complete SQL dumps in Rust, then supplies managed chunks to the existing coordinating callers without launching a subprocess for each row. Even when selecting only the tenant declaration table, it first validates the complete table catalog, all columns, and data in unselected tables. Numbers retain their exact values, and JSON rejects duplicate keys and nonfinite numbers. The result directory binds the original dump, catalog digest, file identities, and complete result digest. Each chunk read rechecks those bindings; only complete consumption followed by EOF, row-count, and source checks permits precise deletion of that result. Creation, reading, or closing failures preserve the failure scene without automatically retrying or deleting the original dump. On a formal copy failure, the command identifies its stage record and run manifest; failure.json in the copy directory records the failed phase, complete call locations and available system codes, omitting exception text, arguments and source lines. Compare complete before/after images before continuation; an error category alone does not authorize replay. If a source snapshot cannot execute Git, check the local Git installation and operating-system PATH. Application-environment switching retains allowlisted OS variables; APP_ENV still only selects application configuration files. Full-stack build and runtime verification share native source facts, checking the model file, complete Git snapshots and applicable CI identity together. Preserve the scene on a mismatch instead of manually changing original source receipts. A reported `.local-tests/sql-row-streams/sql-rows-*` directory is a local derived result, not evidence that remote copying completed. Save diagnostics and check the source and complete target image before continuing through the formal recovery entry point. Stop migration operations that depend on invalid backups, and check targets, checksums, collection times, and retention policies. Regenerate and verify backups after recovery rather than marking them successful manually. External tools back up and restore bytes; RyFrame only handles manifest collection, registration, recovery verification, state, and alerts. Source export and subsequent generation verification share the complete physical binding: database connection identities, target modes, public object-storage metadata and the overall digest must agree, without including credentials. Preserve the original export and failure evidence when a binding is incomplete or inconsistent. After checking source data and the complete target image, perform a new read-only export through the formal entry point in a new run directory; do not rewrite or re-sign the old export or automatically replay copying.

### Reference Environment and Consistency

The reference drill uses the system tenant and 10 ordinary tenants across shared and dedicated data targets, with at least 100,000 representative business records and 1 GiB of object data. External operations scheduling performs a full backup every 12 hours with at least 7 days of retention. Drill reports must record the Windows machine, MySQL/RustFS versions, storage, and network conditions. A 24-hour recovery point and 60-minute recovery time are targets that require actual verification at this scale.

Before collection starts, pause business writes and stop API write entry points, Worker, scheduler, messaging, and other producers. Maintain quiescence throughout manifest collection, database dumping, and object copying, so data from different times is not registered as a consistent backup. Database digests follow the complete primary-key order, and objects use streaming SHA-256. Manifests include source SHA, schema fingerprints, physical database identities, tenant placements, object prefixes, byte sizes, and digests, without secrets.

Post-copy administrator sessions use a separate file containing current credentials. Complete the first password change through the normal account flow, then create a private file in the backend's ignored directory, for example the absolute path `<backend>/.local-tests/clone/administrator.toml`:

```toml
[administrator]
tenant_id = "system"
username = "admin"
password = "<current-password-after-first-change>"
```

The post-copy registration request's `source_admin` contains only four metadata fields: `subject_id`, `tenant_id`, `username`, and `client_address`. Register the TOML separately as `administrator_credentials` using its `path`, `bytes`, and `sha256` file binding. Never copy the password into requests, public registrations, or receipts. The tenant and username in the file must match the metadata. The file and every path component must have no links and remain inside the current backend's `.local-tests`. Registration and session startup verify the file binding before and after reading. Content or binding changes, invalid fields, and TOML parsing failures stop execution without echoing the source text. After login, the authoritative `SessionContext` must explicitly report the root field `password_change_required` as the Boolean `false`; `true`, a missing field, or an incorrectly typed field prevents business actions. This password is independent of `bootstrap.admin_password`: tools never change passwords automatically, fall back to initialization passwords, or replay business writes. If the first password change is incomplete, finish the explicit account flow rather than registering the initialization password as current credentials.

Continue to register explicitly through `cargo xtask check recovery clone post-copy --run-dir <run> --operation register --request <request.json> --write`; subsequent operations that write still require `--write`. The file bound by `api_environment` accepts only `{"environment":{"APP_ENV":"test"}}`, with no administrator credentials or other project configuration. Addresses, Worker mode, CORS, and other settings come from their bound application TOML files. An amendment may rebind the environment selector only after the existing stop-evidence and failure-reconciliation flow; environment fields cannot modify project configuration. The read-only post-copy pacing binding uses the explicit request's `frontend_root`, with no fixed directory name or sibling topology and no second frontend selection from `tools.toml`. The native entry checks existing absolute directories without links, the exact `post-copy/login-budget.json` position in the current run, and the SHA-256 bindings of the Python tool and that frontend's `scripts/browser-login-budget.mjs`; drift is rejected without creating or overwriting budget state. Business semantics of `contract` remain validated at the existing session stage. The session's `app_config_dir` is resolved from the frozen target registration through the existing configuration-directory verifier, never from another environment or post-copy request directory.

### Collection and Registration

Historical producer checks on Windows first read the kernel identity. Only an absent process or a strictly later creation time for the same PID proves that the recorded generation has ended. A managed Rust child queries local CIM only when the kernel query reports access denied (error code `5`), with a 15-second query timeout budget. CIM retains microsecond precision: its creation time must be strictly later than the recorded time plus 10 ticks of 100 ns each. The same generation, an adjacent precision boundary, duplicate identities, unknown timestamps, and query failures reject registration. This path no longer falls back to PowerShell/PDH and never signals the process currently using that PID. When an error includes a CIM HRESULT, inspect the local service with `Get-Service Winmgmt` and check read access to `ROOT\CIMV2`. After repair, rerun the original verification command. Preserve existing stage results and partial files, and recover according to their actual state; never manually mark a process as stopped or automatically replay data writes. `Get-Service Winmgmt` is for manual troubleshooting only, not a runtime fallback.

Use `cargo xtask data` on a Windows maintenance machine for backup and recovery registration. Keep configuration and secrets in a controlled ignored directory. This maintenance capability is not included in production runtime images.
```powershell
cargo xtask data --help
cargo xtask data backup inventory --output <absolute-new-file-in-backend-workspace/.local-tests> --source-sha <exact-backend-sha> --quiesced-at <writes-quiesced-at-rfc3339>
```
`backup inventory` and `target inventory` are explicitly selected read-only inventory operations. They only atomically create new evidence files with create-new semantics inside the current backend's `.local-tests`, without modifying databases, objects, or registration state, so they do not use `--write`; the output file must not already exist. External tools then copy and verify the exact databases, tables, and object prefixes from the manifest, and fill in `id`, `completed_at`, `retention_until`, and `artifacts` to form a `BackupManifest`. Every `db:<logical-target-key>` and `objects:<bucket>` must have at least one file artifact recording its `relative_path`, `bytes`, and `sha256`; relative paths must not escape the backup root. See `crates/ryframe-application/src/ports/backup/manifest.rs` for the structure definition.

To inspect targets without assigned tenants or state before and after initialization, use `cargo xtask data target inventory --target <configured-target-key> --output <absolute-new-file-in-backend-workspace/.local-tests>`. This command connects only to explicitly configured databases, validates schema and the exact complete table catalog, and calculates full row digests in a read-only transaction. `target.database` stores business tables and placements; `target.preserved_tables` separately stores ownership, migration ledgers, and backup/recovery registration tables. It does not access object storage or modify the target, and does not omit unused targets as an "empty manifest." Consistency between the control database and dedicated targets still requires externally stopping all producers; a single target inventory does not establish successful backup or recovery.

```powershell
cargo xtask data backup register --manifest <absolute-manifest-in-backend-workspace/.local-tests> --backup-root <registered-external-absolute-backup-directory> --write
cargo xtask data backup status
```
Registration rereads files to verify size and SHA-256; missing or corrupted files are registered as invalid and return failure. Repeated verification under the same backup ID is only allowed for the same manifest, without replacing data. Successful registration means backup files have been verified, not that recovery has succeeded. Status queries only read the control database and do not depend on current object-storage connectivity.

### Isolated Recovery and Acceptance

1. Prepare new isolated databases and object prefixes, initialize them against the current baseline, and establish target ownership. First initialization registers ownership automatically. For an existing unmarked database, stop producers and review and execute `ownership-adopt` as described in the [data guide](data.en.md#initial-ownership-registration-and-explicit-adoption-of-existing-databases); do not guess markers, rerun `up` to claim it, or substitute `reset`. If commit outcome is unknown, `inspect` the original plan first. Keep logical target keys consistent, but physical databases, scope, JWT secrets, and Redis namespaces must differ from the original environment; Worker uses external mode. The maintenance command's `--config-dir <directory>` selects source-side registration database configuration, while `--restore-config-dir <directory>` selects only isolated recovery target configuration. Check physical identities, scope and endpoints in both plaintext files to avoid mixing source and target. Application-relative configuration directories resolve from the command's current working directory; absolute paths are recommended. Product `backup-register`, `restore-begin`, and subsequent verification state all write to the source-side registration database.
2. Following `crates/ryframe-application/src/ports/backup/restore.rs` and its `RestorePlan`, fill in the complete targets, fault time, frontend SHA, API/Worker readiness addresses, and new object prefixes. Physical database identities must match and must not point to any original business database.
3. Execute `restore-begin` before external restoration starts. Repeating the same plan does not reset timing. External restoration only overwrites the verified isolated resources in that plan and retains the target's own ownership and backup registration metadata. Database dumps contain only business tables in the manifest and must not execute `USE` targeting source databases, database creation, or cross-database statements. Object paths only replace the scope prefix and must not copy source ownership markers.
4. Stop target business writes and execute `restore-verify-data`. It revalidates backup files, current schema, complete table contents, tenant relationships, and the complete object set. Missing, extra, corrupted, or incorrectly owned data causes failure.
5. Start API, Worker, and frontend with entirely new Redis temporary state, complete real browser business acceptance, then submit a `RestoreBusinessProof` binding the drill ID, plan hash, source SHA, scope, and time range. `restore-verify` checks both readiness probes again and only records success when data and business verification both pass, total elapsed time does not exceed 60 minutes, and the backup recovery point is no more than 24 hours before the fault.

Run `cargo xtask data restore begin --plan <absolute-plan> --output <absolute-new-running.json> --restore-config-dir <absolute-target-configuration> --write`, `cargo xtask data restore verify-data --id <drill-id> --backup-root <absolute-backup-root> --output <absolute-new-data-verified.json> --restore-config-dir <absolute-target-configuration> --write`, and `cargo xtask data restore verify --id <drill-id> --proof <absolute-business-proof> --tests-receipt <absolute-test-details> --runtime-receipt <absolute-runtime-receipt> --target-plan <absolute-target-plan> --runner-root <absolute-clean-test-runner-worktree> --restore-config-dir <absolute-target-configuration> --write` in that order. Plans, proofs, receipts, and outputs must be descendants of the current backend's `.local-tests`; backup roots, isolated configurations, and clean runners may use registered external absolute directories. No path may traverse symbolic links or reparse points. Input files and directories must exist; output parent directories must exist and target files must not exist. These conditions and `--write` are checked before maintenance binaries start or resources are connected. After business success, a temporary file is written and synchronized in the same directory, atomically published with create-new semantics, then reread to verify canonical bytes, JSON, and paths. Argument errors, business failures, or existing targets do not create or truncate success records. If publication or revalidation fails after business writes succeed, retain registration-database state and any published files, perform a read-only status check first, and do not replay blindly. The running record published by `restore-begin --output <new-file>` is then passed to the external recovery stage.
