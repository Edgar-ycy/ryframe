# 容量测试与验收标准

> 最后核对：2026-08-13

容量测试的目的不是得到单一“最大 QPS”，而是证明目标部署规格在峰值、故障和恢复时
仍满足服务等级。正式验收应使用能输出分位数、稳定速率和失败明细的工具，并保存原始结果。

## 1. 测试前提

- 环境拓扑、实例规格、MySQL/Redis/对象存储版本与生产一致，数据量至少达到预计
  90 天规模；禁止使用本地内存替代生产依赖。
- 使用脱敏测试数据和独立测试租户。认证、权限、租户过滤、上传下载都必须走真实链路。
- 先定义预计峰值 RPS、并发会话、登录占比、读写比、上传大小及批处理规模。没有业务
  预测时，以最近峰值的 2 倍作为临时验收负载，并在报告中标记假设。
- 监控覆盖应用、Nginx、MySQL、Redis、对象存储和主机。测试前确认时钟同步、无发布
  任务、无备份争抢，并记录版本 SHA 和完整配置（密钥除外）。

## 2. 标准场景

| 阶段 | 负载 | 持续时间 | 目的 |
| --- | --- | --- | --- |
| 预热 | 0.5 倍预计峰值 | 10 分钟 | 建立连接池和缓存 |
| 基准 | 1.0 倍预计峰值 | 30 分钟 | 验证正常峰值 SLO |
| 安全余量 | 1.5 倍预计峰值 | 30 分钟 | 证明发布和流量波动余量 |
| 短时突发 | 2.0 倍预计峰值 | 5 分钟 | 验证限流和排队边界 |
| 稳态耐久 | 1.0 倍预计峰值 | 4 小时 | 检查泄漏、漂移和存储增长 |
| 单实例故障 | 1.0 倍预计峰值并摘除一实例 | 15 分钟 | 验证容量冗余与恢复 |
| Redis/对象存储故障 | 受控注入 | 各 10 分钟 | 验证 fail-closed、告警和恢复 |

登录和密码哈希是 CPU 密集链路，必须单独测试；文件场景至少包含 1 MiB、5 MiB 头像
和 10 MiB 普通文件。不得用 `/livez` 或 metrics 请求量代表业务吞吐。

## 3. 默认验收门槛

在业务尚未定义更严格 SLO 前，所有门槛同时满足才算通过：

- 基准与安全余量阶段：业务请求成功率 `>= 99.9%`，非预期 5xx `< 0.1%`；
  P95 `<= 500 ms`、P99 `<= 1 s`。上传/导入另按文件大小设 SLO，不混入普通 API。
- 短时突发：服务不得崩溃或产生数据错误；拒绝必须是受控 `429/503` 并包含可重试语义；
  突发结束后 5 分钟内 P95、连接数和队列恢复至基准的 20% 范围内。
- MySQL 活跃连接持续低于上限 80%，Redis 不发生内存淘汰或 required 模式降级，
  CPU 持续低于 70%，内存无单调增长，磁盘测试后保留至少 20%。
- 故障注入期间不得越权、跨租户、发放不可信会话或丢失已确认数据；依赖恢复后
  10 分钟内 readiness 恢复且无需清理安全状态。
- 耐久测试首尾 30 分钟相比，稳定负载下 RSS、连接数和对象 pending/cleanup 数量
  不得持续增长；增长超过 10% 必须解释并复测。

限流产生的预期 `429` 只能在突发场景单列，不能从基准阶段成功率分母中删除。客户端
超时、连接重置和响应校验失败均计为失败。

## 4. 后台任务与 Outbox 验收

后台任务和 Outbox 必须在与生产一致的 MySQL、Redis、Worker 并发和 Jobs 配置下单独留存验收
记录，不能以 API 请求吞吐替代：

- 在空队列稳定运行 5 分钟，对比优化前相同配置的数据库 SQL 计数，任务与 Outbox 轮询相关 SQL
  总量必须下降至少 80%。
- Redis 或进程内唤醒正常时，新任务从提交到被领取的 P95 不高于 1 秒；人为丢弃提示时不高于
  `max_idle_poll_interval_ms × 1.2`，且任务仍必须由 MySQL 轮询领取。
- 默认配置下，崩溃任务在租约到期后不晚于 16 秒恢复；任意有效配置的上限为
  `lease_recovery_interval_seconds + 1` 秒调度误差。
- 每轮任务指标采集最多执行两条 SQL。领取、条件聚合统计和深分页候选都应保存
  `EXPLAIN ANALYZE` 证据；只有代表性数据的耗时或扫描行数改善至少 30% 时，才能新增或调整索引。

验收报告需同时保留 Redis 订阅断开、重复/未知唤醒负载、提示丢失和进程优雅关闭的结果，证明
唤醒只是延迟优化而非业务可靠性前提。

## 5. 容量模型

### 数据生命周期与异步导入

数据保留和异步导入必须使用代表性历史规模单独验收，不能只以普通 API 延迟代替：

- 清理预览、各资源候选选择和趋势时间桶查询都保存 `EXPLAIN` 证据，确认命中新迁移索引；不得因新增索引破坏任务领取、租约恢复或现有列表查询。
- 默认单资源单次清理上限为 50,000 条。运行达到上限时必须稳定返回 `partial`，下一次继续且不重复统计已经删除的记录。
- 分别验证 1、100、10,000 和 20,000 行用户导入；20,000 行边界应记录总耗时、Worker CPU/RSS、Argon2 阻塞线程并发、数据库连接峰值、对象存储吞吐和每批提交延迟。
- 中断 Worker 后重启，导入必须从已提交游标继续；重复用户名、失败行和取消不得重复创建用户或绕过租户配额。
- 同时运行清理、导入、导出、Outbox 和普通任务，验证优先级与连接预算不会让在线 API 超过 SLO。
- 对象容量至少覆盖活动导入源文件、错误报告、通用上传、导出文件和保留窗口内的增长，并预留失败重试与清理延迟空间。

### 租户配置包与迁移

配置迁移容量验收必须同时覆盖压缩包、解压数据、MySQL 写事务和对象快照，不得只测上传接口：

- 默认边界为压缩包 5 MiB、解压后 20 MiB、最多 10,000 项；分别验证恰好达到边界和超过边界，
  超限必须在进入应用事务前以受控 `400/413` 拒绝。
- 使用正常包、异常高压缩比包、额外或重复 ZIP 项、路径穿越、加密 ZIP、过深 JSON、SHA-256
  不一致和重复稳定键做安全验收；拒绝时不得遗留可用业务记录或未受控对象。
- 用部门、岗位、字典、portable 参数、权限、菜单、角色和关系的代表性组合跑满 10,000 项，记录
  解析/规范化耗时、Worker CPU/RSS、对象存储吞吐、快照大小、最终事务耗时、锁等待和副本延迟。
- 同一租户同时发起两个应用/回滚以及普通配置写请求，验证锁顺序固定为“租户行 → 配置租约 →
  资源/关系行”，无死锁、无旧快照覆盖，并且冲突稳定返回 `409`。
- 预览后修改目标资源，再应用旧计划，必须因 `configuration_version` 或
  `authorization_epoch` 变化拒绝；重新预览后才能继续。
- 快照上传失败不得修改数据库；应用中任意写失败必须整体回滚。168 小时回滚窗口内完成成功、
  版本冲突、新引用冲突和快照不可用场景，并证明回滚不删除目标端独有资源。
- 对象容量预算至少包含来源配置包和应用前快照各 168 小时窗口、并发迁移、失败重试与安全清理
  宽限。配置包/迁移历史元数据没有已配置的自动删除期，不能按对象窗口推导其数据库增长上限。

### 平台租户容量治理

容量治理验收使用系统租户和具有 `tenant:list`、`tenant:usage:list` 的受控平台角色。原有租户列表
接口必须保持兼容；新分页接口默认 20 条、最大 100 条，并覆盖租户标识、名称、启停、到期和容量
状态筛选。普通租户访问分页、详情或用量接口必须返回 `403`，只有基础列表权限的系统租户角色不能
看到用量字段，也不能按容量状态筛选。

用户、角色和存储使用与写入配额校验相同的主库口径。验收数据至少覆盖 79.99%、80%、89.99%、
90%、99.99%、100% 和超过 100% 的边界，分别得到 `normal`、`warning`、`critical`、`exceeded`；
三类配额的 `0` 都必须表示 `unlimited`。整体状态取三项中最严重状态，请求限流窗口不能改变整体
状态。文件占用必须来自 `sys_file` 元数据，不能以对象存储目录扫描结果替代。

对 20 和 100 条页面分别记录 SQL 次数与执行计划。页内用量必须使用单次条件聚合，租户数增长时查询
次数保持不变，不允许出现逐租户用户、角色、文件、后台任务、计划或导入计数。使用代表性数据确认
以下索引被容量聚合使用：`idx_user_tenant_del`、`idx_role_tenant_del`、
`idx_file_tenant_del_size`、`idx_schedule_tenant_del_enabled`。

请求用量只验证当前一分钟窗口的计数、上限和剩余秒数，不采集或声称提供历史请求趋势。Redis 正常
时读取快照不得增加计数；Redis 故障时只有请求窗口变为 `unknown`，主库三类资源和辅助汇总仍应
成功。页面进入、翻页、筛选、打开详情与手动刷新会产生查询，但空闲页面不得持续轮询。Prometheus
容量与接口指标不得增加租户 ID 标签；容量状态和租户明细只通过受权限保护的 API 查询。

运维趋势固定最多 28 个时间桶，但底层历史数据仍按租户与时间窗口扫描。容量报告必须覆盖高活动租户和空活动租户，验证零值补齐不会掩盖慢查询或跨租户统计。

实例数至少满足以下两项中的较大值，并额外保留一个实例故障的容量：

```text
按吞吐 = ceil(预计峰值 RPS × 1.5 / 单实例验收 RPS)
按并发 = ceil(预计峰值并发 / 单实例验收并发)
```

数据库连接预算：

```text
应用实例数 × 每实例 max_connections
+ 迁移、备份、监控和人工运维预留
<= MySQL max_connections × 0.8
```

本地对象存储仅允许单实例或所有实例挂载同一个具备所需一致性语义的共享卷。多实例
生产优先使用 RustFS/MinIO/S3，并把对象容量、请求率和故障域纳入同一容量报告。

## 6. 交付证据

容量报告必须包含版本 SHA、拓扑规格、数据规模、负载模型、每阶段实际 RPS/并发、
成功率、状态码、P50/P95/P99、资源曲线、依赖指标、告警触发记录、故障时间线和恢复
时间。保留工具配置及原始结果，结论需明确“通过/不通过”和生产建议上限。任何配置、
代码或基础设施变化都会使旧结论失效，至少重跑基准、安全余量和受影响场景。
