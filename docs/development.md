# 开发指南

[English](development.en.md)

产品套餐的能力选项来自后端编译目录和前端 feature manifest。基础管理功能保持可用并遵循 RBAC，通知公告与租户主动消息发布可以按套餐启停。首批能力使用 `standard` 变体和严格空对象配置；停用公告后管理与读取入口关闭，停用主动消息后拒绝新的发布，已有数据和已接受消息保留，系统通知继续运行。租户、产品套餐、数据目标及平台基础设施管理属于系统租户，不能通过普通租户的权限通配符、菜单授权或配置包开放。系统租户具备已部署的管理能力，仍受实际基础设施可用性校验。

## 环境与配置

本机开发验证使用 Windows；原生构建需先准备目标架构的 MSVC C/C++ 工具和 Windows SDK，安装方法见 [rustup 官方前置说明](https://rust-lang.github.io/rustup/installation/windows-msvc.html)。其他原生构建工具（例如 CMake、NASM）按所选目标和锁定依赖的实际要求准备。MySQL 8.0.16 或更高版本、Redis 7.x 协议环境和 RustFS/MinIO/S3 兼容存储可以运行在任意满足版本、协议及连接要求的平台，也可以连接远程服务；不要求使用 WSL。安装 rustup 后，在项目目录运行 `rustup show` 安装并选择固定的 Rust 1.100.0、rustfmt 和 Clippy；项目使用 Rust 2024 edition，最低 Rust 版本为 1.100，本地、CI 和生产构建镜像使用同一固定工具链。 `APP_ENV` 是唯一项目配置环境入口，例如 `$env:APP_ENV = "dev"`，只接受 `dev`、`test`、`prod`。`config/app.toml` 可省略，所选 `config/app.<environment>.toml` 必须存在；省略公共文件时，环境文件须完整提供必填配置，已存在但损坏或不可读的公共文件仍失败。地址、密码、JWT、Redis、存储和监控凭据直接使用明文配置字段；真实配置保存在仓库外的私有目录，不提交凭据。应用通过 `--config-dir <directory>` 选择目录，默认 `config`，相对路径以当前工作目录解析。数组在环境文件中整体替换，修改一个副本、source 或租户目标时必须重写整个数组。完整规则和示例见[数据指南](data.md#文件配置与凭据)。`app.locales_dir` 在 TOML 中显式指定，默认 `locales`；普通应用相对进程当前工作目录解析，不相对配置目录，也不读取 `APP_LOCALES_DIR`。目录包含 `zh-CN.toml` 和 `en-US.toml`；资源缺失或加载失败时，生产严格拒绝启动，开发环境可内嵌回退。部署模板与私有配置目录的资产结构、CI 工具测试已通过；真实容器、镜像和部署整链仍未验收，局部检查不代表整体门禁。 受管存储只读观察与初始化命令共用操作系统运行环境白名单，并以已绑定的私有环境覆盖同名系统字段；不会继承额外的 `APP_*` 配置或凭据。Windows 平台工具需要 `SYSTEMROOT`、`USERPROFILE` 等标准运行字段，不能把“应用仅保留 `APP_ENV`”误解为清空操作系统环境。若固定观察命令失败，核对工具、系统运行环境及进程观察权限，保留失败目录；不得据此认定服务已停止，也不自动重放或清理。

## 启动后端

在 Git 工作树之外选择一个私有配置目录。从后端根目录运行以下命令，把公共和开发样例复制到并列的新目录 `../ryframe-dev-config`。这是后端启动所用的私有配置位置，仓库内的运行目录由工具按需创建。已有适用的配置可直接用 `--config-dir` 选中，复制命令会在目标已存在时停止，以保留原文件。

- `if (Test-Path -LiteralPath ../ryframe-dev-config) { throw "Configuration directory already exists; preserve it and choose a new directory" }`
- `New-Item -ItemType Directory -Path ../ryframe-dev-config -ErrorAction Stop | Out-Null`
- `Copy-Item -LiteralPath config/app.toml,config/app.dev.toml -Destination ../ryframe-dev-config -ErrorAction Stop`

在编辑器中打开 `../ryframe-dev-config/app.dev.toml`，填写真实数据库、JWT、Redis、存储及 `[bootstrap] admin_password`，不修改受版本控制的原始样例，也不把密码放入命令参数。先设置 `$env:APP_ENV = "dev"`，并确保已创建空 MySQL database；若另选配置目录，须同步替换后续绑定 `../ryframe-dev-config` 的路径。从后端根目录按 [README：下载后首次运行](../README.md#下载后首次运行)的同目录命令，依次初始化、校验两个账本并启动后端。`control verify` 只校验，不能初始化新空库；控制库和默认 `shared-control` 租户数据面有不同账本，两者都要完成初始化和校验。API/Worker 启动只做结构校验，不自动执行 DDL。完整步骤、SQL 导入和多目标说明见[数据指南](data.md#全新环境初始化)。

非生产默认 `jobs.mode="embedded"`，`cargo serve -- --config-dir ../ryframe-dev-config` 已消费后台任务。独立 API／Worker 必须使用两份实例配置；以下示例从后端根目录开始，要求两个目录都是全新目录，任一目录存在就停止，不覆盖用户真实配置。从刚才已填写真实值的 `../ryframe-dev-config` 复制公共配置和 dev 配置，不再复制受版本控制的空样例：

- `if ((Test-Path -LiteralPath ../ryframe-api-config) -or (Test-Path -LiteralPath ../ryframe-worker-config)) { throw "Configuration directory already exists; preserve it and choose two new directories" }`
- `New-Item -ItemType Directory -Path ../ryframe-api-config,../ryframe-worker-config -ErrorAction Stop | Out-Null`
- `Copy-Item -LiteralPath ../ryframe-dev-config/app.toml,../ryframe-dev-config/app.dev.toml -Destination ../ryframe-api-config -ErrorAction Stop`
- `Copy-Item -LiteralPath ../ryframe-dev-config/app.toml,../ryframe-dev-config/app.dev.toml -Destination ../ryframe-worker-config -ErrorAction Stop`

在编辑器中打开 `../ryframe-api-config/app.dev.toml` 和 `../ryframe-worker-config/app.dev.toml`：将各自文件顶部的根字段分别设为 API `snowflake_worker_id=1`、Worker `snowflake_worker_id=2`，在两份文件的 `[jobs]` 中均设置 `mode="external"`；同一部署的 `scope_id`、数据库、Redis 与 JWT 配置保持一致。密码只在配置文件中编辑，不放入命令参数。保存后另开两个 PowerShell 终端，各自先设置下面的 `APP_ENV`，分别执行 API 命令或 Worker 命令；`--` 将参数传给对应应用：

- `$env:APP_ENV = "dev"`
- `cargo serve -- --config-dir ../ryframe-api-config`
- `cargo worker -- --config-dir ../ryframe-worker-config`

前端单独运行 `corepack pnpm dev`。非生产重建使用直接入口 `cargo reset`；执行前先停止全部生产者，完整安全步骤见[运维指南](operations.md#非生产重建)。 Worker 未消费任务时，确认文件配置 `jobs.mode="external"` 并检查健康端口、lease 和数据库连接；Redis 或对象存储故障按运维指南核对 `scope_id`、连接模式、TLS、ownership marker 与服务端口。

## 数据库迁移

控制库使用默认目标；租户数据可操作全部已登记目标或单个目标。常用命令为 `cargo migrate -- --config-dir ../ryframe-dev-config control status`、`cargo migrate -- --config-dir ../ryframe-dev-config control verify`、`cargo migrate -- --config-dir ../ryframe-dev-config control up`、`cargo migrate -- --config-dir ../ryframe-dev-config tenant-data status --all`、`cargo migrate -- --config-dir ../ryframe-dev-config tenant-data up --target <target-key>` 和 `cargo migrate -- --config-dir ../ryframe-dev-config tenant-data verify --target <target-key>`。租户目标使用配置键而非数据库名；`--all` 只处理已登记目标，多个目标会先做物理身份预检，相容共享别名可以合并，dedicated、多个既有路由及组外 fence 仍在 DDL 前拒绝；代表键规则见[初始化与归属接管](data.md#首次初始化与既有数据库归属接管)。修改迁移源码后，用 `cargo xtask data migrate check` 只读检查历史与注册，提交前用 `cargo xtask data migrate check --require-frozen`；开发版重整基线显式执行 `cargo xtask data migrate baseline --write`，稳定版只追加并执行 `cargo xtask data migrate freeze`。生产配置仍保持 `database.migration_mode="verify"`，DDL 只由显式迁移命令执行，迁移历史维护命令不连接数据库。 初始化前在 `[bootstrap]` 中显式填写 `admin_password`。密码须包含大小写字母、数字、符号，长度为 8～72 个可见 ASCII 字符；JWT 使用 `auth.jwt_secret`，监控 token 使用 `monitor.metrics_bearer_token`。根 TOML 字段 `snowflake_worker_id` 必须在同一部署的每个实例上不同。普通初始化用户 `user`、新建及批量导入的普通用户使用 `123456`，每个新账号首次登录都必须改密。已有正常账号不会被重复初始化重置。 启动报告迁移不一致时，先检查 status 与 verify 结果，再决定是否执行 up。

## 创建业务 crate

默认在隔离副本预览骨架和锁文件，`--write` 才统一安装；离线解析只允许新增本次本地业务包，不升级、换来源或移除已有锁定依赖。原项目需有有效 Cargo.lock 和已安装的锁定依赖，缺失时明确报错且不安装半个 crate。创建事务更新业务 crate 的 `kind = "business"` 元数据和 SDK feature、工作区成员、组合根的可选依赖与 API/Worker/迁移/数据维护 feature，以及 `business_modules()` 注册；不会生成 CRUD 或操作数据库。命令和 Builder 均接受模块名 `order` 或包名 `order-business`，显式名称决定新包，不使用配置中的默认包。模块名须以小写字母开头。已有 crate、重复注册或计划生成后的并发修改均拒绝覆盖；中途失败尝试恢复原文件，回滚未完成时保留并指出恢复目录。Windows CRLF 输入按原始字节校验后输出 LF。 业务 crate 的 `src/resources/`、`src/extensions/` 与 `migrations/` 保存手工代码和本模块迁移，可重生成代码统一进入 `src/generated/{entities,dto,repositories,services,handlers,openapi,models,resource_catalog}`，`.ryframe/generated.toml` 记录 ownership。脚手架已生成 `src/lib.rs` 的模块装配；模块名中的中划线在 API 路径、operation ID 和页面路径中统一为下划线；权限段及菜单路由键统一使用中划线，例如 `sales-orders.order-item`。业务菜单标题键由资源名转换为小驼峰，例如 `order_item` 对应 `orderItem`；与现有翻译键冲突时停止组合。资源在 `resources/mod.rs` 的 `descriptors()` 中登记，例如 `vec![<Order as ryframe_sdk::ResourceModel>::descriptor()]`。

模型级 `#[resource(primary_key = ["tenant_id", "id"])]` 可明确索引顺序，与字段顺序独立，列表须恰好包含全部主键标记字段，省略时沿用字段顺序。反向导入从 PRIMARY 索引读取顺序，将业务主键映射到 Rust `id` 并用 `column="order_id"` 等属性保留物理列名；与已有 `id` 列冲突时拒绝生成。实体按主键顺序声明字段，DDL 保留原物理列顺序。租户主键必须以 `tenant_id` 开头，其他复合主键明确阻断，不自动修改原库。审计时间列组可省略，此时物理删除或软删除均不补写时间列；已声明的时间及操作者字段仍严格校验并由 Service 管理，请求级操作审计继续遵循原有事务策略。 模型使用 `#[derive(ryframe_sdk::ResourceModel)]`。在 `resources/mod.rs` 定义模型后，将其描述符加入同文件的 `descriptors()`。`database="tenant"` 用于租户业务，表以 `biz_` 开头并把 `tenant_id` 放入联合主键；`database="control"` 用于无 `tenant_id` 的全局业务，Service 与持久化只允许系统租户访问，页面资产携带同样的访问限制。启用多租户不会使全局业务共享，跨租户共享读取须编写明确的用例扩展。ID 默认由应用生成雪花值；数据库自增主键使用 `#[resource(primary_key, auto_increment)] pub id: i64`（无符号列使用 `u64`），不声明默认值或表单写入。生成器为租户复合主键补充以 id 开头的非唯一索引，插入时省略 ID，在同一事务中取得实际自增值。

数据范围字段用 `#[resource(..., owner_field = "owner_id")]` 声明；字段必须是同一结构体中保存用户 ID 的 `i64` 或 `Option<i64>`，租户业务和控制库全局业务都可声明，后者仍保持系统租户专用访问。生成器把该值写入 `resources.json` 和 OpenAPI `access.owner_field`，创建时总写入当前用户（可空字段为 `Some(user_id)`），标准更新不接受改值。列表、详情、锁定更新和删除按当前角色数据范围过滤：全部数据不过滤，本人匹配当前用户，部门、部门及子部门或自定义部门范围展开为可访问 owner 集合；无范围时为空或不存在。租户业务读取锁定当前投影，控制库范围读取走主库。 `owner_field` 不能替代 `tenant_id`、RBAC 或服务端授权，也不提供任意表达式过滤或逐行共享 ACL；转移归属或额外共享需要明确扩展。省略时不按创建人过滤；字段缺失、类型错误、名称为空或含空白、重复属性都会在宏展开或生成预检时拒绝。

模型驱动新建从 `ResourceModel` 生成 CRUD、迁移和受管资产；已有数据库用 `schema-import` 只读反向生成模型、CRUD 和迁移；运行目标已有表和业务行时，模型与历史迁移匹配后还必须显式 adopt，adopt 只登记结构，不执行建表 DDL 或改写业务行。`generator.source` 或 `--connection` 只决定结构来源，可取 `primary`、`sources.<name>` 或 `tenant_data.targets.<target-key>`；`storage` 或 `--database` 单独决定运行范围 `control|tenant`，二者不会自动映射。`source="local"` 在 control 范围读 primary，在 tenant 范围读 `tenant_data.default_target`，后者必须是 MySQL 目标；import 示例使用显式 primary。 资源生成前先编写并登记模型。
业务 crate 与资源生成命令见 [README：开发业务](../README.md#开发业务)，省略 `--write` 时预览。

命令可从工作区根目录或业务 crate 的 `src` 等子目录执行；生成器默认读取后端 `workspace/config`。`--config-dir <directory>` 与 Builder `.configuration_directory(path)` 的相对路径统一以后端 Workspace 根目录解析。优先级为显式 CLI/Builder、本机 `.local-tests/tools.toml`、公共 `config/tools.toml`、`workspace/config`；`[generator] config_dir` 可省略，工具文件不通过环境变量覆盖。预览在隔离缓存编译模型、生成 CRUD 与迁移并报告差异；`sync_frontend=true` 或 `--sync-frontend` 还会导出本次候选 OpenAPI、同步 typed caller、生成列表表单和路由，并执行前端类型与 lint 检查。需先安装前端依赖；业务页面模板由前端仓库的 `scripts/resource-render/` 维护，后端通过固定 Corepack 入口传递已校验 IR，校验返回资产的版本、完整集合、归属和路径后才进入受管安装。候选副本复用 package.json 完全匹配的已安装前端环境，依赖不完整时直接报错，不隐式安装或改锁文件。`--no-sync-frontend` 可临时关闭，并且不调用前端渲染器。全部成功后，`--write` 统一安装两仓受管文件；并发改动拒绝覆盖，失败回滚未完成时报告备份路径。默认页面使用生成的 page.vue，模型的 `frontend_page="@/views/…/index.vue"` 可指定手写页面。`resource` 不写手写目录或覆盖历史迁移。描述符 reader 离线使用 Workspace 锁定版本、来源、校验和及 patch，不修改项目锁文件。生成器构建缓存用工具文件的 `generator.target_dir` 选择（本机文件优先），相对后端根解析，也可显式设置无链接的绝对目录，缺省为 `target`；不从 `CARGO_TARGET_DIR` 读取生成器缓存选择。bootstrap、catalog 和候选流水线共用该缓存根；嵌套业务夹具把协调器选定目录写入其本机工具文件，所有 Cargo 构建显式复用，避免深层路径。真实两表反向导入验收在新建业务前，将既有 `resource-workspace-control.json` 的 `target_dir` 写入候选本机 `generator.target_dir`，同步前端时保留它；缺少控制文件时仅核验后端，已有文件无效则失败，不伪装为跳过。该验收沿用正式配置语义：公共 `app.toml` 可省略，选中的 `app.test.toml` 必须存在；捕获时的文件缺失也会冻结，私有副本不创建空壳，后续出现或漂移均停止导入。夹具沿用脚手架已审查的锁文件增量登记，不重新解析全部依赖；实际编译保持 `--locked`。配置支持 `package`、`models`、`tables`、`source`、`storage`、`strip_table_prefix` 和 `sync_frontend`；`resource --models Order,OrderItem` 覆盖模型列表，`import --tables biz_order,biz_order_item` 选择完整表批次。`run` 根据 tables 是否为空选择导入或模型生成，导入需 `--features schema-import`；`--plan` 的工具内任务只列同一执行计划，不编译业务描述符、不连接数据库、不创建锁、生成缓存或报告，也不写入生成目标。`cargo generate` 与 `cargo xtask` 是现有 `cargo run` 别名：首次启动或工具源码变化时，Cargo 仍可能先编译工具并写入构建目录。若需避免这一步写入，先显式构建，再直接运行 Cargo 返回的同一工具二进制及 `--plan`；无需安装其他生成器或增加入口。 脚手架已经在 `crates/ryframe/Cargo.toml` 添加 `order-business` 依赖，并在 `crates/ryframe/src/business.rs` 的 `business_modules()` 中加入 `order_business::module()`。API、Worker 和迁移程序会读取同一列表。模块名、资源名、表名、路由、OpenAPI operation/schema 和依赖循环在启动前校验。生成的 `access.toml` 与 `access.rs` 由模型维护，脚手架通过 `.access_catalog(generated::access::CATALOG)` 接入模块；已有手写装配须补上该调用再重新生成，不能只登记资源而遗漏访问目录。默认模块父目录自动生成，`menu_parent` 可复用已有框架目录；目录、页面或权限冲突会整批停止。审阅生成结果后执行 `cargo migrate -- --config-dir ../ryframe-dev-config control up`、`cargo migrate -- --config-dir ../ryframe-dev-config control verify`；服务启动不自动补写菜单权限。新租户管理员默认获得租户业务 CRUD，普通用户和扩展操作手工授权；系统租户专用业务不复制到普通租户。已有租户不自动增加角色授权。
维护三角色构建也使用当前执行后端的 `generator.target_dir`：先读公共 `config/tools.toml`，再由 `.local-tests/tools.toml` 覆盖；显式配置时与生成器共用缓存。未配置时保持 `target/ci/backend`。构建和所有维护收据读侧使用同一 Rust 解析，不以宿主 `CARGO_TARGET_DIR` 覆盖。修改缓存配置后，旧收据不能冒充新配置构建，须保留旧证据并显式构建新产物。

反向导入只读读取选中表，整批预检名称、模型、文件与 `descriptors()` 显式 vec 列表，在候选工作区编译模型并继续生成 CRUD 与迁移；发生冲突整批停止，不覆盖手写模型。`--strip-table-prefix biz_` 仅改变资源、模块及类型名，保留物理表名；租户目录要求表名带该前缀。原始列类型、默认值、索引、外键及 schema 保存在 `.ryframe/imports/`。`source=primary`、`sources.legacy` 或 `tenant_data.targets.<key>` 决定只读来源，`storage=control|tenant` 决定运行范围，二者独立。开启前端同步时也校验本批契约和页面；生成结构与来源不一致会整批停止，不安装半批模型。物理外键通过结构体 `resource(foreign_key(...))` 属性保留，不自动生成页面关系、联表或跨表事务。生成不建表或接管原表，仍须审阅用途并显式迁移或 adopt。未知类型、视图和不可读列拒绝，`tinyint(1)` 不猜测布尔；布尔、文本/文本域、整数、日期、日期时间、Decimal 和 JSON 会生成与类型匹配的标准表单控件，JSON 查询筛选需改用强类型扩展。Rust [示例](../crates/ryframe-generator/examples/generate.rs) 可用 `cargo run --locked -p ryframe-generator --example generate` 或 IDE 运行，导入需 `--features schema-import`；Builder 的 `plan()` 只读，`execute()` 才执行，`.write(true)` 才更新文件。 已有数据库先用 `cargo generate --features schema-import -- import --package order-business --connection primary --database tenant --tables biz_order,biz_order_item --config-dir ../ryframe-dev-config --plan` 读取工具默认值并列任务图，不加载应用配置、不连接数据库或读取迁移元数据，也不执行候选生成；去掉 `--plan` 后实际只读来源，在隔离候选工作区生成并校验模型、CRUD、迁移、契约和可选前端资产，但不更新两个仓库。审阅 `.ryframe/imports/`、差异和编译结果后再追加 `--write`。若导入表已在运行目标中存在，`--write` 后仍不能运行普通 `up` 猜测接管。

模型级 `#[resource(collation="utf8mb4_0900_ai_ci")]` 声明表排序规则；字符串字段可用 `#[resource(collation="utf8mb4_bin")]` 覆盖。未声明的表使用 `utf8mb4_general_ci`，未声明的列继承表规则。导入读取实际表、列规则并保存在 Rust 模型中，DDL、结构指纹、复制目录和接管校验共用声明。只接受安全的 utf8mb4 规则名称，实际可用性由目标 MySQL 校验；其他字符集须先审阅迁移或使用扩展。既有模型改变排序规则时整批停止自动迁移，先核对比较语义、唯一索引和存量数据，不自动转换。

物理外键属性完整声明 `name`、有序物理 `columns`、`referenced_table`、有序 `referenced_columns`、`update_rule`、`delete_rule` 和 `match_option`，例如 `#[resource(foreign_key(name="fk_note_customer", columns=["customer_id"], referenced_table="legacy_customer", referenced_columns=["id"], update_rule="RESTRICT", delete_rule="SET NULL", match_option="NONE"))]`。只接受同一存储范围、当前受管资源集合中的同库引用；本表须显式声明同列序前缀索引，引用列完整匹配主键或唯一索引，类型和字符串排序规则须兼容。租户约束必须包含本表与引用表对应的 `tenant_id`，不能只引用业务 ID。支持 `CASCADE`、`RESTRICT`、`SET NULL`、`NO ACTION` 和 `MATCH NONE`，`SET NULL` 要求本列可空；未知动作、跨库或目标、重复名称、未解析引用和循环依赖整批拒绝。新表按已验证的父表优先拓扑创建；已有外键新增、删除或变更只报告需要审阅安全增量，不改写历史迁移或自动删除约束。

`resource` 计划的持久化目标由各资源模型声明，执行时解析并校验；一个业务包可同时声明控制库和租户库资源。`import` 计划显示读取结构的来源、选中表和生成模型的目标类型。两种操作使用各自的目标依据，安装前都核验全部已注册业务模块：关闭前端同步时复用 `export_openapi`，因此仅生成后端也需能编译组合根的 `bin-api`；开启时复用已有契约生成校验，不重复导出。预检不启动服务或连接数据库，失败不安装正式资产；骨架生成、后端资源生成或后端预检失败时，工具保留后端候选和已有恢复文件，并报告实际路径。前端候选生成失败时，前后端候选和嵌套恢复备份均保留。先核对失败现场和正式文件，处理完毕后只清理这些精确目录，不自动重放。`--plan` 仅展示计划，不执行候选生成或预检。

### 已有表接管

已有表接管要求模型、迁移与数据库物理结构完全一致。先在业务 crate 导入或手写模型并登记描述符，用 `cargo generate -- resource --package order-business` 预览、审阅后加 `--write`；导入的字段类型、排序规则、索引、外键和迁移历史必须保留。停止目标上的 API、Worker 和调度写入，控制库先完成框架初始化；tenant 表必须选择单个目标键，`adopt` 不接受 `--all`。生成接管计划时控制库运行 `cargo migrate -- --config-dir ../ryframe-dev-config control adopt --module order --output D:/ryframe-private/migration/order-adopt.json --write`，租户库把 `control` 改为 `tenant-data` 并增加 `--target business-shared`，输出另取新文件。为 `--output` 选择工作树外的私有绝对文件路径，路径中不能含有 `..`。保存计划时命令按需创建父目录，目标文件已存在时会拒绝。先 `--inspect` 该计划，只读核对物理实例、数据库、表、迁移前缀和指纹，再用同一计划 `--apply ... --write` 和对应 `verify`。`--module` 预览的 `--plan` 不读配置或数据库；`--output` 必须配 `--write`，`--inspect` 拒绝写入。部分登记、前像不符、来源不同或结构漂移都失败关闭；未知结果先 inspect 原计划，不能换计划重放。目标为空、只把已有表当结构模板时不需要 adopt，按正常 `up` 建表。

### 模型结构演进

Rust 业务模型用 `ryframe_sdk::time::Date` 声明 MySQL `DATE` 字段，可空列使用 `Option<ryframe_sdk::time::Date>`。反向导入也会生成这两种类型。 修改 Rust 模型后继续运行相同的 `cargo generate -- resource --package order-business` 预览，审阅后加 `--write`。生成器保留全部历史迁移原字节及摘要，只追加稳定编号的新迁移，`src/generated/migrations/history.json` 与 ownership 一起保存前后结构链；这一步不连接或修改数据库。 字段可用 `#[resource(sql_type="VARCHAR(32)")]` 保留物理类型；导入自动写入该属性，DDL、复制目录和接管校验共用它。业务模型的 `DATETIME` 字段声明为 `ryframe_sdk::time::OffsetDateTime`，可空列用 `Option`。生成的接口按 RFC3339 接收带时区的时刻并归一为 UTC。接口会拒绝闰秒以及归一后超出可表示范围的值。 当前支持与 Rust 类型匹配的 CHAR/VARCHAR、TEXT 系列、有符号整数及 `u8/u16/u32/u64` 无符号整数、布尔、DATE、DATETIME（0～6 位小数）和 JSON；推导字符长度、文本字节容量及整数范围，矛盾校验、未知声明或 SQL 子句在写入前报错。整数 CRUD 保留 Rust 位宽及符号，默认值和枚举必须在该类型范围内；物理 SQL 容量须完整适配模型，增量转换按物理范围检查。`u64` 普通字段保留完整无符号容量并使用字符串传输，超过 i64 的默认值使用十进制字符串；主键支持 `i64/u64`，自增及雪花策略、URL 和持久化保持类型一致；Decimal 必须显式声明 `DECIMAL(p,s)`（1≤p≤28、0≤s≤p），使用 SDK 的 `rust_decimal::Decimal`；正文、查询、响应及文本表单均以字符串传输。超出列容量或小数位数会拒绝，API 和 SDK 用例均不做自动舍入。FlatCrud 按模型生成文本或文本域、整数、开关、日期、日期时间、枚举单选和精确 Decimal 文本控件；JSON 使用可编辑文本域，提交前严格解析为结构化值，可空或可选空文本分别提交 null 或省略。JSON 不支持标准查询参数筛选，需要结构化查询时编写强类型扩展。

复合索引用结构体属性 `#[resource(index(name="idx_code",fields=["code","id"]))]` 声明，唯一索引加 `unique`；导入保留索引名、字段顺序和唯一性，拒绝前缀、降序、函数、不可见及非 BTREE 索引。仅为自增联合主键补充必要的 id 首列索引，不给主键已覆盖字段补冗余索引。 字段的 `#[resource(sql_comment="Database comment")]` 独立于界面标签；导入、DDL、模型摘要及追加迁移保留该值，结构指纹仍只核对结构。引号、反斜杠、换行原样保存；字段注释不能含 NUL 或超过 1024 个字符。 字面量默认值使用字段 `default="value"`，数据库时钟使用 `sql_default="CURRENT_TIMESTAMP(6)"`、`sql_on_update="CURRENT_TIMESTAMP(6)"`；时钟只支持与 DATETIME 列一致的 0～6 位精度，不接受任意 SQL，`default` 与 `sql_default` 不能并用。导入保留这两类默认值及更新时间表达式。业务模型中显式声明数据库时钟表达式的字段不进入创建和更新表单；强类型插入输入省略数据库尚未生成的值，Repository 插入时省略这些列，更新时不写回数据库管理列，并返回实际持久化值。Record、实体和响应保留声明的非空类型；无数据库表达式的审计字段继续使用应用时钟，可编辑字段的可空替换语义不变。日期、Decimal 的字面量默认值须符合当前 CRUD 支持范围，其他表达式使用明确迁移扩展。

- 新增可空列、带显式默认值的非空列、整数或字符串扩宽、放宽非空约束及新增索引可生成向前 DDL；唯一索引仍须先核对存量重复值。
- 删除或重命名列、收窄类型、收紧非空约束、改变主键/表名/存储范围、调整已有列顺序或删除/修改索引只输出审阅原因，整批停止，不覆盖初始迁移或发布半批注册。非空新列没有默认值时，先用可空列分阶段回填。
- 审阅迁移后停止生产者，再显式执行 control 或所选 tenant-data 目标的 `up` 和 `verify`。数据库被直接改动时 verify 报告漂移，生成器不会反向覆盖模型或猜测已执行状态。
- 可空可写字段使用完整替换：创建时省略或传 null 均为空，更新时省略或传 null 均清空该字段；非空可选更新省略时保留原值。需要三态补丁时编写明确扩展。业务 `i64/u64` 默认字符串传输，正文、查询、返回值及文本表单保持精确十进制；不使用 number 控件。空文本提交为可空字段的 null 或可选字段的省略值，必填字段仍由表单与服务端校验；有限枚举保留字符串值，不转换为浮点数。契约中字符串传输的 64 位整数范围同样使用规范十进制字符串，前端以 BigInt 校验，禁止将边界先解析为 Number。

生成器不执行数据库迁移。受管文件写入并审阅后，按模型存储范围先运行 `status`，再运行 `cargo migrate -- --config-dir ../ryframe-dev-config control up` 或 `cargo migrate -- --config-dir ../ryframe-dev-config tenant-data up --target <target-key>`，最后用对应 `verify` 校验；多个目标共享版本时可显式用 `--all`，但不能替代 `control up`。最终结构校验失败仍应保留现场，先核对账本和实际表，不重放未知结果。 Post 和 Notice 仍是 RyFrame 框架自身的标准资源。框架维护者继续使用内部 `cargo xtask generate resource` 检查它们；使用者业务不写 `catalog/resources/*.toml`。

租户业务资源同时生成 `generated/tenant_catalog.rs` 与 `generated/tenant_catalog.json`，包含完整列、类型、复制游标及规范化 schema。模块通过 `tenant_data_tables()` 声明生成描述，组合根在连接数据库前统一装配、核验依赖并冻结目录；同一进程再次登记只能使用相同描述。重复表、缺失描述或无效 schema 会阻止启动，不会忽略业务表。复制和恢复校验使用完整目录，并保留业务迁移账本。生成迁移同时注册模型指纹与每张表的 before/after 物理结构；手写 `SeaOrmBusinessMigration` 也必须提供 `BusinessMigrationSchema`。单条 `verify_ledger` 仅校验历史账本，整组 `verify_business_migrations(database, scope, migrations)` 接收该范围的全部注册迁移，拒绝未知账本和归属冲突，再按每张表最新状态校验实际结构，避免合法追加迁移被旧结构误判。修改模型后先通过正式生成入口更新受管资产，再显式执行业务迁移；不要手改目录或 ownership 摘要。已有表按[已有表接管](#已有表接管)预览、保存、核对和执行计划；租户接管必须选择单个目标，不用 up 猜测接管。

- 通常继续使用 `SeaOrmBusinessMigration::new(...).with_initialization_sql(...)`，生成器也使用该封装，无需业务模块手写会话管理。该实现的普通 `up` 与 `up_in_session` 共用 DDL 前置条件、历史账本/归属核验和执行后结构核验；只有连接持有方式不同。
- 直接实现 SDK `BusinessMigration` trait 的使用者必须同时实现 `up_in_session(&mut DatabaseTransaction)` 和 `verify_ledger_in_session(&DatabaseTransaction)`，与原 `up`、`verify_ledger` 保持相同校验强度，不提供成功默认值，不重新租用连接。初始化工具在整个窗口保留该物理会话的迁移互斥，因此单连接池也必须可用。自定义实现和受管生成业务源码升级到当前 SDK 时须同步方法合同。
- 业务 DDL 可能隐式提交，不能声称整个初始化可回滚；本次业务账本登记仍必须在独立原子事务中完成完整元数据锁、结构及归属核验，成功后才记录 executed。数据库归属登记发生在全部适用初始化及最终核验成功后，是另一个元数据事务。任一提交结果未知都先核对完整前后像，不自动重放 DDL 或登记。
- 保留的 MySQL 会话通过两个最小 SeaORM 操作调用现有 SQLx TransactionManager：`finish_mysql_root` 只接受深度一，`begin_mysql_root` 只接受深度零，均要求独占可变持有者，拒绝嵌套与其他后端。SDK 会话迁移从已结束的根事务开始，不会提交调用方无关的活跃事务。事务网络操作前先使会话失效并标记连接丢弃，成功后才恢复可用；取消或提交未知会永久禁止该持有者继续 SQL/begin，防止迟到 Drop 回滚下一代事务。只有当前事务已结束或已回滚，才显式释放命名锁；否则依靠丢弃连接与断连释放，不宣称已确认释放。未知结果用新连接和原计划只读核对。DDL 隐式提交、业务账本原子登记及最终 ownership 登记分别具有独立边界。

1. 创建业务 crate、登记 `ResourceModel` 后预览生成，再用 `--write` 写入；再次预览应没有差异。
2. 为业务模型和用例添加测试，执行 `cargo test --locked -p order-business`。先通过控制库与明确租户目标的迁移状态检查，再显式应用本模块迁移，命令见[数据指南](data.md)。
3. 默认开发模式运行 `cargo serve -- --config-dir ../ryframe-dev-config`，确认模块路由和内嵌任务正常装配；验证独立进程时，按[双目录启动步骤](#启动后端)选择两份不同实例编号的配置。接口变化后从后端执行 `cargo xtask generate api --write` 同步候选契约。OpenAPI 与数据库结构快照通过正式生成或迁移维护入口产生，不直接运行内部二进制。 前端请求与后端不一致时，重新同步契约并运行消费者检查。
4. 正式注册的业务权限和菜单由显式 `control up` 按编译目录同步，命令见上文[数据库迁移](#数据库迁移)，无需重复手工登记生成目录。已有普通角色及额外扩展操作仍须按实际需求授权；生成或同步目录不代表全部已有租户或普通用户自动获得权限。变更角色授权后，确认会话已取得新的授权投影，再验证接口；未授权时接口应返回 403。
5. 在前端通过生成的 typed caller 接入业务 API；页面登记路由与 i18n namespace，查询和变更绑定当前会话 scope，方法见[前端架构说明](https://github.com/Edgar-ycy/ryframe-vue3/blob/main/ARCHITECTURE.md)。
6. 运行前端 `corepack pnpm check --full`，再用本地 Chrome 验证业务成功、权限拒绝、租户切换和取消。只在隔离开发环境准备数据，完成后核验自己创建的数据库与对象资源。

框架的自动化业务夹具使用同一脚手架，在忽略目录中生成使用者业务 crate 并核验重复生成；可通过 `cargo xtask check recovery fixture --output-dir <absolute-isolated-directory> --write` 创建，不会向框架产品加入内置业务模块。 参考夹具运行时完成 `build`、`start` 后，使用 `cargo xtask check recovery fixture runtime bind` 为独立的 `run_id` 和 `dev` 或 `preview` 模式创建浏览器绑定，再执行同组的 `browser`。`preview` 会先执行真实前端构建，并在浏览器前后校验生产产物及浏览器实际收到的静态响应；`dev` 不创建生产构建。`browser-verify` 只读核验运行中的 API/Worker 与全部成功证据，停止运行时后使用 `browser-close` 只读核验关闭状态。具体必填路径与写入参数见该命令的 `--help`。每个 run id 的输出只能创建一次；失败、残留锁或 pending 文件、来源变化及未知业务写入必须先核对完整现场，不能覆盖结果或自动重跑。浏览器绑定登记 MySQL、Corepack/Node 与 Worker 原生工具，不要求 Python 路径。登录密码由本机短生命周期凭据代理提供，工具配置和脱敏日志不保存密码。

## 开发自定义业务

在自己的业务 crate 的 `extensions/` 中编写模型、用例、Repository 和 Handler；业务复杂后可自行拆成多个 crate。通过 `ryframe-sdk` 使用事务、数据库和 HTTP 扩展接口，在该 crate 的 `module()` 中注册路由、OpenAPI 和迁移。生成骨架已通过 `.control_tables(generated::CONTROL_TABLES)` 装配当前控制库业务结构；手写模块用 `BusinessControlTableDescriptor` 提供完整规范化结构，必须与控制库资源一一对应，不能只登记表名。测试覆盖业务成功和失败路径，同步前端契约并联调；模块选择和请求流见[架构说明](architecture.md)。

## 生产构建

`cargo xtask build` 从同一构建计划依次运行三个任务：关闭默认 feature 后分别定向构建 API 和 Worker，再通过 Corepack 构建前端生产目录。每项完成后输出 Cargo 实际报告的可执行文件或完整前端目录的路径、字节数和 SHA-256；`--profile dev` 只改变构建 profile，任务边界保持不变。 `cargo xtask build --plan` 渲染这份计划的依赖、有效参数、输入范围、编译覆盖和允许写入，不启动 Cargo、Corepack 或服务，也不创建目录、缓存和报告。实际执行在首个任务前和全部任务后核对前后端工作树指纹；任一来源在构建期间变化都会失败，已生成文件不能作为同源成功产物。

## 集成验证

本节面向框架维护者。真实服务门禁使用已登记的隔离测试配置。 租户业务读写保持数据范围投影版本的严格校验；投影缺失、未就绪或落后时使用 `TenantDataTargetUnavailable(message, 5)`，通过现有 HTTP 错误映射返回 503 和 `Retry-After: 5`，不要求客户端刷新产品会话。生成仓储与租户数据端口使用相同分类；修改生成器后，已有业务项目须通过正式生成入口更新受管仓储文件，不能手工修改生成产物。
租户数据范围投影的真实 MySQL 用例 `data_scope_projection_mysql` 复用 `.local-tests/mysql/config` 与同一归属夹具，核验共享控制库及独立 dedicated schema；目标只初始化租户结构，版本发布从控制库读取最小身份与部门事实。场景核验投影落后拒绝、注入写入失败后的完整前后像及恢复发布；不创建额外数据库用户，不代表不同实例或业务 CRUD 已验收。

正式 `cargo xtask check ci integration` 对 `business_initialization_mysql` 测试目标使用 `--no-default-features --features bin-api,bin-migrate`，使现有 `replicas::real_replica_monitor_routes_recovers_and_rejects_business_drift` 用例编入并执行。两项 feature 只组合用于这个测试目标；产品 migrate 的定向构建仍仅启用 `bin-migrate`，其依赖隔离不变。完整集成门禁会验证 MySQL required TLS，以及 Redis TLS、S3 HTTPS 和 OTLP HTTPS 三个 AWS-LC 真实出站测试。本地需有 `openssl`，并在回环地址提供隔离的 MySQL 与 Redis；服务按版本和协议要求选择平台，测试显式选择独立 Redis 实例和数据库。门禁只接受回环 Redis，不执行 `KEYS`、`SCAN` 或 `FLUSH`，测试 key 由唯一 `scope_id` 隔离并精确删除。运行前必须配置后端根目录的 `.local-tests/integration/ci.toml`，填写 `format_version=1`、`run_id`、`artifact_root`、`redis_config_dir`、`openssl_program`，并准备显式测试目录 `.local-tests/mysql/config` 与 `.local-tests/service-tests/redis/config`；字段与路径限制见[运维指南的 TLS 证书](operations.md#tls-证书)。运行入口与 CI 相同：


Unix 与 Windows 使用同一套 Rust fixture：xtask 调用本机 OpenSSL 生成两日有效的临时 CA，在动态回环端口启动 Redis TLS 代理和 HTTPS 服务，不再启动 Python 门禁脚本。上述文件的 `openssl_program` 支持明确值 `"openssl"`（使用操作系统 PATH），或无链接的普通可执行文件绝对路径、以后端根目录解析且禁止 `ParentDir` 的相对路径；找不到工具或证书命令失败时，诊断会保留 OpenSSL 日志路径和实际退出原因。相关测试结束或失败后停止 fixture 监听，仅在发布输入与所有权核对安全时清理临时证书；部分发布、外来文件、来源漂移或清理未确认时保留配置及证书现场。实际产物目录在该文件的 `artifact_root` 下排他创建并输出，历史目录不会覆盖。CI 对成功和失败运行都上传 14 天，失败摘要会输出每个已运行测试的最近日志。隔离测试配置中的 Redis host 不是 `127.0.0.1`、`::1` 或 `localhost` 时门禁直接拒绝启动，避免误连共享 Redis。Linux DevEx cgroup 内存门禁同样完全由 Rust xtask 执行：公开 `run` 只允许 Linux GitHub Actions 的非 root runner，创建新的 `.local-tests` 证据目录并记录精确 run、attempt、nonce、源码 SHA 和 runner uid/gid，再通过 `sudo -n` 执行 prepare、test、cleanup；Cargo 由另一个永久降权到原 runner 身份的 Rust 子进程启动。门禁只使用本次创建的 `/sys/fs/cgroup/ryframe-devex-ci-*`，要求 `/sys/fs/cgroup` 是明确的 cgroup2 挂载且已启用 memory controller，不改父 controller 或限额。`cleanup` 只读取同一计划、内核 device/inode 和进程登记，确认 freeze 后按需写 `cgroup.kill`，遇到未知或复用 PID 时拒绝终止并保留现场。证据文件只创建或追加，`--plan` 只展示同一任务图，不启动 sudo、不创建目录。

真实全栈的 API 与 external Worker 每次分别由私有长驻监督进程托管。Windows 监督进程先把自身加入启用关闭即终止的私有 Job Object，Unix 监督进程先建立独立 session 和进程组，再启动产品代码；进程树收据绑定 scope、启动操作以及监督进程和产品进程的创建身份。停止与故障注入使用不同控制收据，保留产品真实退出码；正常停止先请求产品退出并等待宽限，随后才回收完整 Job 或进程组。Windows 当前没有可继承的温和控制台通道，正常停止触发的 `TerminateProcess` 会如实记录为强制终止。控制操作只有在完整进程树停止且监听端口释放后才完成，不会按 PID 猜测或影响未登记进程。 Worker 探针和控制收据守卫由正式绑定的 Rust 工具执行；Python 仍持有锁，负责进程生命周期和恢复编排。启动控制器中断后，`status` 或 `reconcile` 会核对原启动收据。启动失败收据先于监督进程退出时，核对会等待该进程退出及完整成员回收证明，再归档原失败记录；不会自动重新启动 Worker。等待超时、PID 复用或关闭证明不完整时保留现场，按原日志及收据排查，不能直接删除控制锁。进程级 Worker 测试失败时，隔离现场副本保存在 `.local-tests/python-failures/`，包含原运行收据和日志。

历史保留期夹具通过 `cargo xtask check recovery fixture retention` 的 Rust 实现执行。`plan-history` 只读绑定当前租户、迁移、配置、服务器及全部任务尝试；`historical-expired --plan-sha256 <摘要> --write` 仅在 Worker 已停止且事务内前后像一致时平移 169 小时，保留 168 小时策略。`export-backup --write` 在精确租户写入 fence 下实际导出并验证摘要，明确不代表恢复成功；中断、部分写入或确认丢失均保留证据，先核实数据库和导出文件，不能自动重放。 复制阶段的原生事务门入口为 `cargo xtask check recovery fixture retention hold-copy --runtime-dir <目录> --tenant tenant-xxxxxxxx --migration <正 i64>`，仅接受已登记且 Worker 已停止的隔离运行。标准输入每行发送 `{"operation":"wait-blocked"}` 或 `{"operation":"release"}`，标准输出保留 `held`、`blocked`、`released` 的逐行 JSON 协议；EOF 或异常退出会回收锁连接。复制门与历史保留期操作均由 Rust 执行。CI 四库初始化同样由 Rust 的 `__ci-databases` 私有入口执行：协调器通过有界 stdin JSON 绑定当前 Job、显式配置目录及规划时捕获的配置快照；连接字段、TLS、容器归属、客户端凭据文件和配置发布只由 Rust 校验和执行，不再保留 Python MySQL helper。凭据仅进入私有管道和受限目录文件，不进入 argv、环境或公开日志；容器内客户端固定使用 3306，保留显式 TLS 参数。建库前先持久化 `creation-unknown` 收据，只有四库创建成功才写入 `created`；失败、取消或进程中断均保留现场且禁止自动重放。已有同名资源仍失败，不使用 `IF NOT EXISTS`；API 和 Worker 分别使用已校验的实例编号与固定编号 2。

Extended CI 的 core/business 全栈任务负责启动后端并构建前端，不执行浏览器验收，也不生成浏览器专用配置；浏览器门禁由前端 CI 独立执行，真实全栈浏览器验收继续使用正式入口。 全栈 `prepare`、`start`、`collect` 与登录预算导出由 Rust 协调，业务夹具工作树复制、双仓来源复核、资源生成顺序、只读检查和 xtask 预热也由 Rust 执行；原 Python 协调入口已经删除。全栈 CI 与参考夹具 runtime build 共用 Rust 四角色构建核心及来源采集：按 Cargo JSON 中当前 Workspace 的唯一二进制产物取路径，构建前后复核双方来源、业务夹具、模型及产物摘要；已有清单或证据时拒绝覆盖。夹具运行登记与监督复用有界 stdin 原生端口：API、Worker 与前端有限命令使用同一 Rust 引擎，分别核对角色、冻结产物与 argv/cwd、配置、就绪或完成协议及整树归属；端口不决定父阶段或自动重试。没有监督树的旧 API 不接管、不补签，由原现场控制器收尾。全栈 CI 由 Rust 原生监督器启停 API，复核同一进程的创建身份、就绪状态与监听归属后才启动 Worker。收集阶段独立检查 API 端口是否释放，并继续采集诊断。源码组合签发与 Release 归档校验复用既有 Rust 实现，不再保留重复的 Python 实现。对象存储后端、目录、端点和凭据取自已绑定的明文文件配置。参考夹具的首代 RustFS、Redis 和五桶由 Rust 按同一账本顺序初始化。对象桶创建调用原生 Rust S3 客户端，先保存写入未知收据，创建响应与独立 HEAD 核验均成功后才标记完成。目录权限及实例编号改写共用 Rust 文件协议，凭据不进入子进程环境或公开日志。 已 ready 的业务夹具可在其后端根执行 `cargo xtask check recovery fixture source-pair publish-execution --output-dir <新的绝对目录> --write`，输出必须位于该后端 `.local-tests`，父目录须已存在。该命令依据原 clean HEAD 和冻结的完整生成差异发布两份独立、干净的本地 Git 源码，保留已跟踪的源码配置模板；输入复制和发布初态仅接收完整源码及下述机器契约例外，不带入其他 ignored 运行配置或产物，生成差异不得混入运行配置。后续核验仍逐项检查完整 Git 来源，只在确认目录根为普通无链接目录且已被 Git 忽略后，允许后端根 `.local-tests` 和前端根 `.local-tests`、`node_modules`、`dist`；不豁免 backend target、深层同名目录或其他 ignored 内容。这里不认证这些资产的内容、内部链接或运行资格，仍由既有配置、依赖、产物和目录 guard 核验。原 fixture、仓库索引与 HEAD 保持不变，原 source-pair 发布方式保留。 唯一额外接收的 ignored 输入是 `openapi/candidate.json`：候选态严格核验其五字段规范 JSON、前端契约与原 前端改名或移动后在 `config/tools.toml` 设置路径，框架维护验收的本机覆盖可放在 `.local-tests/tools.toml`。各节字段及开发监督器的完整注释示例见 [config/tools.toml](../config/tools.toml)；工具文件可登记租户迁移验证目标；环境数组整体替换。可选 `verification.pnpm_cache_dir` 按后端根解析，复用 `generator.target_dir` 的非空 UTF-8、无控制字符、无父跳转及拒绝驱动器相对路径规则；读取配置不创建缓存目录。显式配置时，后端发起的 pnpm 依赖命令统一传递 `--config.cache-dir=<目录>`，夹具与生成候选只传播已选绝对缓存路径；未配置保留 pnpm 标准缓存行为和 CI 默认选择，不新增环境变量入口。它与依赖 store 是不同设置，不能用 store 已预热推断所需元数据或策略检查可用。其中 `[development]` 字段只影响开发监督器，不能代替显式的数据库初始化。框架维护者使用 `cargo xtask dev --measure-once --case config-only --output .local-tests/dev-save.json` 选择保存测量场景；`--case` 和 `--output` 仅允许与 `--measure-once` 一起使用，默认场景为 `shared-runtime`，不改变历史测量结果合同。 维护程序、API 与 Worker 的正式验收构建共用工具文件字段 `verification.build_jobs`，公共默认值为 `4`，合法范围为 `1..64`。内存不足时在 `.local-tests/tools.toml` 的 `[verification]` 下设置 `build_jobs = 1`；本机覆盖优先于 `config/tools.toml`，不新增应用环境变量。实际 Cargo 命令显式携带 `--jobs`，构建收据记录采用值；读取历史收据按其原命令核验，校验当前构建时另行比较当前配置，配置漂移不会被当成仍可复用。修改配置后保留原失败目录，再显式选择新的输出目录，不覆盖失败收据或自动重放。显式配置的 `generator.target_dir` 也用于普通运行、参考夹具和全栈构建；相对路径以后端根目录解析，跨工作树共享缓存使用明确的绝对路径。工具把这个文件值传入 Cargo 子进程的标准目标目录环境，覆盖继承的 Cargo 目标目录；原有构建上下文记录实际环境摘要，不新增应用配置环境入口，也不修改历史收据结构。未配置时保留各入口既有的 Cargo 默认行为。构建期间更改该字段会拒绝发布成功收据，并保留现有产物；核对配置后显式选择新输出目录。降低编译并发不改变测试并发、样本规模、服务期限或恢复验收门槛。

CI 配套前端仓库可在工具文件的 `[workspace].frontend_repository` 中显式设置为完整 `owner/repository`，本机 `.local-tests/tools.toml` 覆盖公共 `config/tools.toml`。省略该字段时，仅使用 GitHub 标准身份 `GITHUB_REPOSITORY_OWNER` 选择 `<owner>/ryframe-vue3`；本地没有该身份时必须配置此字段。空值、非法仓库名或换行会报错，不回退到环境覆盖；旧 `RYFRAME_FRONTEND_REPOSITORY` 和 `FRONTEND_REPOSITORY` 均不再作为配置入口。`cargo xtask check ci frontend-source` 同次输出 `ref`、`changed` 和 `repository`，各工作流使用该结果检出配套源码；`--plan` 只展示任务图，不解析 GitHub owner 或写入 job 输出。

Full Resource Workspace 门禁在同一次 Cargo 编译中准备 `resource_workspace_compilation` 与 `generation_pipeline`，在同一受管控制目录先运行原正向目标一次，再核对并仅运行后者的两个 `cross_module_` ignored 冲突入口，不重复其旧正向长链；Targeted 保持原范围，不追加冲突矩阵。 CI 计划和快速预检通过 `cargo xtask check ci <plan|preflight> --base-sha <SHA>` 选择基准，省略或空值表示没有基准。资源门禁使用 `cargo xtask check ci resource-gate [--base-sha <SHA>] [--head-sha <SHA>] [--frontend-ref <SHA>] [--targeted] [--decision-file <绝对文件>] [--jobs <1..64>] [--test-jobs <1..64>]`：三个 SHA 参数必须是非零的 40 位十六进制提交 SHA，参数不得重复；缺少基准、head、前端提交或 targeted 激活时执行完整门禁。decision 文件只创建新文件，父目录必须已存在；并发参数必须为 1 到 64。工作流仅在 PR 或分支 push 传入基准，tag 不使用 `before`。回放器显式传递每个案例的提交、激活状态、decision 路径与固定预算；本地 DevEx 不从环境推测范围，缺少显式范围时记录完整回退。预检将同一基准传给迁移保护和函数长度增量扫描。默认预检运行原有全部任务。通过 `--part checks` 运行格式、源码、策略、权限路由与迁移历史检查，通过 `--part python` 运行解释器核验和完整 Python 测试。两种分片都能与 `--base-sha` 组合。资源门禁不读取项目自定义环境变量。Python 用例在 CI 中开始时会打印名称，日志可用于定位尚未执行完的用例。

资源门禁回放由 `cargo xtask check ci resource-gate replay` 原生执行。manifest 每个案例绑定前后端精确提交；回放器在 `.local-tests/resource-gate-replay` 创建隔离 worktree，交替执行 targeted 与 full arm，只安装一次前端离线依赖并复用 session 级 Cargo target。报告只创建新文件，`--work-dir` 与报告都必须位于该证据根目录的子路径。`--activation-gate` 还要求隔离 MySQL、Redis 与 TLS 服务、至少 20 个案例、10 个成功 targeted 案例、双模式与 pass/fail 覆盖、零分歧、健康 sccache 和 60 秒 P95 预算；失败保留命令末尾、退出码及清理错误，不自动重放未知写入。 外部驱动不追加门禁参数，通过 stdin 接收版本为 1、上限为 16 KiB 的 JSON 请求，包含 `format_version` 与绝对路径 `target_root`；`CARGO_TARGET_DIR` 继续由 Cargo 环境提供，旧 replay 夹具、target 和日志环境入口不再读取。
回放的集成启用事实来自后端根目录下真实测试使用的 `.local-tests/mysql/config` 与 `.local-tests/service-tests/redis/config`，不读取旧 MySQL/Redis 环境启用标志、主机或数据库覆盖。存在的角色目录必须有有效的 `app.test.toml`，可选 `app.toml` 按正常文件配置规则合并；未启用 `--activation-gate` 时允许角色目录缺失，但存在且无效的配置仍失败。激活要求两个角色均存在：MySQL 的 `database.primary.host` 和 Redis 的 `redis.host` 只能是 `127.0.0.1`、`localhost` 或 `::1`，MySQL 必须启用 TLS，Redis 必须显式配置 host/port、使用 `mode = "required"` 和数据库 15。原有作用域、连接和 TLS 配置校验继续生效；证书及私钥字段必须指向普通无链接的绝对文件。回放在外部资源命令前捕获配置与 TLS 材料，将配置原字节发布到隔离 worktree 的相同角色路径，并在每个预热和比较命令前后、报告发布前后复核。来源增删、身份或内容漂移会失败并保留现场，不重新捕获。报告的三个集成状态使用字符串 `"0"`/`"1"`，由文件事实派生，只附路径、缺失事实和文件字节数/SHA-256 绑定，不序列化配置或凭据。

恢复私有子进程由当前 Rust 协调器显式传递必需的原生工具身份，通过各入口固定的参数、stdin 或受管请求文件接收；工具身份与产品输入、业务计划和来源指纹分别记录。Python 在业务派发前核验工具文件并安装绑定，同一绑定可复用，不同绑定拒绝替换。缺少或损坏的绑定直接失败；S3 与夹具客户端不再通过 Cargo 临时构建。原生 S3 私有请求只接收 `configuration_binding`，核对绑定文件前后摘要后在内存读取凭据；不接受内联凭据。来源私有 `source.s3` 仅含 `configuration` 文件绑定，公开端点和 region 从该文件推导，不作为配置覆盖；库存诊断脱敏也只在核验绑定后读取内存中的凭据。检查应从正式 Rust 入口执行，父进程已安装的 Python 内存状态和旧工具环境变量均不能为新子进程提供绑定。

来源运行验收的完整证据清单、动态采集文件身份、生产者 ready 绑定和授权缓存收据由 Rust xtask 校验。来源比较由 Rust xtask 执行。用 `cargo xtask check recovery source comparison-capture --help` 查看两侧必填的来源、构建收据和环境参数，再以 `--source-export-result <unique-export-outer-result> --output <new-source-manifest> --write` 显式授权发布新清单。`cargo xtask check recovery source comparison-verify --receipt <source-manifest>` 只读执行，拒绝 `--write`。两条命令严格核对 B0 原产品及已登记执行适配、B1 最终源码、两侧构建环境与完整前后端产物，并绑定同一份已发布 `source-export` 的外层结果与内部导出身份。参数不合法、输入漂移或绑定不匹配时以非零状态退出。详细参数见[运维指南](operations.md#参考环境的外部验收驱动)。恢复运行的 API/Worker 就绪探针与前端完整文件响应核验由绑定的 Rust 工具执行：禁用代理和重定向，每次响应最多等待 10 秒；API 仅接受严格就绪 JSON，Worker 必须为空响应，静态文件逐项验证长度和 SHA-256。运行请求文件同时绑定协调器工具；缺少绑定时拒绝临时编译回退，取消或失败不产生成功证据。`source verify`、`source verify-recover` 以及 `source-generation-stop` / `source-generation-recover` 的父执行链由同一 Rust xtask 控制器持有 RunLock，直接执行生产者授权、完整像核对和精确进程树回收。Rust xtask 也执行来源代次启动、状态查询、重启状态查询和重启闭合。来源与凭据异常只返回脱敏分类，未确认的缓存清理结果保留原 intent 并先核对全部计划键，不自动重放。 恢复生命周期的代次状态、首次目录 intent、完整进程树绑定和成功启动收据由同一 Rust 工具校验与发布；状态替换核对冻结前像，intent 和成功收据只允许独占创建。未知文件、未绑定启动收据、部分发布或已改变的关闭证明继续拒绝成功与自动重放。夹具服务公开入口和生命周期由 Rust 编排。RustFS 启动和 Windows Redis 启停使用绑定的 Rust 子进程。停止与恢复继续由原控制器核对 owner、状态前像及锁身份。 Windows 验收环境由原生 Rust 工具控制已登记的 Windows Redis 启停。33 键来源授权缓存的条件清理由 Rust 持有单一 Redis 连接执行 WATCH/MULTI/EXEC；比较失败、竞争与未知 EXEC 结果分别失败关闭，禁止 transaction helper 自动重试，服务端清理 Lua 及其结果 decoder 已移除。

架构检查由 Rust xtask 执行，覆盖 crate 依赖图与声明边、system 业务域公开面、人工文档、源码与函数规模、旧持久化接口、异步端口、Workspace unsafe lint、测试布局及租户数据静态边界。函数规模与 unsafe 语法由 Rust 内固定版本的 tree-sitter 与 Rust grammar 解析，不再依赖 Python 原生扩展；函数阈值、变更范围和例外策略保持不变。`python.environment` 通过固定的标准库探针读取实际解释器路径、实现和版本，响应使用严格 UTF-8 JSON。剩余 Python 检查要求 Python 3.11+，解释器缺失、版本过低、进程非零退出、无输出、超时和 Windows 崩溃均有诊断。Python 与 Node 入口分别由工具文件 `[verification].python_program` 和 `[verification].node_program` 指定，两者的显式入口均须非空、禁止父目录跳转和控制字符，相对路径以后端根目录解析，绝对路径原样保留，本机文件覆盖公共文件，缺省分别使用操作系统 PATH 中的 `python` 和 `node`；观察 Python 解释器身份不会将 venv 入口替换为 base 路径，`--plan` 不启动 Python。Python 检查通过 `--rate-limit-tool-binding` 参数将固定原生工具描述交给 `tools/python/run_checks.py`，在运行 `unittest` 前仅安装一次；不再读取旧限流工具环境绑定，测试失败保留原退出状态。供应链来源检查同样由 Rust xtask 只读执行：以 `tools/policies/supply_chain_policy.json` 为事实源，校验策略 schema、本地 patch 许可证及 registry 原件、GitHub Action/可复用工作流/容器引用、service image digest、安装工具版本、工作流命令和 Cargo 条件依赖例外；`ci.security.supply-chain` 额外校验 API、Worker、Migrate 与默认生成器的定向 feature 树。工作流解析保留锚点、别名和 YAML 1.2 布尔语义，遇到重复键或未支持的静态结构会失败关闭；全栈工作流的双仓来源、业务夹具顺序和诊断产物绑定也由 Rust 在快速预检及完整后端门禁中核对。前端 consumer context 不选择或传递 Python 解释器；前端构建证明由 Rust 统一校验。独立 PythonSuite 使用上述解释器运行。

优先级为命令行 `--frontend-dir`、本机工具配置、公共工具配置；相对路径统一以后端 Cargo Workspace 根目录解析，与命令在哪个子目录运行无关。工具配置不放服务连接密码，不通过环境变量覆盖，也不影响 `cargo serve -- --config-dir ../ryframe-dev-config` 的运行时配置。后端范围只检查后端，显式跨仓范围找不到前端时会输出实际路径与配置位置。前端目录可使用 `../ryframe-vue3` 等正常相对配置；实际执行时逐级核验原始目录后再解析父跳转，拒绝链接或缺失目录后接 `..` 的路径，正式来源上下文只保存无父跳转的绝对路径。跨仓 consumer 通过 `--consumer-context <absolute-json>` 传递正式文件协议，每次执行独占 `.local-tests/consumer-contexts/<unique>/context.json`，绑定两仓路径、五对契约参数、origin 工具和公私工具配置摘要，上下文不含解释器选择字段；工具与编译来源不匹配或配置漂移时失败并保留证据，不能以旧绑定继续执行。
语言与文件构成使用 `cargo xtask check language`，默认只向终端报告完整后端非 ignored 文件的原始字节；已跟踪但符合 ignore 的文件也排除。自维护代码包含手写、测试、生成物及源代码模板，vendor 单列，文档、配置、资源与全量文件体积另列；固定分类以 [language-policy.toml](../architecture/language-policy.toml) 为准。显式 `--min-rust-percent 80` 用精确整数运算校验阈值，未达或分母为空时失败，不隐式加入本地日常门禁；CI 计划任务显式执行同一 80% 检查，也覆盖只修改 Python 等非 Rust 文件的提交；百分比允许 0 到 100、最多六位小数。框架维护者如需保存证据，可用 `--output <new-report-file> --write`，命令只创建未跟踪的新报告并保留已有文件，维护验收流程提供 `.local-tests` 下的既有验收目录；报告含口径摘要、HEAD 和逐文件字节及摘要，同时请求阈值时先保存结论再返回失败。`--plan` 只输出同一任务图，不启动 Git、不落盘。54.4% 缺少原始复现证据，只保留为旧参考，不计算增减趋势。

唯一登记的内联 Lua 是 Redis 归属初始化 `marker.rs` 中顶层 `SCRIPT` 的原始字符串内容。报告把内容中的原始换行一同计入 Lua，Rust 字符串定界符及宿主文件其余内容仍计入 Rust。该文件的 JSON 记录保留完整物理字节和 SHA-256，同时用 `embedded_lua_bytes` 标明 Lua 字节。语言统计可分别把这一文件计入 Rust 和 Lua 的文件数，物理文件总数及自维护代码分母仍只计一次。

DevEx 在每个样本前后使用当前原生 xtask 可执行文件核对运行来源。维护者运行配置的 `bindings.provenance` 包含 `runtime_receipt`、`target_plan`、`runtime_registration`、`runtime_launch` 和 `environment_document`。前四份收据分别登记精确路径、字节数和 SHA-256。环境说明使用被测后端仓库 `.local-tests/devex` 中的绝对路径，摘要登记在 `contract.environment_sha256`。核验读取原运行代次、进程身份、来源、构建输入和登记端点，不修改运行状态。在维护者配置中，`bindings.metrics_urls.api` 填写已登记 API 就绪端点同源的 `/api/v1/monitor/metrics` 完整 URL，`bindings.metrics_urls.worker` 填写已登记 Worker 就绪端点同源的 `/metrics` 完整 URL。每个阶段仍有 180 秒超时、4 MiB 响应上限，并保存脱敏收据。 任务性能样本的 `.local-tests/devex/runtime.json` 中，`bindings.job_timings` 只包含 `control`、`server_uuid` 和 `mysql_client`，不再配置 Python 采集器。`control` 明确登记隔离回环控制库的 `host`、整数 `port`、`database`、`username`、明文 `password`、`tls_mode`；`mysql_client` 是客户端二进制的绝对路径。控制器自动向内部采集入口传递当前原生产物绑定，在样本目录保存 `native-tool-before.json` 与 `native-tool-after.json`；不要手动指定或临时编译另一个采集器。采集会同时核对服务器 UUID、scope 和 ownership，完成观察复用只读连接并为每轮建立新快照，最终耗时使用全部持久化尝试的排队和执行时间。警告输出不会使有效查询失败；退出、超时、响应不完整或归属变化都不能成为成功样本，诊断保留固定分类并隐藏凭据和原始 SQL 输出。 凭据仅经后端 `.local-tests` 下的会话独占 MySQL option file 传递，启动前核验私有权限，客户端完全退出后删除；首参数固定为 `--defaults-extra-file=<绝对路径>`。子进程清空项目与凭据环境，仅保留必要的操作系统环境；不读取 `MYSQL_PWD`、`password_env` 或 CI 容器环境协议，CI 同样连接显式主机端口。凭据包含 NUL、无法安全编码的字符，或文件权限、写入、清理失败时均拒绝成功。 DevEx HTTP 工作负载结束后在样本目录保存 `http-requests.jsonl`，记录 `scenario`、`worker`、会话内自 1 起的 `sequence`、`operation`、`status`、`duration_ms` 与 `request_id`。时长从节流通过后计到响应读取与解码结束或请求失败。无响应时 `status` 为空值，只有响应头中唯一、规范的小写 UUIDv7 才写入 `request_id`，其余为空值。原工作流汇总继续见 `cycles.jsonl` 和 `session-events.jsonl`。

### Cargo 工具来源核验

完整来源清单的逐文件元数据、链接检查与摘要读取最多使用四个标准 Rust scoped threads，并按原排序合并结果；不缓存旧结果，保留完整文件集合及 Git、指纹前后核验。恢复数据集静态权威读取窗口活动期间（含最终后验核验）保持串行读取，以保留全部实际输入保护。线程创建或读取失败、线程异常终止均失败关闭；原生缓存工具采集在读取同一显式配置后，先串行核验字段格式及双端路径的绝对性与链接安全，再按 Image/Git/Manifest 固定顺序组织三个独立只读核验并发；Image 仍执行完整校验，包含第二次路径核验及全部 ELF/header/hash 检查；返回前等待全部线程，按原顺序报告失败，仅使用摘要匹配的完整来源清单构造绑定。活跃读取窗口仍按原顺序串行、遇错即停，IO 错误分类保留；内部逐文件读取仍最多四线程，不缓存旧结果。该优化不改变接受期限或核验协议。旧 Python 缓存协议逐帧许可读取：只有当前端口处理并回复后才读取下一帧，完整终结响应不等待长期服务的 EOF；stdout 仅由 reader 关闭，主线程有界等待。超时仍失败并保留未知写入、意图与锁，不自动重放；若读取已阻塞，daemon 可能持续到本次短命 CLI 退出，由 OS 收尾，不能据此声称 reader 已退出或服务已清理。此传输不用于捕获失败后继续运行的长驻控制器。完整机制、失败处理及受管工具协议见[架构说明：Cargo 工具来源核验](architecture.md#cargo-工具来源核验)。过程宏共享缓存回归及运行命令也见该节。
